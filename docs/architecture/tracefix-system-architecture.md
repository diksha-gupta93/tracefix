# Product Development Architecture

## TraceFix: Observable and Sandboxed Automated PR Repair Agent

**Domain:** AI Developer Tools, Agentic AI, LLMOps, Platform Engineering
**Primary language:** Python
**Project type:** Production-oriented portfolio project
**Target users:** Software engineering teams, platform teams, AI engineering teams and code reviewers
**Implementation roadmap:** `docs/plan/tracefix-execution-plan.md`

---

## 1. Project Overview

TraceFix is an asynchronous, observable and security-conscious pull-request repair system.

The platform receives a failing GitHub pull request, reproduces the failure inside an isolated execution environment, analyses the relevant code and test output, generates bounded repair attempts using a configurable large language model, and verifies each candidate patch against deterministic quality and security checks.

A successful repair is not automatically merged. Instead, TraceFix publishes a verified repair proposal, supporting evidence and evaluation results to GitHub for human review and approval.

The project is designed to demonstrate senior-level skills in:

* Production-grade AI system design
* Asynchronous and durable workflow orchestration
* LLM observability and evaluation
* Secure execution of untrusted code
* Reliability and failure recovery
* GitHub application integration
* Backend and platform engineering
* Human-in-the-loop AI systems
* Testing, benchmarking and reproducibility
* Idempotent and recoverable external-service integration
* Deterministic platform validation separated from stochastic model evaluation

## 2. Problem Statement

LLM-based coding agents can generate code quickly, but production adoption requires more than successful code generation.

Engineering teams need systems that can answer the following questions:

* Can the generated patch actually resolve the original failure?
* Does the patch introduce new regressions?
* Was the code executed safely?
* Can the repair process recover after infrastructure or model failures?
* Can every decision and execution step be audited?
* How much did the repair cost?
* How long did it take?
* How often does the agent succeed?
* How often do developers accept the proposed patch?
* Can the system detect cases where it should stop and ask for human intervention?
* Can platform failures be distinguished from model-repair failures?
* Can interrupted external operations be recovered without incorrectly claiming exactly-once execution?
* Can stale repair results be prevented from being published after a pull request changes?

TraceFix addresses these concerns by combining deterministic verification, isolated execution, durable workflow state, structured observability, recoverable external operations and human approval controls.

## 3. Product Goal

Build a production-oriented pull-request repair service that:

1. Receives failing GitHub pull-request events.
2. Validates and deduplicates incoming webhook deliveries.
3. Persists repair jobs before starting asynchronous processing.
4. Reproduces failures inside restricted containers.
5. Selects only the code context relevant to the failure.
6. Generates structured and bounded patch attempts.
7. Rejects unsafe or invalid patches before execution.
8. Runs static checks, visible tests and hidden regression tests.
9. Records complete traces, logs, metrics, model usage and evaluation results.
10. Publishes a repair proposal for human approval.
11. Recovers safely from worker, infrastructure and model-provider failures.
12. Distinguishes repair attempts from infrastructure retries.
13. Prevents duplicate submissions and duplicate worker deliveries from creating duplicate jobs or outcomes.
14. Revalidates GitHub pull-request state before publishing or creating a repair branch.
15. Produces reproducible benchmark evidence separating platform correctness from model capability.

---

## 4. Non-Goals

The initial version will not:

* Automatically merge patches into protected branches
* Support every programming language
* Execute arbitrary user-supplied shell commands
* Execute arbitrary shell commands generated by the model
* Accept unrestricted public repository URLs
* Replace human code review
* Guarantee that every software defect can be repaired
* Use Kubernetes before the core workflow is complete
* Attempt large architectural rewrites
* Modify deployment, authentication or CI configuration without explicit approval
* Claim exactly-once execution for remote model-provider operations
* Use live-model benchmark success as a required ordinary CI gate

The first supported ecosystem will be Python repositories using `pytest`.

---

## 5. Product Positioning

TraceFix should be positioned as:

> An observable, reproducible and sandboxed software-repair service that proposes verified patches for failing Python pull requests.

The project should not initially be described as a fully autonomous self-healing system.

A human approval boundary makes the architecture more realistic and safer for production environments.

The project should also distinguish between:

> **Platform correctness:** Does TraceFix behave correctly?

and:

> **Model capability:** How effectively does a particular model repair the benchmark defects?

These are measured independently.

## 8. System Components

### 8.1 GitHub Application

TraceFix will integrate through a GitHub App rather than accepting arbitrary repository URLs.

The GitHub App will use minimal permissions required to:

* Read repository content
* Read pull-request metadata
* Read check results
* Create check runs
* Publish pull-request comments
* Create a draft repair branch after human approval

Incoming webhook data should include:

```text
installation_id
repository_id
repository_full_name
pull_request_number
base_commit_sha
head_commit_sha
delivery_id
event_type
event_action
```

The system must always operate on immutable commit SHAs rather than mutable branch names after ingestion.

Before publication or repair-branch creation, TraceFix must revalidate the current pull-request head SHA.

If the head commit has changed, the previous repair result must be treated as stale and must not be published as the current repair.

---

### 8.2 Webhook and Ingestion Layer

The FastAPI ingress service acts only as a lightweight and reliable entry point.

Responsibilities:

* Validate the GitHub webhook HMAC signature
* Validate event type and payload structure
* Verify that the repository is authorised
* Use the GitHub delivery ID as an idempotency key
* Detect duplicate or redelivered events
* Persist the repair job transactionally
* Enqueue asynchronous work
* Return promptly after acceptance
* Apply rate limits after GitHub integration is hardened

The API must not execute the repair workflow inside the webhook request.

Example endpoints:

```text
POST /api/v1/github/webhooks
POST /api/v1/jobs

GET  /api/v1/jobs/{job_id}
GET  /api/v1/jobs/{job_id}/attempts
GET  /api/v1/jobs/{job_id}/evaluations

POST /api/v1/jobs/{job_id}/approve
POST /api/v1/jobs/{job_id}/reject
```

`POST /api/v1/jobs` is introduced in v0.2 as manual ingress before GitHub webhooks are added in v1.0.

---

### 8.3 Persistent Job Model

PostgreSQL is the source of truth for persistent workflow status from v0.2 onward.

A repair job should conceptually contain:

```python
class RepairJobState(BaseModel):
    job_id: UUID
    idempotency_key: str

    status: JobStatus
    attempt_number: int
    max_attempts: int

    baseline_result: TestResult | None
    failure_analysis: FailureAnalysis | None
    repair_plan: RepairPlan | None
    candidate_patch: PatchProposal | None

    verification_results: list[TestResult]
    evaluation_results: list[EvaluationResult]

    model_provider: str | None
    model_name: str | None
    model_version: str | None
    prompt_version: str | None

    trace_id: str | None

    created_at: datetime
    updated_at: datetime
```

GitHub-specific identity is added when GitHub integration is introduced:

```text
installation_id
repository_id
repository_full_name
pull_request_number
base_commit_sha
head_commit_sha
delivery_id
```

Recommended production-oriented job statuses include:

```text
RECEIVED
VALIDATED
QUEUED
CHECKING_OUT
BASELINE_TESTING
ANALYSING
PLANNING
GENERATING_PATCH
VALIDATING_PATCH
RUNNING_STATIC_CHECKS
VERIFYING
AWAITING_APPROVAL
PUBLISHING
COMPLETED
FAILED
CANCELLED
DEAD_LETTERED
```

Every significant persistent state transition should generate exactly one audit event.

The v0.1 local state is intentionally smaller and does not require PostgreSQL or GitHub identifiers.

---

### 8.4 Queue and Worker Layer

A queue separates incoming API traffic from long-running repair work.

Responsibilities:

* Dispatch repair jobs to workers
* Limit concurrent repair executions
* Retry infrastructure failures
* Apply exponential backoff
* Tolerate duplicate worker delivery
* Move repeatedly failing jobs to a dead-letter queue
* Support clean worker shutdown
* Recover stale claims
* Resume jobs after service restart
* Avoid corrupting repair-attempt metrics when infrastructure retries occur

Retries must distinguish between:

#### Retriable infrastructure failures

* Temporary model-provider outage
* GitHub API timeout
* Docker daemon temporarily unavailable
* Database connection interruption
* Redis interruption
* Worker process termination
* Temporary GitHub publishing failure

#### Non-retriable product failures

* Invalid repository configuration
* Unsupported project type
* Policy-violating patch
* Baseline tests cannot be reproduced
* Unsupported or ambiguous task
* Maximum repair attempts reached

A repair attempt and an infrastructure retry are different concepts.

Infrastructure retries must not increment the repair attempt count.

---

### 8.5 External Operation Recovery

Some operations cross system boundaries and cannot safely be treated as exactly-once.

Examples include:

* model-provider requests
* sandbox execution
* later GitHub publishing operations

From v0.2, TraceFix should persist an external-operation record containing fields such as:

```text
operation_id
job_id
attempt_number
operation_type
request_fingerprint
status
started_at
completed_at
result_reference
error_category
```

Model requests should follow:

```text
Persist STARTED
    ↓
Call provider
    ↓
Persist COMPLETED + result reference
```

If a worker terminates after the provider processed a request but before TraceFix records completion, the operation is considered uncertain.

TraceFix must:

* reuse a recorded completed result where possible;
* distinguish unresolved operations from known failures;
* record possible duplicate provider cost if retrying an uncertain request;
* avoid claiming exactly-once remote model execution.

Sandbox execution is different because it is disposable and locally controlled.

On uncertain sandbox execution:

* remove stale containers where possible;
* recreate the disposable workspace;
* safely rerun the operation;
* ensure no orphan container remains.

## 9. LangGraph Repair Workflow

The repair workflow should be deterministic where possible and agentic only where useful.

### Node 1: Prepare Repository

For local benchmark execution:

* Load the benchmark case
* Checkout the required commit
* Create an isolated workspace
* Prevent path traversal
* Compute repository fingerprint
* Record commit identity

For GitHub execution:

* Obtain a short-lived GitHub installation token
* Clone the authorised repository
* Checkout the exact head commit SHA
* Validate repository structure
* Read trusted project configuration
* Compute repository and dependency fingerprints
* Create an isolated workspace

---

### Node 2: Run Baseline

* Execute the original failing test before generating a patch
* Run the test only inside the sandbox
* Capture stdout, stderr, exit code where available and duration
* Confirm that the reported failure is reproducible
* Stop if the baseline unexpectedly passes
* Store complete baseline evidence
* Do not invoke the model if the failure cannot be reproduced

---

### Node 3: Classify Failure

Runtime failure classification should use categories such as:

```text
syntax_failure
import_or_dependency_failure
assertion_failure
incorrect_exception_behaviour
type_related_failure
timeout
test_environment_failure
unsupported_or_ambiguous
```

Runtime failure categories are distinct from benchmark bug categories.

For example:

```text
Benchmark bug category:
boundary_condition

Observed failure category:
assertion_failure
```

The benchmark taxonomy must not be reused as the runtime failure-classification enum.

---

### Node 4: Select Relevant Context

Build a bounded context package containing:

* Issue description
* Failing test
* Stack trace
* Referenced source files
* Relevant function or class definitions
* Imports and type definitions
* Repository instructions
* Protected-path policy
* Prior attempt failure evidence when retrying

The following must be excluded:

* Hidden tests
* Reference patches
* Unrelated files
* Secrets or credentials
* Generated benchmark/evaluation artifacts

The full repository should not be sent to the model unnecessarily.

---

### Node 5: Plan Repair

Generate a structured repair plan describing:

* Suspected root cause
* Files expected to change
* Intended behavioural correction
* Risks
* Validation strategy
* Whether the task is appropriate for autonomous repair

Canonical conceptual schema:

```python
class RepairPlan(BaseModel):
    suspected_root_cause: str
    files_expected_to_change: list[str]
    intended_behavioural_correction: str
    risks: list[str]
    validation_strategy: str
    autonomous_repair_suitable: bool
```

The model's belief that a repair is suitable does not override system policy.

---

### Node 6: Generate Patch

The model must return a structured response rather than unrestricted prose.

Canonical schema:

```python
class PatchProposal(BaseModel):
    summary: str
    root_cause: str
    files_changed: list[str]
    unified_diff: str
    expected_effect: str
    risks: list[str]
    confidence: float
```

`confidence` should use a bounded range of:

```text
0.0 .. 1.0
```

The proposed diff remains inert data until it passes schema and policy validation.

Invalid structured output must become a diagnostic failure.

It must not be silently coerced into validity.

---

### Node 7: Validate Patch Policy

Reject the patch before execution when it:

* Modifies protected files
* Changes more files than permitted
* Exceeds the line-change threshold
* Contains binary content
* Adds secrets or credentials
* Disables or skips tests
* Removes important assertions
* Weakens tests
* Changes CI or security policy
* Adds unrestricted subprocess execution
* Introduces unapproved dependencies
* Modifies hidden tests
* Modifies benchmark metadata
* Modifies reference patches

Patch-policy evaluation must be deterministic and occur before untrusted candidate execution.

---

### Node 8: Run Static Checks

Initial deterministic checks include:

* Patch application validation
* Changed-file validation
* Python compilation
* AST parsing
* Ruff linting
* MyPy type checking where supported
* Bandit security analysis

The hardened validation gate later adds:

* Secret detection
* Dependency-diff inspection
* Complexity comparison
* Suspicious generated-file detection
* Dependency-policy validation

Failures block progression unless an explicit future architecture decision makes a check advisory.

---

### Node 9: Verify in Sandbox

Execute in increasing scope:

1. Original targeted failing test
2. Full visible test suite
3. Hidden regression tests

Potential later additions:

4. Coverage analysis
5. Mutation testing

A candidate that passes visible tests but fails hidden tests is a failed repair candidate.

---

### Node 10: Evaluate Candidate

Calculate functional, quality and efficiency evidence including:

* Functional pass/fail
* Files changed
* Lines added
* Lines removed
* Sandbox execution duration
* Model latency
* Input tokens
* Output tokens
* Estimated cost where available

Later versions add broader reliability, security and human-outcome metrics.

---

### Node 11: Route Result

Possible outcomes include:

```text
Candidate passes all required checks
    → Await human approval when GitHub integration exists
    → Produce successful local artifact in v0.1

Candidate fails and repair attempts remain
    → Use prior failure evidence for next repair attempt

Candidate violates policy
    → Stop and escalate

Static checks fail
    → Candidate failure / diagnostic outcome

Maximum repair attempts reached
    → Produce terminal failure analysis

Failure cannot be reproduced
    → Stop with diagnostic result

Infrastructure failure
    → Infrastructure retry where permitted

Malformed model output
    → Structured diagnostic failure
```

Repair-attempt limits are versioned:

```text
v0.1: maximum 1 repair attempt

v0.2+: maximum 3 repair attempts
```

Later attempts receive evidence from previous candidate failures.

Infrastructure retries do not consume repair attempts.

## 10. Sandbox Security Architecture

Generated or repository code must never run directly on the host.

The Docker sandbox is introduced incrementally but must ultimately enforce all of the following controls.

Each execution container should use:

* Linux container
* Non-root user
* Network disabled during untrusted execution
* Read-only root filesystem
* Explicit temporary writable workspace
* CPU quota
* Memory limit
* PID limit
* Execution timeout
* stdout size limit
* stderr size limit
* Output truncation markers
* Dropped Linux capabilities
* `no-new-privileges`
* Docker default seccomp profile or an approved project-owned profile
* No host credential mounts
* No developer home-directory mount
* No model-provider credentials
* No GitHub credentials
* No Docker socket
* Validated mount sources
* Unique container identity
* Automatic container destruction
* Cleanup in failure paths

TraceFix must reject:

```text
seccomp=unconfined
```

The initial implementation should not introduce an unnecessarily restrictive custom Python syscall allowlist.

### Suggested Initial Resource Limits

```text
CPU:       1
Memory:    512 MB
PIDs:      128
Timeout:   120 seconds
stdout:    1 MB
stderr:    1 MB
```

These are configurable engineering defaults rather than permanent product guarantees.

### Command Validation

The sandbox must not accept arbitrary shell commands from:

* webhook payloads;
* benchmark metadata;
* model output.

v0.1 permits only strictly validated pytest-oriented execution commands.

Examples of prohibited unrestricted execution include:

```text
bash -c
sh -c
PowerShell
cmd.exe
```

### Adversarial Security Validation

Sandbox tests should verify:

* Network access is blocked
* Host credentials are inaccessible
* Docker socket is inaccessible
* Writes outside the workspace are blocked
* Privilege escalation attempts are blocked
* Excessive process creation is bounded
* Memory exhaustion is bounded
* Infinite execution is terminated
* stdout/stderr growth is bounded
* Containers are removed after crashes
* No secrets appear in container environment
* Invalid host mounts are rejected

### Dependency Preparation

Some repositories require dependency installation.

Dependency handling should be separated into two phases.

#### Controlled dependency phase

* Use approved package registries
* Prefer lock files
* Cache trusted dependencies
* Enforce installation time and size limits
* Record dependency hashes
* Validate dependency changes

#### Untrusted execution phase

* Disable network access
* Remove credentials
* Execute only predefined validation commands

## 11. Protected Path Policy

By default, automated repairs should not modify:

```text
.github/workflows/
infra/
terraform/
deployment/
docker/
authentication/
authorization/
security/
secrets/
migrations/
dependency lock files
```

Exceptions require an explicit future approval mechanism and are not part of the initial automated repair path.

The policy should also prevent the agent from:

* Removing failing tests
* Marking tests as skipped
* Weakening assertions
* Disabling lint or type checks
* Silencing exceptions without justification
* Adding broad ignore rules
* Replacing implementations with hard-coded test outputs
* Modifying hidden tests
* Modifying benchmark metadata
* Modifying reference patches
* Introducing unapproved dependencies

The model's repair plan does not override the protected-path policy.

## 12. Human-in-the-Loop Approval

TraceFix should never directly merge generated code into a protected branch.

After successful verification, the system should publish:

* Root-cause analysis
* Proposed patch
* Files changed
* Tests executed
* Static-analysis results
* Regression-test results
* Security-policy results
* Model and prompt versions
* Number of repair attempts
* Infrastructure retry information where relevant
* Token usage
* Cost estimate
* Total latency
* Model confidence
* Risk information

Before approval is acted upon, TraceFix must revalidate:

* Current PR state
* Current head commit SHA
* Repository authorization
* GitHub App installation access

The initial v1.0 approval workflow supports:

```text
Approve
Reject
```

### Approval

Approval permits TraceFix to create a draft repair branch from the correct immutable commit.

It does not permit TraceFix to merge into a protected branch.

### Rejection

Rejection records the human decision and creates no repair branch.

Human decisions should be stored as evaluation labels for future analysis.

Reviewer-feedback-driven repair attempts may be added later but are not required for the initial v1.0 approval flow.

## 14. Evaluation Framework

Evaluation must separate:

1. deterministic platform correctness; and
2. live-model repair capability.

### Deterministic Platform Evaluation

Uses a fake model provider with predetermined plans and patches.

Purpose:

* Verify graph behavior
* Verify schema handling
* Verify patch application
* Verify policy enforcement
* Verify static checks
* Verify sandbox execution
* Verify artifact generation
* Verify CLI behavior

Characteristics:

* Deterministic
* Stable
* No external model credentials
* No live model network dependency
* Suitable for ordinary CI
* CI-blocking when platform behavior fails

### Live-Model Evaluation

Uses a real model provider.

Purpose:

* Measure repair capability
* Measure model latency
* Measure token usage
* Estimate cost
* Compare model/prompt configurations

Characteristics:

* Non-deterministic
* May incur cost
* May be affected by provider/network failures
* Runs manually or on a controlled schedule
* Does not block ordinary CI because model repair failure is a valid benchmark result

A live model failing to repair a defect is a benchmark outcome.

A provider or platform infrastructure failure is an execution failure and must be classified separately.

---

### 14.1 Functional Correctness

* Repair success within one attempt
* Repair success within two attempts
* Repair success within three attempts

## 15. Correct Use of Repair Metrics

Because later repair attempts receive feedback from earlier failures, the primary sequential metric should be:

```text
Repair success within N attempts
```

For example:

```text
Repair success within 1 attempt
Repair success within 2 attempts
Repair success within 3 attempts
```

Reports may use convenient shorthand:

```text
success@1
success@2
success@3
```

but this must be documented as **cumulative sequential repair success**.

It must not be confused with statistical `pass@k`.

`pass@k` should be used only when evaluating independently sampled candidate patches under equivalent conditions.

Evaluation reports should include confidence intervals once the benchmark size is sufficient.

Example future report:

```text
Repair success within 1 attempt: 46%
Repair success within 3 attempts: 68%
Hidden-test pass rate: 63%
Regression failure rate: 4%
Median repair latency: 51 seconds
p95 repair latency: 128 seconds
Median attempts per successful repair: 2
Infrastructure retry rate: 3%
Human patch acceptance rate: 72%
```

These values are examples only and must never be presented as project results unless measured.

## 29. Final Product Statement

TraceFix is not intended to be only an LLM demonstration.

It is designed to show how AI-generated software changes can be transformed into a reliable engineering workflow through:

* Durable workflow execution
* Bounded agent behavior
* Typed contracts
* Secure isolation
* Deterministic verification
* Statistical evaluation
* Reproducible benchmarking
* Failure recovery
* Explicit infrastructure-retry semantics
* Full observability
* Immutable repository identity
* Human oversight

The central engineering message of the project is:

> Building a production-quality AI agent requires much more than generating a correct answer. It requires security, measurable quality, operational reliability, traceability, recoverable execution and controlled human decision-making.

And the core TraceFix principle is:

> A generated patch is a proposal, not proof. Trust is earned through deterministic verification, isolated execution, reproducible evidence and explicit human authority.
