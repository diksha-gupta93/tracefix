# Task 0.1.7 — Validate Patch Policy

## 1. Goal

Add a deterministic, typed patch-policy gate that inspects an existing `PatchProposal` and rejects
unsafe or out-of-bounds changes before patch application, static checks, Docker sandbox execution,
or any other execution of candidate code.

The gate must report every independently detectable violation in a stable order. A policy-compliant
proposal passes through unchanged as data; approval does not mean that the patch applies, compiles,
passes tests, or is otherwise correct.

## 2. Context

Task 0.1.6 produces a strictly validated, inert unified diff whose normalized changed-path set agrees
with `PatchProposal.files_changed` and `RepairPlan.files_expected_to_change`. It does not enforce
security or change-scope policy. Task 0.1.5 already defines an immutable `ProtectedPathPolicy` with
the architecture-default protected paths and no exceptions. Trusted benchmark manifests also carry
case-specific `forbidden_changed_files`; those values are not model context and remain trusted policy
metadata.

This task implements workflow Node 7 only. The execution plan requires rejection for protected or
excessive changes, binary data, secrets, test manipulation, CI/security changes, unrestricted
subprocess execution, unapproved dependencies, and evaluator-only benchmark material. Policy
evaluation is a pure host-side inspection of inert text. Candidate application and all static or
runtime validation remain later tasks.

## 3. In Scope

- Add one typed policy entry point that accepts:
  - the existing `PatchProposal`;
  - an immutable `PatchPolicy` assembled from the existing `ProtectedPathPolicy`, trusted
    case-specific forbidden paths, fixed v0.1 limits, and a dependency allowlist;
  - no repository path, filesystem adapter, command runner, or sandbox adapter.
- Add strict, frozen Pydantic v2 contracts for:
  - `PatchPolicy`;
  - `PatchPolicyViolationCode`;
  - `PatchPolicyViolation`;
  - `PatchPolicyResult`;
  - a stable typed input/parse diagnostic for malformed or inconsistent caller input.
- Revalidate and parse the unified diff as inert UTF-8 text. A small shared typed diff parser may be
  extracted from `app.agent.planning` so planning and policy use one structural interpretation.
  Preserve all Task 0.1.6 behavior and diagnostics during that refactor.
- Evaluate all rules below without short-circuiting after the first ordinary policy violation:

  | Order | Violation code | Required rejection |
  | ---: | --- | --- |
  | 1 | `protected_path_modified` | A changed path is equal to or below an architecture-default protected path or a trusted case-specific forbidden path. |
  | 2 | `too_many_files` | The proposal changes more than 3 unique files. |
  | 3 | `line_change_limit_exceeded` | Added plus removed hunk lines exceed 200 across the proposal; headers, context, and the no-newline marker do not count. |
  | 4 | `binary_content` | The diff contains NUL/non-text control data or a recognized Git binary-diff marker such as `GIT binary patch` or `Binary files ... differ`. |
  | 5 | `secret_detected` | Any proposal text contains a high-confidence credential/private-key signature. |
  | 6 | `test_disabled` | A test file is deleted, a test definition is removed, or an added line introduces a recognized skip/skip-if/xfail/imperative-skip construct. |
  | 7 | `assertion_removed` | A removed hunk line removes a Python `assert` statement or a recognized pytest/unittest assertion call/context manager. |
  | 8 | `ci_or_security_config_modified` | A changed path identifies CI automation or security policy/configuration. |
  | 9 | `unrestricted_subprocess_introduced` | An added line introduces a direct process/shell execution import or call for which this v0.1 policy grants no exception. |
  | 10 | `unapproved_dependency_added` | An added dependency declaration cannot be mapped to an allowlisted normalized package name. |
  | 11 | `hidden_test_modified` | A changed path has an `evaluator` or `hidden_tests` component, or otherwise identifies a hidden-test path. |
  | 12 | `benchmark_metadata_modified` | A changed path is benchmark metadata, including any `manifest.json` under a benchmark case or content under a `benchmarks` tree other than repository source paths supplied for repair. |
  | 13 | `reference_patch_modified` | A changed path identifies `reference.patch` or another evaluator reference-patch path. |

- Match paths using normalized relative POSIX identities and case-insensitive comparisons. Directory
  rules match complete path components, not arbitrary substrings. Reject path aliases, absolute,
  drive/UNC/device, backslash, traversal, control-character, duplicate, and inconsistent path input
  as malformed input rather than attempting partial policy evaluation.
- Use the protected paths already established by Task 0.1.5:
  `.github/workflows/`, `authentication/`, `authorization/`, `deployment/`, `docker/`, `infra/`,
  `migrations/`, `security/`, `secrets/`, `terraform/`, `Pipfile.lock`, `poetry.lock`, and `uv.lock`.
  Add the trusted manifest's `forbidden_changed_files` to the effective protected set. There are no
  v0.1 exceptions.
- Treat CI/security configuration as an explicit rule even when the same path also triggers the
  general protected-path rule. At minimum, recognize `.github/workflows/`, `.github/actions/`,
  `.gitlab-ci.yml`, `.circleci/`, `azure-pipelines.yml`, `Jenkinsfile`, `Dockerfile`, `docker/`,
  `security/`, seccomp profiles, Bandit configuration, and repository security-policy files.
- Secret detection uses fixed, local, high-confidence signatures only: PEM/OpenSSH private-key
  blocks; AWS access-key identifiers; GitHub personal/access token formats; and non-placeholder
  values assigned to names such as `api_key`, `access_token`, `client_secret`, `password`, or
  `private_key`. Scan all human/model-controlled strings in the proposal, but never reproduce a
  matched value in a result, exception, or log.
- Test-disable detection recognizes Python test paths (`tests/`, `test_*.py`, and `*_test.py`), file
  deletion, removed `def test_...`, and newly added `pytest.skip`, `pytestmark` skip/xfail,
  `@pytest.mark.skip`, `@pytest.mark.skipif`, `@pytest.mark.xfail`, and `unittest.skip*` constructs.
  Comments or string literals containing these words must not trigger solely by substring.
- Assertion-removal detection recognizes removed Python `assert` statements, `pytest.raises` and
  `pytest.warns` contexts, and standard `unittest.TestCase` `assert*` calls. Added assertions and
  unchanged context do not count.
- Unrestricted subprocess detection recognizes newly added imports or calls that directly expose
  process/shell execution, including `subprocess`, `os.system`, `os.popen`, `os.spawn*`, and
  `shell=True`. Because Task 0.1.7 has no approved command abstraction for candidate code, all such
  newly introduced direct execution is rejected.
- Dependency inspection recognizes the current Python ecosystem only: `pyproject.toml`,
  `requirements*.txt`, `setup.py`, `setup.cfg`, `Pipfile`, `Pipfile.lock`, `poetry.lock`, and
  `uv.lock`. Normalize PEP 503-style names for comparison. The default v0.1 allowlist is empty.
  Ambiguous added dependency syntax in one of these files fails closed as unapproved; comments and
  whitespace alone do not.
- Return `PatchPolicyResult(approved=True, violations=())` for a valid patch, or
  `approved=False` with an immutable tuple of violations. Order violations by the rule table above,
  then normalized path, source line, and a final stable message key. Deduplicate identical findings
  without hiding distinct rule violations on the same path.
- Each violation contains only a stable enum code, a constant safe message, and optional normalized
  relative path/line metadata. It must not retain or echo diff lines, secret values, proposal prose,
  or host paths.
- Add focused unit tests for every execution-plan rejection rule, valid pass-through, combined
  violation reporting, and deterministic ordering.

## 4. Out of Scope

- Applying a patch, modifying a prepared repository, invoking `git`/`patch`, or checking whether a
  diff applies. That is Task 0.1.8.
- Python compilation, AST validation of the resulting files, Ruff, mypy, Bandit, changed-file
  verification against a post-apply tree, or any other static gate from Task 0.1.8.
- Running visible/hidden tests, executing candidate code, or evaluating repair success. Those are
  Task 0.1.9.
- LangGraph nodes, routing, state transitions, CLI exit codes, or artifact persistence. Those are
  Task 0.1.10a.
- Production fake/live model providers, benchmark commands, retries, persistence, queues, APIs,
  GitHub integration, human approval, or observability.
- v0.2 static-gate hardening: general secret-scanning products, dependency-diff comparison against
  resolved environments, complexity comparison, suspicious generated-file detection, and a
  configurable organization-wide dependency policy.
- Proving semantic test strength, detecting every possible assertion weakening, hard-coded test
  output, exception swallowing, or arbitrary code obfuscation. This task implements the bounded,
  deterministic signatures specified above.
- Enforcing `expected_changed_files` as correctness policy. Task 0.1.6 already enforces agreement
  among the plan, proposal, and diff; benchmark expected paths remain evaluation data.
- Reading evaluator files, hidden tests, reference patches, prepared repository content, manifests,
  lock files, or host environment values during policy evaluation.
- Adding policy override/exception mechanisms. Human approval does not bypass this v0.1 gate.

## 6. Python and Packaging Requirements

- Use the existing CPython `>=3.14,<3.15` interpreter and `.venv`; do not install another Python or
  create another environment.
- Use Pydantic v2 for cross-module policy input, result, violation, and diagnostic contracts. New
  models are strict, extra-forbidding, and frozen.
- Reuse `PatchProposal` and `ProtectedPathPolicy`; do not change their established meaning or
  duplicate them. Do not add a policy result to `LocalRepairCaseState` in this task.
- Fully type public and cross-module interfaces. Do not use `Any`, untyped dictionaries, unchecked
  casts, or implicit stringly typed policy results.
- Use standard-library `ast`, `re`, `pathlib`, and immutable collections as needed. Content rules
  should tokenize or parse isolated added/removed Python lines conservatively where that avoids
  comment/string false positives; parsing must never import or execute candidate code.
- Do not use `eval`, `exec`, dynamic imports, shell commands, subprocesses, repository imports, or
  filesystem access to validate a proposal.
- Add no runtime or development dependency. In particular, do not add a secret scanner, diff/patch
  library, dependency parser, packaging library, or security-analysis tool in this task.
- Keep existing setuptools discovery and dependency/version ranges unchanged.
- Policy input is bounded by the Task 0.1.6 provider-response limit. The validator must still use
  linear or predictably bounded passes and must not compile attacker-controlled regular expressions
  or use patterns vulnerable to catastrophic backtracking.

## 7. Development Tool Requirements

- Retain the existing Ruff, strict mypy, pytest, and `python scripts/check.py` configuration.
- Unit tests must be deterministic and operate entirely on in-memory proposal/policy values. They
  must not invoke Docker, touch benchmark evaluator content, use credentials, read ambient
  environment variables, access the network, or modify fixture repositories.
- Parameterize rule-focused examples where useful, but retain an explicit named test proving every
  rejection rule in the execution plan.
- Test safe public behavior rather than private regex implementation. Parser extraction must retain
  the existing Task 0.1.6 structural-diff regression suite.
- No test may be weakened, skipped, deleted, or rewritten merely to make the implementation pass.

## 8. Cross-Platform Requirements

- Produce identical policy decisions, normalized paths, line counts, violation metadata, and
  ordering on Windows and Linux for identical proposal/policy values.
- Normalize CRLF and lone CR to LF before structural and line inspection. Count logical diff lines,
  not platform-native separators or encoded byte length.
- Repository identities use relative `PurePosixPath` semantics. Native backslashes, drive-relative
  paths, absolute/UNC/device paths, traversal, empty/dot components, NULs, control characters, and
  case-fold aliases fail closed.
- Path comparisons are case-insensitive and component-aware even on a case-sensitive host, so a
  casing alias cannot bypass policy.
- Do not depend on shell quoting, locale encodings, platform file modes, symlink behavior, Docker,
  or Git configuration.
- Windows commands use `.venv\Scripts\python.exe`; POSIX commands use `.venv/bin/python`. The
  activated, portable command remains `python scripts/check.py`.

## 10. Security Considerations

- Treat the entire proposal, diff, policy input, and all embedded paths/content as untrusted. Policy
  text cannot define new rules, grant an exception, change limits, select commands, or trigger tool
  use.
- Evaluate policy before any patch application, compilation, import, static tool, Docker call, or
  candidate execution. Approval is necessary but not sufficient for later progression.
- Fail closed on malformed/inconsistent proposal, diff, policy, or path data. Do not silently skip a
  file/hunk or return a partial approval.
- Never read or expose hidden tests, reference patches, benchmark expected answers, secrets, the
  developer environment/home directory, absolute host paths, model/GitHub credentials, or Docker
  state.
- Never include a detected secret, matching source line, diff body, proposal prose, or raw parser
  exception in a violation, diagnostic, log, assertion message, or snapshot. Test secret fixtures
  use unmistakably synthetic values.
- The default dependency allowlist is empty, protected-path exceptions are empty, and model output
  cannot modify either value.
- Avoid regex denial of service and unbounded diagnostic growth. Aggregate findings over the bounded
  proposal, deduplicate them, and expose only safe metadata.
- A valid result must preserve the original `PatchProposal` unchanged; the policy gate never rewrites
  a patch to make it acceptable.

## 11. Failure Cases

Expected typed input diagnostics must cover:

- wrong runtime type, Pydantic-invalid or mutated `PatchProposal`, `PatchPolicy`, or
  `ProtectedPathPolicy`;
- missing/empty protected policy, any protected-path exception, invalid threshold, malformed or
  duplicate case-forbidden path, malformed allowlist name, or nondeterministically ordered policy;
- invalid/aliased/absolute/backslash/traversal/control-bearing changed path;
- disagreement among `files_changed` and parsed diff paths, duplicate file identity, unsupported
  header, malformed/missing hunk, or inconsistent hunk counts;
- parser input that cannot be inspected completely and safely.

Ordinary policy findings return a complete rejected `PatchPolicyResult`, not an exception. Binary
content must be classified as `binary_content` when its recognized marker/control signature can be
identified safely. Malformed structure that prevents trustworthy inspection is a typed input failure
and cannot return approval.

The validator must not return partial approval, mutate the proposal/policy, echo unsafe data, invoke
later gates, or convert process-control exceptions such as `KeyboardInterrupt` and `SystemExit` into
policy diagnostics.

## 12. Acceptance Criteria

1. One typed, deterministic policy entry point evaluates an existing inert `PatchProposal` without
   filesystem, environment, network, Docker, subprocess, or candidate-code access.
2. The effective protected set combines the existing architecture-default `ProtectedPathPolicy`
   with trusted case-specific `forbidden_changed_files`, grants no exceptions, and uses normalized
   component-aware case-insensitive matching.
3. A patch changing more than 3 unique files or more than 200 added-plus-removed hunk lines is
   rejected with exact boundary tests for 3/4 files and 200/201 lines.
4. Binary content and high-confidence secrets are rejected without retaining or disclosing matched
   content.
5. Test deletion/disable signatures and removed assertion signatures are rejected, while comments,
   string literals, added assertions, and unchanged diff context do not create false positives.
6. CI/security configuration changes, newly introduced direct subprocess/shell execution, and
   unapproved or ambiguous dependency additions are rejected.
7. Hidden tests, benchmark metadata, and reference patches are rejected by independent explicit
   rules even if another protected-path rule also matches.
8. Every execution-plan rejection category has at least one focused unit test, and a valid current
   fixture-shaped source-only patch passes unchanged.
9. A multi-violation proposal reports all safely detectable findings, deduplicates identical ones,
   retains distinct codes for the same path, and orders them by the fixed rule/path/line/message
   sequence on every run.
10. Policy violations use strict immutable typed results with only safe constant text and optional
    normalized path/line metadata; malformed caller input uses a distinct typed diagnostic and never
    approves.
11. CRLF/LF and path-casing variants cannot change or bypass decisions except that normalized output
    uses canonical LF/POSIX representation.
12. Task 0.1.6 plan/generation behavior and tests remain unchanged, including structural patch
    validation and inert output.
13. Formatting, linting, strict typing, focused tests, the full test suite, canonical validation, and
    diff checks pass under Python 3.14.
14. No patch application, static gate, sandbox candidate execution, graph/routing, CLI, persistence,
    provider, adjacent/future behavior, dependency, commit, or push is introduced.

## 13. Tests and Validation Commands

Add focused tests covering:

- valid single-file and valid three-file pass-through, proposal immutability, and result schema
  strictness/immutability/serialization;
- each architecture-default protected directory/file, component-boundary near misses,
  case-fold aliases, and trusted case-specific forbidden paths;
- exactly 3 versus 4 files; exactly 200 versus 201 total added/removed lines; replacements count as
  one removal plus one addition; context/header/no-newline lines do not count;
- NUL/control data and recognized binary markers;
- every supported synthetic secret signature, proposal-field coverage, placeholders/near misses, and
  proof that result/exception representations do not contain matched values;
- deleted test files, removed test definitions, each recognized skip/xfail form, and comment/string
  near misses;
- removed `assert`, `pytest.raises`/`pytest.warns`, and `unittest` assertions; added/unchanged and
  similarly named non-assertion near misses;
- every CI/security path class and non-policy names containing similar substrings;
- each direct subprocess/shell signature plus comment/string/ordinary identifier near misses;
- supported dependency files, normalized package names, empty-allowlist rejection, explicit
  allowlist pass, comments/whitespace, and ambiguous syntax fail-closed behavior;
- hidden-test, evaluator, benchmark-manifest, benchmark-tree, and reference-patch path variants;
- one proposal triggering multiple rules, overlapping protected/specific violations, duplicate
  finding suppression, and stable ordering under shuffled policy/proposal construction;
- LF/CRLF equivalence and malformed/unsafe/case-aliased paths;
- malformed policy/proposal/diff input, safe typed diagnostics, non-mutation, and preservation of
  `KeyboardInterrupt`/`SystemExit` behavior;
- absence of filesystem access, patch application, subprocess, Docker, network, environment reads,
  evaluator reads, candidate execution, and later-gate calls.

## 15. Definition of Done

- All thirteen execution-plan rejection categories are implemented through strict typed,
  deterministic, non-mutating inspection and have focused acceptance evidence.
- A valid bounded source-only proposal receives an immutable approval result and remains inert; a
  policy-violating proposal receives all safely detectable, deduplicated violations in stable order.
- Malformed or inconsistent input fails closed through safe typed diagnostics and can never be
  mistaken for an ordinary approved result.
- Policy validation performs no filesystem/environment/network/process/Docker access, exposes no
  secret or evaluator content, and necessarily precedes every later candidate-processing gate.
- Section 13 gates pass with Python 3.14. Existing integration/security tests pass or skip only under
  their established local capability policy.
- README and progress documentation are updated during implementation; governing documents and the
  approved specification remain unchanged.
- No application behavior outside Task 0.1.7, unrelated abstraction/dependency, commit, or push is
  included.
- The implementation completion report lists files changed, commands, test results, acceptance
  evidence, architecture decisions, security controls, assumptions, and remaining risks/deferred
  work.

## Assumptions Requiring Human Review

1. **Scope limits:** approve a maximum of 3 changed files and 200 added-plus-removed hunk lines. The
   architecture and execution plan require thresholds but do not assign values.
2. **Policy contract:** approve returning an immutable aggregate `PatchPolicyResult` for ordinary
   violations and using a separate typed diagnostic/exception for malformed caller input. The
   existing state has no policy-result field, and graph/state routing is deferred to Task 0.1.10a.
3. **Trusted policy assembly:** approve combining the Task 0.1.5 `ProtectedPathPolicy` with
   `Manifest.forbidden_changed_files` supplied by a trusted caller, without letting the policy gate
   read the manifest or evaluator tree. `expected_changed_files` is not a policy allowlist.
4. **Overlapping findings:** approve reporting explicit CI/security, hidden-test, benchmark-metadata,
   and reference-patch violations even when the same path also reports `protected_path_modified`.
   This supports complete rule evidence and combined reporting.
5. **Secret signatures:** approve the bounded high-confidence local signatures in Section 3 and
   scanning every proposal string. Comprehensive entropy/history/scanner-based detection remains
   Task 0.2.7 hardening.
6. **Test and assertion signatures:** approve the named Python/pytest/unittest rules as the v0.1
   deterministic meaning of “disable tests” and “remove assertions.” General semantic weakening is
   intentionally not claimed.
7. **Process policy:** approve rejecting every newly introduced direct `subprocess`/shell-execution
   construct because v0.1 defines no candidate-code command allowlist or exception mechanism.
8. **Dependency policy:** approve an empty default dependency allowlist, PEP 503 name normalization,
   and fail-closed handling of ambiguous added declarations in the named Python dependency files.
9. **Benchmark path rule:** approve treating evaluator/hidden-test/reference paths and benchmark
   `manifest.json` metadata as forbidden by path identity, while allowing ordinary repair source
   paths already rooted inside a prepared benchmark repository.
10. **Shared parser refactor:** approve extracting the existing Task 0.1.6 inert unified-diff parser
    into one small typed module if needed for line-level policy inspection, provided planning behavior
    and diagnostics remain unchanged.
