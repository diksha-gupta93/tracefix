# Task 0.1.12 — Safe LangSmith Diagnostic Observability

## Goal and accepted evidence

Add opt-in, metadata-only LangSmith tracing at existing benchmark, case, graph-node,
provider, structured-output, patch-envelope, policy, static-check, verification, and evaluation
boundaries. This task diagnoses where a later run fails; it does not change repair behavior or fix
model output.

GitHub Actions run `43051385469` is the accepted pre-task live evidence. It used provider `groq`
and model `openai/gpt-oss-120b`; all five development cases executed, with `not_run=0`,
`execution_failure=0`, `repair_success=0`, `repair_failure=5`, `execution_status=completed`, and
process exit `0`. Every repair failure terminated as `malformed_model_output`. The existing safe
report proves the infrastructure, pacing, artifact, usage, cost, and fail-fast behavior worked,
but it cannot identify the exact internal structured-output failure stage. No claim is made that
LangSmith has diagnosed that failure until a separately authorized traced benchmark runs.

## Architecture

- `DiagnosticTracer` and `DiagnosticSpan` are project-owned typed interfaces. Core graph and
  planning logic depend only on these interfaces.
- The default is a validating no-op tracer. Ordinary repair, deterministic tests, the fake-model
  benchmark, ordinary CI, and local development need neither LangSmith configuration nor a key.
- `LangSmithDiagnosticTracer` is manual instrumentation using the official SDK. It creates
  metadata-only `RunTree` instances with empty inputs, empty outputs, empty tags, no attachments,
  and no serialized callable data; it never traces function arguments or return values.
- `TRACEFIX_LANGSMITH_DIAGNOSTICS=true` is the only application-level opt-in. The LangSmith and
  LangChain framework tracing switches remain false. Graph invocation additionally runs inside an
  explicit `tracing_context(enabled=False, parent=False)` guard, so LangGraph cannot install a
  `LangChainTracer` even when a hostile ambient process setting attempts to enable one.
- The SDK client is always constructed with `tracing_mode="langsmith"`, `hide_inputs=True`,
  `hide_outputs=True`, and `omit_traced_runtime_info=True`. TraceFix verifies the effective client
  mode is `langsmith`, the effective API URL is the fixed URL, and no OTEL exporter exists before
  returning the tracer. The corresponding hide environment flags must also be explicitly true for
  enabled live diagnostics.
- The client API URL is explicitly pinned to `https://api.smith.langchain.com`. Non-empty
  `LANGSMITH_ENDPOINT`, `LANGCHAIN_ENDPOINT`, `LANGSMITH_RUNS_ENDPOINTS`, or
  `LANGCHAIN_RUNS_ENDPOINTS` values fail preflight without including their values in diagnostics.
- OTEL and hybrid export are forbidden. Non-empty `LANGSMITH_TRACING_MODE`,
  `LANGCHAIN_TRACING_MODE`, `LANGSMITH_OTEL_ENABLED`, `LANGCHAIN_OTEL_ENABLED`,
  `LANGSMITH_OTEL_ONLY`, `LANGCHAIN_OTEL_ONLY`, `OTEL_EXPORTER_OTLP_ENDPOINT`, or
  `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` values also fail preflight. LangSmith 0.14.x reads the first
  six values when selecting its trace transport and the last two when constructing an OTLP
  exporter; rejecting them is defense in depth around the explicit REST-only client argument.
  Other OTEL variables that cannot select this client's transport or destination are not rejected.
- TraceFix owns the active-run context and supplies explicit parent runs to each `RunTree`.
  LangSmith ambient/current-run context is never used for hierarchy. TraceFix resets its parent
  before best-effort close/export, so a close failure cannot make the next case a child of the
  previous case.
- One tracer is created by the live benchmark application factory and injected into provider,
  benchmark, case, graph, and planning boundaries. No Groq client wrapper or automatic LLM
  instrumentation is used.
- The fixed project is `tracefix-live-diagnostics`.
- The direct SDK requirement is bounded to `langsmith>=0.14,<0.15`, compatible with the existing
  LangGraph 1.2 dependency graph; LangGraph and unrelated packages are not upgraded.

## Trace hierarchy

Only reached stages create spans:

```text
tracefix.live_benchmark
  case.<safe_case_id>
    prepare_repository
    run_baseline
    classify_failure
    build_context
    plan_repair
      provider_request
      parse_repair_plan
      validate_repair_plan
    generate_patch
      provider_request
      parse_patch_proposal
      validate_patch_proposal
      validate_patch_envelope
    patch_policy
    static_checks
    verification
    evaluation
```

Graph routing is unchanged and is not duplicated for tracing. A failed stage records a safe
classification on the reached span, and normal graph routing prevents later spans from existing.
No automatic LangGraph graph or node spans are created around this hierarchy.


Values are restricted to bounded strings, finite floats, bounded integers, and booleans. Code-like
results are additionally pattern-restricted. Unknown keys and container/object values are rejected
before the SDK boundary.

## Sensitive-content controls

Prompts, repository source, visible/hidden test content, model response content, generated patches,
unified diffs, credentials, environment values, raw exception text, raw Pydantic errors, and host
filesystem paths are never supplied to tracer methods. The allow-list is the primary boundary;
SDK input/output hiding is defense in depth. SDK trace contexts suppress exception serialization,
so exception strings cannot be exported. Groq instrumentation records only sanitized completion
category, usage, latency, and response byte count.

Pydantic failures call `errors(include_input=False, include_context=False, include_url=False)` and
retain only the first schema-controlled field location and normalized error type. Numeric list
indices are bounded. Unknown or model-controlled location components become `$.unknown`; `input`,
`ctx`, complete error dictionaries, and `ValidationError` strings are never serialized.

Planning and patch generation each call the existing Pydantic `model_validate_json` operation
exactly once. The parse span classifies the safe Pydantic `json_invalid` error type, and the schema
span observes the saved result or sanitized validation failure. Observability never performs a
second JSON parse or validation pass, so deeply nested, malformed, valid, and schema-invalid model
responses have identical repair semantics with diagnostics enabled or disabled.

## Configuration and failure policy

Tracing is disabled unless the TraceFix-owned switch is exactly true. Enabled diagnostic runs
require:

```text
TRACEFIX_LANGSMITH_DIAGNOSTICS=true
LANGSMITH_TRACING=false
LANGSMITH_API_KEY=<secret>
LANGSMITH_PROJECT=tracefix-live-diagnostics
LANGSMITH_HIDE_INPUTS=true
LANGSMITH_HIDE_OUTPUTS=true
```

The legacy `LANGCHAIN_TRACING`, `LANGCHAIN_HANDLER`, `LANGCHAIN_TRACING_V2`, and
`LANGSMITH_TRACING_V2` switches must likewise be absent or false. Endpoint, transport-mode, legacy
OTEL-mode, and OTLP destination override variables listed above must be absent. These checks occur
before client construction and provider initialization.

Missing or invalid enabled configuration fails during application construction, before provider
initialization and before any paid request. Once execution begins, observability is best effort:
span creation, metadata update, buffering, or export failures are suppressed and must not change
repair semantics, benchmark classifications, reports, pacing, accounting, or exit codes. This
keeps diagnostic availability from becoming a correctness dependency. Failure handlers never log
SDK exception text. Explicit TraceFix-owned parent tracking is reset before close/export, so these
best-effort failures cannot leave a stale parent for later spans or benchmark cases.

The manual workflow scopes `GROQ_API_KEY` and `LANGSMITH_API_KEY` only to the paid live benchmark
step. Tracing variables are absent from deterministic validation, so ordinary validation makes no
LangSmith request.

## Preserved behavior

This task does not change prompts, `repair-v1.0`, Groq payloads or SDK retry behavior, response or
Pydantic schemas, model settings, 61-second pacing, case order, attempt count, fail-fast behavior,
benchmark/report schemas, classifications, accounting, graph routes, sandboxing, patch policy,
static checks, verification, evaluation, or fake-provider behavior. In particular, the suspected
`PatchProposal.confidence` schema/runtime mismatch is intentionally unchanged.

## Deterministic acceptance

Tests use injected recording/no-op tracers, a fake run exporter, and fake providers. They prove
default-disabled behavior, configuration preflight and endpoint pinning, automatic tracer
suppression, the real compiled-graph hierarchy and short-circuiting, metadata allow-list
enforcement, separate source/visible-test/hidden-test/prompt/model/patch/diff/credential/validation
sentinel exclusion, sanitized validation metadata, distinct JSON/RepairPlan/PatchProposal/envelope/
path/diff failures, distinct policy/static/verification/evaluation stages, traced/untraced deeply
nested JSON parity, stale-parent resistance after start/close failures, unchanged outputs and report
schema, no real pacing sleep, and no Groq or LangSmith network call.

A production-boundary regression additionally runs a compiled graph through the real
`LangSmithRunExporter`, real SDK `RunTree`, and real SDK `Client` transformation. A test-only HTTP
session intercepts the final send before any socket operation. It asserts REST-only mode, the fixed
endpoint, no OTEL exporter, absent runtime data, empty inputs/outputs/events/tags/errors, allow-listed
metadata only, and exclusion of separate source, visible-test, consumed hidden-test, rendered-prompt,
provider-response, patch, diff, credential/environment, and validation-input sentinels. A bounded
eight-scenario benchmark/CLI matrix compares tracing off and on for malformed, deeply nested,
schema-invalid, and valid RepairPlan/PatchProposal responses, including terminal diagnostics, repair
status, classifications, attempted/not-run behavior, reports, fail-fast behavior, and exit codes.

The subsequent separately authorized traced live benchmark should prove which of provider finish,
JSON parse, PatchProposal schema validation (including the safe field/type), patch-envelope, path,
or unified-diff boundaries caused each accepted `malformed_model_output` result. It must also prove
all five cases remain infrastructure-complete under tracing. It must not be described as diagnosed
until those traces exist.
