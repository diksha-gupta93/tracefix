# Task 0.1.10b — Deterministic Fake-Model CI Integration

## 1. Goal

Implement the v0.1 deterministic fake model provider and connect it to the existing production
composition for `tracefix repair <case_id>`. The provider must return predetermined, strictly typed
repair plans and patch proposals for each of the five development fixtures, keyed by `case_id`,
`prompt_version`, and `attempt_number`.

Exercise every fixture through the installed CLI and the real eleven-node platform pipeline in
ordinary GitHub Actions CI. Each case must validate repository preparation, baseline reproduction,
classification, context selection, fake-model planning and generation, patch policy, static checks,
sandbox verification, candidate evaluation, artifact publication, CLI summary, and exit status
without model credentials or a live-model network request.

This task proves deterministic platform correctness. It does not measure model repair capability.

## 2. Context

Tasks 0.1.1 through 0.1.10a already provide:

- five versioned development fixtures and trusted/model-safe benchmark loaders;
- a typed `ModelProvider` protocol and strict `ModelProviderRequest`/`ModelProviderResponse`
  envelopes;
- deterministic `repair-v1.0` prompts, strict `RepairPlan` and `PatchProposal` parsing, and the
  single-attempt planning/generation boundary;
- patch policy, static validation, hardened sandbox execution, visible and hidden verification,
  and deterministic candidate evaluation;
- a synchronous eleven-node LangGraph with seven terminal outcomes;
- `tracefix repair <case_id>`, an injectable `ProviderRegistry`, graph-owned workspace cleanup, and
  safe metadata-only JSON artifacts; and
- one ordinary `ubuntu-latest` CI job that installs the development environment, builds both fixed
  Docker images, and runs `python scripts/check.py`.

Task 0.1.10a intentionally leaves the default provider registry empty. A known case therefore
currently ends as `infrastructure_failure` even when fake-shaped model configuration is supplied.
This task adds the first concrete production provider implementation and registers only that local
deterministic provider. Live-provider adapters remain deferred to Task 0.1.11a.

The current `ModelProviderRequest` contains operation, model settings, prompt version, attempt
number, and rendered prompt, but no explicit case identity. The execution plan requires fake
responses to be selected by case identity. This task must add a validated `case_id` field to the
typed request and populate it from the already validated `ContextPackage`; the fake provider must
not discover identity by parsing untrusted prompt text.

The fake response catalog is trusted project-owned deterministic test data. It may contain patches
that produce the same code changes as the benchmark reference patches, but it must be defined
independently and must never read `evaluator/reference.patch`, hidden-test content, or other
evaluator-only files at runtime. Hidden tests remain accessible only to the existing trusted
verification boundary.

## 3. In Scope

- Extend `ModelProviderRequest` with a strict validated `case_id` field using the existing case-ID
  syntax and maximum length. Planning and generation must populate it from the validated
  `ContextPackage.case_id`.
- Preserve every existing model-request field and behavior. Adding case identity must not change
  prompt contents, structured-output parsing, response-size limits, diagnostics, or the one-attempt
  contract.
- Add a concrete deterministic fake provider implementing the existing `ModelProvider` protocol.
  It must:
  - accept only a strict base `ModelProviderRequest`, not subclasses or mutated/partially valid
    objects;
  - select one immutable response bundle by the exact tuple `(case_id, prompt_version,
    attempt_number)`;
  - select the plan or patch JSON within that bundle from the typed `ModelOperation`;
  - return a new strict `ModelProviderResponse` containing exactly the predetermined JSON;
  - return byte-for-byte identical `raw_json` for identical valid requests;
  - fail closed for an unknown case, unsupported prompt version, unsupported attempt, unknown
    operation, or malformed catalog entry; and
  - perform no filesystem, environment, subprocess, Docker, credential, or network access.
- Add one immutable response bundle for each existing development fixture:
  - `incorrect_conditional`;
  - `boundary_condition`;
  - `incorrect_return_value`;
  - `exception_handling`; and
  - `fixture_or_mocking`.
- For each bundle, provide a complete canonical `RepairPlan` and `PatchProposal`. The plan,
  proposal, and unified diff must agree exactly on normalized changed paths, satisfy the existing
  strict schemas and patch-envelope rules, pass the fixed patch policy and static checks, and repair
  both the visible and hidden tests.
- Keep fake responses explicit, reviewable, and small. They must not be synthesized from fixture
  source, manifest expected files, reference patches, test output, or hidden tests at runtime.
- Add a typed fake-provider factory compatible with the existing `ProviderRegistry`. Register it in
  `default_application_factory()` under exactly one stable provider identifier.
- Use this exact deterministic configuration profile for production-composition tests and
  documentation:

  ```text
  MODEL_PROVIDER=tracefix-fake
  MODEL_NAME=tracefix-deterministic-v1
  MODEL_TEMPERATURE=0
  MODEL_MAX_TOKENS=4096
  PROMPT_VERSION=repair-v1.0
  ```

- The fake-provider factory must reject a configuration whose provider, model name, temperature,
  token limit, or prompt version differs from the supported profile. Rejection must flow through
  the existing safe provider-resolution/infrastructure-failure behavior without exposing input or
  exception text.
- Preserve dependency injection. Unit tests may construct the fake provider directly, and
  application tests may inject another registry, but business logic must continue to depend only
  on the `ModelProvider` protocol.
- Run each of the five fixture cases through the installed `tracefix repair <case_id>` entry point
  using the real default application composition, real LangGraph, real filesystem boundaries, both
  real fixed Docker images, and the real artifact writer. Do not replace any platform node with a
  stub in these all-fixture tests.
- For every all-fixture run, assert:
  - process exit code `0`;
  - exactly one safe stdout summary and no traceback or unexpected stderr;
  - outcome `success` and attempt number `1`;
  - exactly one artifact at the reported relative `.tracefix/artifacts/` path;
  - strict artifact schema round trip;
  - the expected case, fake-provider/model/prompt identity, baseline, policy, static, verification,
    evaluation, and terminal fields;
  - expected changed file and line-count evidence for that case;
  - no raw prompt/response, plan/proposal prose, unified diff, source/test content, hidden-test
    identity/content, reference-patch content/path, credential, environment value, exception text,
    or absolute host/container/workspace path; and
  - owned workspace and container cleanup after completion.
- Define deterministic stability as:
  - identical fake requests produce byte-identical fake responses;
  - each fixture always produces the same route, exit code, changed-file evidence, patch-size
    evidence, stage outcomes, and provider/model/prompt identity; and
  - volatile run IDs, timestamps, measured durations, temporary paths, and artifact filenames are
    validated for shape and consistency but are not required to be byte-identical across runs.
- Ensure the all-fixture tests are collected by the existing `python scripts/check.py` invocation,
  so they run on every push and pull request in ordinary CI after both Docker images are built.
- Add the focused unit and integration tests described in Sections 12 and 13.

  workspace ownership, or CLI arguments;
- new patch-policy rules, static tools, sandbox commands, images, resource limits, mounts, seccomp,
  container permissions, verification stages, or evaluator behavior;
- persistence, checkpoints, API ingress, PostgreSQL, Redis, workers, queues, GitHub integration,

- a platform matrix, alternate Python runtime, new Docker image, new application dependency,
  secrets, service containers, CI artifact upload, or CI write permission;
- byte-for-byte comparison of complete run artifacts containing inherently variable run identity,
  timestamps, or measured execution durations;

## 6. Python and Packaging Requirements

- Continue to require CPython `>=3.14,<3.15` and use the existing `.venv`. Do not install another
  Python runtime or create an alternate runtime directory.
- Continue to use Pydantic v2 for cross-module request/response and any new structured fake-provider
  contracts. New immutable configuration, key, or response-bundle models must be strict,
  extra-forbidding, and frozen.
- Reuse `ModelProvider`, `ModelProviderRequest`, `ModelProviderResponse`, `ModelOperation`,
  `RepairPlan`, and `PatchProposal`. Do not introduce competing model-boundary or repair schemas.
- Add `case_id` to the existing request rather than passing an implicit tuple/dictionary, parsing
  the rendered prompt, or creating fake-provider-only request arguments.
- Fully type all public and cross-module interfaces. Do not use `Any`, unparameterized collections,
  ignored type errors, dynamic imports, or untyped JSON dictionaries across module boundaries.
- The response catalog must be immutable after module initialization. Validate catalog entries
  eagerly or through a deterministic typed construction path so malformed project-owned data fails
  before it can be returned as a successful provider response.
- Use standard-library serialization through the established Pydantic boundary. Do not add a JSON,
  fixture-generation, provider, HTTP, mocking, or snapshot dependency.
- Do not add or change runtime/development dependencies or package discovery. The fake provider
  belongs under the already packaged `app` namespace; benchmarks remain un-packaged fixture data.
- Preserve the installed `tracefix = "app.cli:main"` entry point, editable installation, and
  `python -m pip check` success.

## 8. Cross-Platform Requirements

- Predetermined unified diffs and JSON responses must use LF and normalized relative POSIX paths.
  Existing parsing may normalize incoming CRLF, but catalog output itself must be canonical.
- Resolve the installed CLI executable portably in tests: `.venv\Scripts\tracefix.exe` on Windows
  and `.venv/bin/tracefix` on POSIX, or an equivalent verified console-script resolution that does

- The all-fixture pipeline continues to require a usable Linux-container Docker daemon and both
  fixed images. Docker Desktop with Linux containers remains supported for Windows development.
- Preserve the documented platform boundary: Linux is production-supported for adversarial host
  filesystem preparation; native Windows is development-supported and does not gain a new claim of
  complete host-side TOCTOU protection.
- Windows validation commands use `.venv\Scripts\python.exe`; POSIX commands use
  `.venv/bin/python`. The activated cross-platform command remains `python scripts/check.py`.

## 10. Security Considerations

- The fake provider is an external-system adapter substitute and must remain behind the existing
  typed `ModelProvider` interface. Business logic must not special-case fake responses.
- Treat the rendered prompt, context, repository content, model request objects, and catalog JSON
  as untrusted at their existing boundaries. The fake provider must key from the explicit validated
  request metadata and must not parse prompt text to recover `case_id` or execute embedded
  instructions.
- The provider must have no filesystem, benchmark-loader, Docker, subprocess, environment,
  credential, network, or tool capability. Importing or invoking it must cause no I/O.
- The response catalog must not read, import, generate from, or refer to evaluator-only paths,
  hidden tests, or reference patches at runtime. Tests must prove provider operation still works
  when benchmark evaluator paths are inaccessible or instrumented to fail if read.
- Predetermined response data is not a source of policy authority. Every fake patch must traverse
  the same strict parsing, patch-policy, static-validation, sandbox-verification, and evaluation
  boundaries as a live provider response.
- Preserve hidden-test isolation. Hidden tests may be loaded only by the existing trusted
  verification service into its private read-only bundle and must never enter model requests,
  provider responses, artifacts, summaries, or diagnostics.
- Preserve all sandbox controls: non-root user, disabled network, read-only root filesystem,
  explicit writable temporary mounts, CPU/memory/PID/time/output limits, dropped capabilities,
  `no-new-privileges`, default seccomp, fixed commands/environment, validated mounts, and automatic
  cleanup. Never mount the Docker socket, project/benchmark/evaluator roots, developer home, or
  credentials into execution containers.
- Do not add secrets or fake secret-shaped values to configuration, responses, logs, artifacts, or
  workflow files. Existing configuration loading must continue to ignore unrelated environment
  values.
- Provider/configuration/catalog failures must expose only existing safe constant diagnostics.
  Never include request prompts, raw response/catalog JSON, diffs, exception text, environment
  values, or paths in diagnostics, console output, or artifacts.
- The default registry must contain only the explicitly approved deterministic local provider. It
  must not dynamically import providers, use entry-point discovery, fall back to a live provider,
  or select a provider from model-controlled data.
- Existing artifact allowlisting, atomic publication, workspace identity validation, and cleanup
  rules remain unchanged. Successful fake-model execution does not authorize broader artifact
  disclosure.

## 11. Failure Cases

The implementation must fail closed for at least:

- missing, blank, malformed, extra, overlong, wrong-type, mutated, or subclassed request data,
  including `case_id`;
- planning/generation case mismatch between `ContextPackage` and `ModelProviderRequest`;
- unknown catalog case, unsupported prompt version, attempt other than `1`, unsupported operation,
  duplicate/case-fold-colliding key, missing operation response, malformed plan/proposal JSON, or
  invalid project-owned response bundle;
- fake configuration with the wrong provider, model name, temperature, token limit, or prompt
  version;
- fake-provider factory or registry construction failure, missing registration, provider exception,
  wrong response envelope, or response mutation;
- plan/proposal/diff file disagreement, malformed unified diff, unsafe path, policy violation,
  static failure, visible or hidden regression, or evaluation mismatch in any fixture;
- any attempt by provider code to read manifests, fixture repositories, hidden tests, evaluator
  directories, reference patches, environment secrets, host paths, or network resources;
- installed CLI not found, non-zero or inconsistent exit status, traceback, extra/unexpected output,
  missing/duplicate/invalid artifact, unsafe artifact disclosure, or artifact path outside the
  isolated invocation directory;
- workspace, hidden-bundle, temporary-artifact, or container cleanup failure;
- Docker CLI/daemon/image/seccomp failure, sandbox timeout/OOM/protocol/integrity failure, or
  unexpected network availability inside untrusted execution;
- nondeterministic fake response bytes or changing normalized deterministic artifact evidence for
  identical case/configuration inputs; and
- regression in any existing format, lint, type, unit, integration, security, package, entry-point,
  or diff check.

An unknown fake lookup or invalid supported-profile configuration is an infrastructure failure,
not a model-repair result. A fake response that is well formed but fails policy, static checks, or
verification follows the existing terminal routing contract; tests for the five approved catalog
entries require success and may not weaken those gates.

## 12. Acceptance Criteria

1. `ModelProviderRequest` has a strict case identity populated from the validated active context in
   both planning and generation, with existing request behavior preserved.
2. One concrete local fake provider implements `ModelProvider` without filesystem, environment,
   subprocess, Docker, credential, SDK, or network access.
3. The provider selects immutable response bundles by exact `(case_id, prompt_version,
   attempt_number)` and selects plan versus patch by `ModelOperation`; unknown or malformed inputs
   fail closed.
4. The five catalog entries are complete, deterministic, directly reviewable, and independent of
   runtime access to benchmark repositories, manifests, hidden tests, evaluator directories, and
   reference patches.
5. Every predetermined plan and proposal passes existing strict schema/diff validation with exact
   plan/proposal/diff changed-path agreement and attempt `1`.
6. `default_application_factory()` registers exactly the `tracefix-fake` factory while preserving
   registry injection and safe behavior for unavailable providers. No live provider or dynamic
   discovery exists.
7. Only the exact documented fake configuration profile resolves. Unsupported fake configuration
   produces safe `infrastructure_failure` behavior and no external call.
8. Each of the five fixtures runs through the installed CLI and every real platform node, returns
   exit `0`, routes to `success`, and repairs the targeted, full visible, and hidden tests using the
   existing sandbox controls.
9. Each run writes exactly one valid safe artifact with the expected case, provider/model/prompt,
   attempt, baseline, policy, static, verification, evaluation, changed-file, patch-size, route, and
   exit-code evidence, plus one matching concise stdout summary.
10. All-five-fixture tests use no injected node/service stubs and prove that generated candidates,
    evaluator bundles, workspaces, containers, and temporary artifact files are cleaned according
    to existing ownership rules.
11. Fake provider responses are byte-stable for identical requests. Route, exit code, changed-file
    and line-count evidence, stage outcomes, and provider/model/prompt identity are stable for each
    fixture; volatile runtime metadata is only shape/consistency validated.
12. Tests demonstrate that hidden/evaluator/reference data cannot enter fake-provider requests,
    responses, artifacts, summaries, or diagnostics, and that the provider does not read those
    assets to produce its response.
13. The ordinary push/pull-request CI job builds both fixed images and collects the all-five-fixture
    integration test through `python scripts/check.py`; any pipeline failure blocks CI.
14. CI and local fake runs require no model credential, provider account, provider SDK, live-model
    endpoint, external model network, database, queue, GitHub write permission, or service
    container.
15. Existing unit, integration, sandbox, security, benchmark-isolation, graph, CLI, and artifact
    tests remain unchanged in intent and pass under Python 3.14.
16. Formatting, linting, strict typing, dependency integrity, focused tests, applicable Docker
    integration tests, the full suite, canonical validation, installed CLI smoke, and diff checks
    pass.
17. README and progress documentation are updated during implementation. Governing documents,
    prior specifications, benchmark/evaluator assets, Docker images, and the approved active
    specification remain unchanged.
18. No live-model benchmark behavior, report aggregation, future-version component, unrelated
    abstraction/dependency, test weakening, commit, or push is introduced.

  abstraction and returns predetermined plans and patches for exactly the five v0.1 fixtures by

  safe injectable behavior for tests and unavailable providers.

  repairs targeted, visible, and hidden behavior through the real sandboxed platform pipeline.
- All five fixture cases pass through the installed CLI in ordinary CI with success artifacts,
  expected deterministic evidence, no provider credentials, and no live-model network dependency.
- Existing sandbox, hidden-test, artifact-disclosure, workspace/container cleanup, protected-path,
  and fail-closed diagnostic controls remain intact.
- Section 13 gates pass in the existing Python 3.14 environment, including both image builds, the
