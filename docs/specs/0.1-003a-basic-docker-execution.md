# Task 0.1.3a — Basic Docker Execution

## 1. Goal

Add the smallest typed Docker execution boundary needed to run a strictly validated pytest command
against a prepared Python repository in a fresh Linux container. The runner must execute as a
non-root user with networking disabled and a read-only root filesystem, provide an isolated
writable workspace, return a structured result, and remove the container after both successful and
failed test runs.

This task establishes basic execution and cleanup only. Resource enforcement and the complete
adversarial hardening suite remain separate tasks in the execution plan.

## 2. Context

Task 0.1.2 created five deterministic fixture repository snapshots and a typed loader, but correctly
prohibited executing fixture code on the host. Task 0.1.3a introduces the first authorized execution
path for those prepared snapshots. Later workflow stages will call this boundary for baseline and
candidate verification.

The system architecture treats Docker as an external system and requires access through a typed
adapter. It also requires untrusted repository code to remain inside Docker. The sandbox controls
are introduced incrementally: this task implements only the controls explicitly assigned to
Task 0.1.3a, while Tasks 0.1.3b and 0.1.3c add resource/output enforcement and the remaining
hardening and adversarial validation.

The current host is Windows-compatible and CI runs on Linux. The execution container is Linux in
both environments. Docker Desktop or another Linux-container Docker daemon is therefore an
external prerequisite, not a Python runtime dependency.

## 3. In Scope

- Add `app/sandbox/results.py` with a typed structured result for a completed pytest execution.
- Add `app/sandbox/runner.py` with:
  - an immutable typed pytest-command value;
  - strict command validation before any Docker operation;
  - a typed Docker command adapter injected into the sandbox runner;
  - validation of a prepared repository directory;
  - creation and startup of one fresh, uniquely named Linux container per execution;
  - non-root container execution;
  - disabled container networking;
  - a read-only container root filesystem;
  - a read-only bind mount containing only the prepared repository;
  - a fresh writable temporary workspace inside the container;
  - execution from the writable copy of the repository;
  - capture of stdout, stderr, exit code, and monotonic duration;
  - unconditional container removal after pass, test failure, and runner failure.
- Add a sandbox Dockerfile containing the Python 3.14 and pytest runtime required by the fixture
  projects.
- Add `.dockerignore` to bound and sanitize the Docker build context.
- Add focused unit tests for validation, command construction, result mapping, and cleanup behavior.
- Add Docker integration tests for passing and failing pytest commands, structured results, and
  container removal.
- Extend ordinary GitHub Actions CI to build the sandbox image and run the Docker integration tests
  through the canonical validation command.

## 4. Out of Scope

- CPU, memory, PID, wall-clock, stdout, or stderr limits; truncation; timeout classification; and
  resource-failure classification. These belong to Task 0.1.3b.
- Capability dropping, `no-new-privileges`, explicit seccomp selection, adversarial escape tests,
  credential and home-path probes, Docker-socket probes from inside the container, and the complete
  validated-mount-source policy. These belong to Task 0.1.3c.
- Patch validation, protected-path policy, patch application, static checks, hidden-test staging,
  or evaluator asset handling.
- Repository preparation, Git checkout/materialization, fixture selection, or copying benchmark
  evaluator directories into a workspace.
- Arbitrary commands, shell expressions, user-selected executables, dependency installation, or
  package-manager commands.
- LangGraph, model providers, prompts, repair logic, CLI commands, or evaluation artifacts.
- FastAPI, PostgreSQL, Redis, queues, checkpoints, GitHub integration, tracing, or metrics.
- Docker Compose, Kubernetes, image publication, registry authentication, or production image
  release automation.
- Automatic recovery from Docker daemon interruption or runner-process termination.
- Changes to the fixture corpus, benchmark loader, core Pydantic schemas, or application state.

`app/sandbox/__init__.py` may expose the intentional public sandbox types but must contain no
execution behavior. No additional sandbox policy or limits module is part of this task.

The image tag used by tests must be a project-owned constant such as `tracefix-sandbox:0.1.3a`, not
an image name accepted from untrusted input. Container names must use a fixed TraceFix prefix and a
random collision-resistant suffix so integration tests can verify cleanup without matching
unrelated containers.

## 6. Python and Packaging Requirements

- Continue to require CPython `>=3.14,<3.15` for the TraceFix host application.
- Use the existing Pydantic v2 dependency for structured public data where validation is needed.
- Do not add the Docker Python SDK or another runtime/development dependency. Invoke the installed
  Docker CLI through a small injected, typed adapter using argument sequences with `shell=False`.
- Every public and internal Python boundary must be fully typed. Do not use `Any`, unparameterized
  collections, implicit dictionaries across module boundaries, new type suppressions, or raw
  `subprocess.CompletedProcess` objects as public results.
- `SandboxResult` must contain exactly:
  - `exit_code: int`;
  - `stdout: str`;
  - `stderr: str`;
  - `duration_seconds: float`.
- `SandboxResult` must reject unknown fields, booleans as integers, negative or non-finite duration,
  and malformed types. A nonzero exit code represents a completed failing pytest run and is returned
  normally; it is not a runner exception.
- Represent an approved command as an immutable typed value, not as a free-form string. The only
  accepted token grammar is:

  ```text
  python -m pytest [<repository-relative-test-path> ...]
  ```

  The first three tokens must match exactly. Zero test paths means normal pytest discovery. Every
  additional token must be a nonempty POSIX-style relative path beneath `tests/`, must end in `.py`
  or select a node within a `.py` file with `::`, and must contain no absolute/drive/UNC form, `.` or
  `..` component, backslash, control character, option prefix, glob, URI, shell metacharacter, or
  whitespace. Pytest flags, environment assignments, response files, plugin loading, and arbitrary
  positional paths are rejected in this task.
- Container execution must use the Dockerfile's fixed Python entry environment and must not install
  dependencies at run time. Fixture repositories currently require only Python and pytest.
- Keep setuptools package discovery and existing dependency version constraints unchanged.

## 7. Development Tool Requirements

- Existing Ruff formatting/linting, strict mypy, pytest, and `scripts/check.py` remain authoritative.
- Add a registered `integration` pytest marker if the Docker tests use one; do not weaken strict
  marker validation or exclude the tests from the normal pytest collection.
- Unit tests must inject a fake Docker command adapter and must not require a Docker daemon.
- Integration tests must use the project-owned prebuilt image and the real Docker CLI/daemon. They
  must not build images implicitly, pull images, access a registry, or install dependencies.
- A Docker integration test may skip only when a developer machine has no usable Docker CLI or
  Linux-container daemon. It must not skip merely because the expected project image is absent; the
  failure must instruct the developer to run the documented image-build command.
- CI must explicitly build the image before `python scripts/check.py`; consequently, Docker
  integration tests must execute rather than skip in CI.
- Tests must use temporary prepared repositories created by pytest or a copied repository-only
  benchmark snapshot. They must never run fixture code on the host.
- Do not add lint, typing, test, or coverage exclusions and do not weaken existing tests.

## 8. Cross-Platform Requirements

- Host-side runner behavior must work on Windows and Linux without shell syntax.
- Use `pathlib.Path`, argument lists, `subprocess` with `shell=False`, monotonic timing, and UTF-8
  decoding with deterministic replacement for undecodable subprocess output.
- Do not construct Docker commands by quoting or concatenating a command string.
- Resolve the prepared repository path before Docker invocation. It must be an existing directory,
  must not itself be a symlink, and its resolved form must remain stable during initial validation.
  Full trusted-root and sensitive-host-path policy is deferred to Task 0.1.3c; callers are responsible
  for passing a repository-only prepared workspace in this task.
- Express the container mount target and pytest paths with POSIX paths. Pass the host bind source to
  Docker as one structured mount argument so spaces in Windows paths do not alter tokenization.
- Do not rely on POSIX host shell tools, Windows shell built-ins, executable permission bits, host
  path separators, or host newline conventions.
- The Dockerfile must produce a Linux image, use LF line endings, set a non-root numeric user, and
  avoid architecture-specific binaries.
- Cleanup assertions must work with both Docker Desktop and native Linux Docker.

## 9. GitHub Actions CI Requirements

- Preserve the existing `ubuntu-latest`, Python 3.14, pinned-action, and `contents: read` posture.
- Add a build step before validation equivalent to:

  ```text
  docker build --tag tracefix-sandbox:0.1.3a --file docker/sandbox/Dockerfile .
  ```

- Continue to install the project with `python -m pip install --editable ".[dev]"` and run the
  canonical `python scripts/check.py` command.
- The validation step must collect and execute the Docker integration tests against the locally
  built image. CI must fail if Docker is unavailable, the image cannot be built, a passing/failing
  result is wrong, or a test container remains after execution.
- CI must not use secrets, elevated service containers, Docker socket mounts into execution
  containers, registry login, image push, model credentials, external services, or live-model calls.
- Docker build inputs must be restricted by `.dockerignore`; the image must not contain `.git`,
  `.venv`, caches, benchmark evaluator assets, tests, documentation, local environment files, or
  credentials.
- Do not add a matrix, separate workflow, privileged job, or unpinned third-party action.

## 10. Security Considerations

- Treat the prepared repository and every requested test path as untrusted. Validation must finish
  before the Docker adapter is called.
- Never execute repository code, pytest, Docker image hooks, or fixture modules directly on the
  host.
- Never use `shell=True` and never invoke `bash`, `sh`, PowerShell, `cmd.exe`, or a command supplied
  by a manifest, model, environment variable, or repository file.
- Use only the fixed project-owned sandbox image. Do not accept an image, entrypoint, Docker flag,
  environment mapping, mount target, user, or working directory from untrusted input.
- Bind only the prepared repository directory, read-only, at a fixed input location. Do not mount
  the project root, developer home, `.git`, credentials, Docker configuration, model/GitHub secrets,
  or the Docker socket.
- Copy the repository from the read-only input mount into a fresh writable container workspace
  before pytest runs. The untrusted process must not gain write access to the host bind mount.
- Run the container with `--network none`, `--read-only`, and a fixed non-root numeric UID/GID.
  Provide writable storage only at the fixed workspace location and any minimal runtime temporary
  location required by Python/pytest.
- Do not forward the host environment into the container. Provide only fixed non-secret values
  required for deterministic Python/pytest execution.
- Use a unique container name and remove that exact container in a `finally` path. Cleanup must use
  noninteractive forced removal and must never target a name not generated by the current run.
- A cleanup failure is an infrastructure error and must not be hidden by a pytest result. Preserve
  exception chaining and report the exact generated container name without including repository
  contents or host secrets.
- This task's controls are not the final hardened sandbox. The implementation and documentation
  must not claim resource isolation, output bounding, capability dropping, `no-new-privileges`, or
  explicit seccomp enforcement until their assigned tasks are complete.

## 11. Failure Cases

The runner must fail closed with typed/domain exceptions, without returning a partial result, for:

- an empty, relative, missing, non-directory, symlinked, or unstable prepared repository path;
- a command with the wrong executable/module prefix;
- a shell executable, shell option, environment assignment, pytest option, response file, URI,
  absolute/drive/UNC path, backslash, traversal component, glob, control character, whitespace, or
  shell metacharacter;
- failure to locate or invoke the Docker CLI;
- Docker daemon unavailability or rejection;
- missing or unusable sandbox image;
- container creation, start, wait, output-capture, or inspection failure;
- an output payload that cannot be mapped into the typed result contract;
- inability to remove the generated container after success or failure.

A pytest exit code other than zero is not an infrastructure failure. It must produce a normal
`SandboxResult` with captured output. Empty stdout or stderr is valid. Cleanup must still be
attempted when any earlier Docker operation fails after a container may have been created.

If both execution and cleanup fail, the raised error must retain both facts through exception
chaining or an explicitly typed combined error; cleanup failure must not silently replace or erase
the original failure.

## 12. Acceptance Criteria

1. `app.sandbox.results` provides the strict typed result contract in Section 6.
2. `app.sandbox.runner` accepts only the exact pytest grammar in Section 6 and rejects arbitrary
   shell execution before any Docker operation.
3. The Docker CLI is isolated behind an injected typed adapter; business logic neither uses
   `shell=True` nor passes raw command strings.
4. Each call uses a fresh uniquely named Linux container based on the fixed project image.
5. The container runs as non-root with networking disabled and a read-only root filesystem.
6. Only the prepared repository is bind-mounted from the host, read-only; pytest runs from a fresh
   writable container-local copy.
7. Passing pytest returns exit code `0` and captured structured stdout, stderr, and duration.
8. Failing pytest returns a nonzero exit code and captured structured stdout, stderr, and duration
   without being misclassified as a runner exception.
9. The exact generated container is removed after pass, test failure, and Docker-operation failure;
   integration tests find no matching leftover container.
10. Unit tests prove invalid commands cause no Docker adapter calls and prove cleanup is attempted
    on every post-creation path.
11. The sandbox image is built explicitly and Docker integration tests execute in ordinary GitHub
    Actions CI without secrets or external services.
12. `.dockerignore` prevents irrelevant, sensitive, evaluator-only, and local-development content
    from entering the image build context.
13. No Task 0.1.3b resource/output behavior, Task 0.1.3c hardening behavior, or adjacent workflow
    behavior is introduced or claimed.
14. Formatting, linting, strict typing, unit tests, applicable Docker integration tests, and review
    checks pass using the existing Python 3.14 environment.

## 13. Tests and Validation Commands

Add unit tests covering at minimum:

- valid zero-path and one-or-more-path pytest commands;
- every prohibited command/path class listed in Section 11;
- validation before Docker adapter interaction;
- prepared repository existence, type, absolute-path, and symlink validation;
- unique container naming and fixed image/flags/mount targets;
- structured mapping of passing and failing results;
- monotonic non-negative duration;
- cleanup after pass, pytest failure, malformed Docker response, and raised Docker error;
- preservation of both execution and cleanup failure evidence;
- strict `SandboxResult` validation.

Add Docker integration tests covering at minimum:

- a minimal passing pytest repository;
- a minimal failing pytest repository;
- captured stdout, stderr, exit code, and non-negative duration;
- non-root execution, disabled networking, read-only root filesystem, and writable workspace as
  observable through fixed test fixtures that do not weaken the container configuration;
- container removal after passing and failing pytest runs;
- invalid command rejection without container creation.

Run from the repository root with the existing Python 3.14 virtual environment:

```text
.venv\Scripts\python.exe --version
docker version
docker build --tag tracefix-sandbox:0.1.3a --file docker/sandbox/Dockerfile .
.venv\Scripts\python.exe -m pytest tests/unit/test_sandbox_results.py tests/unit/test_sandbox_runner.py
.venv\Scripts\python.exe -m pytest tests/integration/test_sandbox_runner.py
.venv\Scripts\python.exe -m ruff format --check .
.venv\Scripts\python.exe -m ruff check .
.venv\Scripts\python.exe -m mypy app benchmarks scripts
.venv\Scripts\python.exe -m pytest
.venv\Scripts\python.exe scripts/check.py
git diff --check
git status --short
```

POSIX uses `.venv/bin/python` for the same Python commands. The canonical cross-platform quality
gate remains:

```text
python scripts/check.py
```

The Docker image build is an explicit prerequisite because `scripts/check.py` must not perform
builds, downloads, or other environment mutation. A local Docker skip is reported as remaining
validation risk; CI is required to execute, not skip, the integration suite.
