# Task 0.1.8 — Static Checks

## 1. Goal

Add a deterministic, typed, blocking static-validation gate that takes a policy-approved inert
`PatchProposal`, applies it exactly once to a fresh copy of the prepared failing snapshot, verifies
the actual changed-file set, and runs the v0.1 Python static checks before any candidate test
execution.

The gate must run Python compilation, AST parsing, Ruff, applicable mypy analysis, and Bandit in a
purpose-built hardened Linux container. It must return safe structured results for candidate
findings and tool/infrastructure failures. Only a candidate for which every applicable check passes
may be returned for Task 0.1.9 sandbox verification.

## 2. Context

Task 0.1.4 materializes a validated failing repository snapshot in a caller-owned workspace and
records a versioned SHA-256 content fingerprint. Task 0.1.6 produces a structurally validated inert
unified diff whose parsed paths agree with `PatchProposal.files_changed`. Task 0.1.7 evaluates that
proposal as inert data and returns an immutable `PatchPolicyResult`; it deliberately does not apply
the patch, inspect a repository, or run static tools.

This task implements workflow Node 8 only. The execution plan requires patch-apply validation,
changed-file validation, Python compilation, AST parsing, Ruff, mypy where applicable, and Bandit.
Every failure is blocking, and tool errors must become structured failures. Task 0.1.9 will execute
the original targeted test, visible suite, and hidden tests against the validated candidate. Task
0.1.10a will later own graph routing, state transitions, CLI exit codes, and artifacts.

The repository's security rules prohibit host execution of untrusted code. Applying and comparing
bytes is a non-executing host filesystem operation, but candidate compilation and third-party
analysis run only inside a hardened container. Candidate-controlled Ruff, mypy, Bandit, Python,
pytest, or project configuration must never be loaded. The existing pytest-only sandbox contract
and image remain unchanged.

## 3. In Scope

- Add one typed static-validation service accepting:
  - the existing `RepositoryPreparation` for the failing snapshot;
  - the existing `PatchProposal`;
  - an existing `PatchPolicyResult` that is strictly valid and approved;
  - an explicit caller-owned candidate-workspace root;
  - injected typed filesystem/fingerprint and static-container boundaries.
- Add strict, frozen Pydantic v2 contracts for:
  - the fixed check identity and order;
  - per-check status and safe evidence;
  - the overall static-validation outcome;
  - the validated candidate repository identity and fingerprint;
  - safe input, patch-application, tool, infrastructure, and cleanup diagnostics.
- Revalidate all typed inputs at the boundary. Reject an absent, malformed, rejected, or internally
  inconsistent `PatchPolicyResult`; approval remains necessary but is not treated as proof that the
  patch applies or that the candidate is correct.
- Revalidate the prepared repository before use:
  - it is still the exact absolute directory recorded by `RepositoryPreparation`;
  - it contains no link/reparse-point, hard-link, special-file, or case-fold alias;
  - its current fingerprint equals `RepositoryPreparation.fingerprint`;
  - it remains outside the project tree, developer home, credential locations, Docker sockets, and
    other existing protected host locations.
- Materialize a fresh candidate tree below the explicit approved workspace root. Never mutate the
  benchmark fixture or the original prepared failing snapshot. Use a unique non-existing
  destination and a private staging name; publish the candidate path only after all checks pass.
- Apply the proposal with a small deterministic in-process applicator built on the existing typed
  unified-diff parser. The applicator must:
  - support the existing v0.1 text-diff envelope for file modification, file addition, and file
    deletion only;
  - use normalized relative POSIX paths already accepted by Tasks 0.1.6 and 0.1.7;
  - require UTF-8 text for every source file touched by a text hunk;
  - require every hunk coordinate, context line, and removed line to match exactly;
  - apply no offset search, fuzz, whitespace correction, path stripping, rename/copy semantics,
    mode change, binary patch, external filter, or partial patch;
  - preserve an existing file's consistent LF or CRLF convention and final-newline state; use LF
    for a newly added file; reject mixed or ambiguous newline structure;
  - create a new file only when it does not exist and delete a file only when the resulting content
    is empty under the parsed deletion patch;
  - write only within the private candidate staging tree through validated contained paths;
  - leave no partially published candidate when any file or hunk fails.
- The shared diff parser may be minimally extended with immutable typed hunk metadata needed for
  exact application. Existing Task 0.1.6 planning diagnostics and Task 0.1.7 policy behavior must
  remain unchanged.
- Validate the actual changed-file set by comparing the pristine prepared tree with the candidate
  tree by normalized relative path, entry type, and file bytes. The validation must prove:
  - the exact case-insensitive set of added, modified, and deleted files equals both
    `PatchProposal.files_changed` and the parsed diff paths;
  - every path not declared by the proposal has identical existence, type, and bytes;
  - no declared path is a no-op;
  - no link/reparse-point, hard-link, special file, case-fold alias, path escape, or unexpected
    directory entry was introduced;
  - the pristine preparation remained unchanged throughout the operation.
- Run these checks in the fixed order below. Independent applicable checks run to completion so one
  candidate can report multiple findings; a failed prerequisite may mark dependent checks
  `not_run` with a constant safe reason.

  | Order | Check | Required behavior |
  | ---: | --- | --- |
  | 1 | `patch_apply` | Exact all-or-nothing application succeeds in a private candidate staging tree. |
  | 2 | `changed_files` | Actual byte-level tree changes exactly match the proposal and parsed diff, before and after tool execution. |
  | 3 | `python_compile` | Every surviving changed `.py` or `.pyi` file compiles under CPython 3.14 without importing or executing it. |
  | 4 | `ast_parse` | Every surviving changed `.py` or `.pyi` file parses with the Python 3.14 AST parser without importing or executing it. |
  | 5 | `ruff` | Ruff linting passes for the surviving changed Python files under a TraceFix-owned fixed configuration. |
  | 6 | `mypy` | Strict mypy passes for the surviving changed Python files when such files exist. |
  | 7 | `bandit` | Bandit reports no finding for the surviving changed Python files under a TraceFix-owned fixed configuration. |

- A language/tool check is `not_applicable`, not passed or failed, only when the patch leaves no
  surviving changed `.py` or `.pyi` file. `not_applicable` is non-blocking. No other skip, ignore,
  baseline, per-file exemption, or advisory status exists in v0.1.
- Add a purpose-built static-check image and typed Docker adapter. The image/adapter must:
  - expose one fixed entrypoint that always runs the complete static-check set;
  - accept only normalized changed Python paths as data, never arbitrary commands or tool flags;
  - copy the read-only mounted candidate into a disposable tmpfs workspace;
  - run as numeric non-root UID/GID `10001:10001` with network disabled, read-only root filesystem,
    dropped capabilities, `no-new-privileges`, default seccomp, bounded CPU/memory/PIDs/time/output,
    fixed environment, and automatic cleanup;
  - mount no project root, developer home, credentials, Docker socket, model/GitHub secrets, or
    evaluator material;
  - invoke tools with argument sequences and `shell=False` only;
  - ignore all candidate-owned configuration, plugins, excludes, baselines, caches, and environment;
  - emit one bounded, versioned JSON result document and no uncontrolled tool output.
- Ruff must use isolated/fixed TraceFix settings equivalent to the repository's Python 3.14 target
  and selected lint rules. It must not apply fixes or formatting changes.
- Mypy must use strict TraceFix-owned settings, no candidate config, no candidate plugins, no
  incremental cache in the candidate, and no arbitrary executable hooks. Analysis is limited to
  the surviving changed Python paths while permitting ordinary source import discovery inside the
  disposable copied repository.
- Bandit must use its built-in Python checks without candidate configuration, skipped test IDs, or
  a baseline. Any Bandit finding, regardless of severity or confidence, is blocking in v0.1.
- Tool findings may retain only normalized repository-relative path, positive line/column when
  provided, and a bounded tool rule/error code. Messages are TraceFix-owned constants. Raw source
  lines, raw stdout/stderr, exception text, candidate configuration, and absolute host/container
  paths are not part of the cross-module result.
- Distinguish:
  - `passed`: every required applicable check passed and a candidate is returned;
  - `candidate_failed`: at least one deterministic candidate check failed;
  - `infrastructure_diagnostic`: a tool could not run reliably, returned malformed evidence, the
    container failed/timed out/OOMed, or required cleanup/integrity verification failed.
- On any non-passing outcome, block progression and return no candidate path. Clean up the private
  staging/candidate directory. On success, return its absolute path and a versioned fingerprint;
  ownership transfers to the caller for Task 0.1.9 and final workflow cleanup.
- Add focused unit tests for every check, aggregation, malformed evidence, patch application,
  changed-file comparison, cleanup, and result invariants. Add Docker integration tests that run
  real static tooling against clean and intentionally failing synthetic candidates and at least two
  existing fixture-shaped patches.

## 4. Out of Scope

- Running the original failing test, the full visible suite, hidden tests, or any candidate code.
  Those are Task 0.1.9.
- Deciding functional repair success, regressions, changed-line metrics, model latency/tokens/cost,
  or evaluation results. Those are Task 0.1.9.
- LangGraph node construction, graph routing, `LocalRepairCaseState` transitions, CLI behavior,
  exit codes, JSON run artifacts, or workflow-owned workspace cleanup. Those are Task 0.1.10a.
- Re-running or expanding Task 0.1.7 policy rules. In particular, secret detection, dependency
  declaration policy, test/assertion manipulation, protected paths, and patch size limits remain
  the preceding policy gate.
- v0.2 static-gate hardening: general secret-scanner integration, dependency-diff inspection,
  complexity comparison, suspicious generated-file detection, configurable dependency policy, or
  advisory checks.
- Applying binary patches, Git metadata patches, renames, copies, mode changes, submodule changes,
  symlinks, hard links, fuzzy/offset patches, non-UTF-8 text patches, or arbitrary patch formats.
- Running `git apply`, `patch`, shell commands, candidate build hooks, package installation,
  dependency resolution, Ruff fixes, mypy plugins, Bandit baselines, or candidate-defined tooling.
- Adding Git/GitHub operations, real commit checkout, model providers, retries, persistence, queues,
  APIs, observability, or human approval.
- Modifying benchmark manifests, fixture/evaluator content, the existing pytest sandbox command
  policy, or the existing `tracefix-sandbox:0.1.3a` image contract.
- Adding a generic command-execution service. The new container boundary is purpose-built for this
  fixed static-check set only.
- Claiming that static analysis proves functional correctness, security, or test success.

## 6. Python and Packaging Requirements

- Use the existing CPython `>=3.14,<3.15` interpreter and `.venv`; do not install another Python or
  create another environment.
- Use Pydantic v2 for all static-check requests/results/diagnostics crossing module boundaries. New
  models are strict, extra-forbidding, frozen, and validate their own outcome/status invariants.
- Reuse `RepositoryPreparation`, `RepositoryFingerprint`, `PatchProposal`, `PatchPolicyResult`, and
  the shared parsed-diff types. Do not duplicate or silently change their established meaning.
- Do not add static results or a candidate path to `LocalRepairCaseState` in this task; graph/state
  integration is Task 0.1.10a.
- Fully type all public and cross-module interfaces. Do not use `Any`, implicit dictionaries,
  unchecked casts, or stringly typed check/status/tool protocols.
- Use standard-library filesystem, hashing, AST, compilation, JSON, and subprocess primitives where
  appropriate. Host-side patch application must not use a shell, Git, `patch`, `eval`, `exec`,
  dynamic import, candidate import, or candidate subprocess.
- Add `bandit>=1.9,<2` to the existing `dev` extra. Retain the existing Ruff and mypy ranges. The
  static image must use the same bounded Ruff, mypy, and Bandit ranges and Python 3.14.
- Do not add a runtime Python dependency for patch application, diff parsing, Docker access, result
  parsing, or filesystem comparison. Continue to access Docker through an injected typed CLI
  adapter rather than a Docker SDK.
- Keep the existing setuptools package discovery, project version, runtime Pydantic range, and
  canonical quality-tool configuration otherwise unchanged.
- Bound every retained text, JSON document, finding count, path count, and rule code. The outer
  Docker adapter must enforce output limits before JSON parsing. Excess or malformed evidence is an
  infrastructure diagnostic, never a partial pass.

## 8. Cross-Platform Requirements

- Host-side preparation verification, candidate copying, exact patch application, tree comparison,
  result ordering, and fingerprints must behave consistently on supported Windows and Linux hosts.
- Use `pathlib` host paths and canonical `PurePosixPath` repository identities. Reject absolute,
  drive-relative, UNC/device, alternate-separator, traversal, control-bearing, dot/empty-component,
  and case-fold alias paths before any write or container interaction.
- Treat proposal paths case-insensitively and component-wise on every host. Never allow a case-only
  alias to create or target a different file on Linux than on Windows.
- Exact patch matching operates on logical lines. Accept consistent LF or CRLF source files,
  preserve their convention, reject lone-CR/mixed ambiguous files, and never depend on native text
  translation, locale encodings, Git autocrlf, or shell quoting.
- Candidate fingerprints and changed-file identities use relative POSIX paths and raw file bytes;
  absolute workspace names, timestamps, inode numbers, platform separators, and ordinary file-mode
  differences do not affect the digest.
- The actual static tools always run in a Linux container under Python 3.14, including when the host
  is Windows with Docker Desktop. Container commands and normalized results must therefore be
  identical for the same candidate bytes.
- Linux remains the production-supported adversarial host filesystem boundary. Native Windows is a
  development-supported host with the existing Task 0.1.4 TOCTOU limitation; this task must not
  claim Docker Desktop eliminates that host-side limitation.
- Windows commands use `.venv\Scripts\python.exe`; POSIX uses `.venv/bin/python`. The activated,
  portable command remains `python scripts/check.py`.

## 10. Security Considerations

- Treat the preparation, proposal, diff, repository bytes, candidate paths, source files, tool
  outputs, and container JSON as untrusted. Revalidate typed values rather than trusting object
  construction or caller order.
- Policy approval is a mandatory prerequisite. A rejected or malformed policy result cannot reach
  patch application. This task does not provide an override or approval exception.
- Host-side code may inspect, copy, compare, hash, and transform inert bytes only. It must never
  import, compile, execute, test, install, or invoke a candidate file on the host.
- Apply only inside a fresh staging copy. Validate the source fingerprint before and after copying,
  validate every destination component before writes, use exclusive creation/replacement, and fail
  closed on races or uncertain identity. Never write to the benchmark corpus, original preparation,
  project root, home directory, credentials, Docker configuration/socket, or evaluator tree.
- Exact matching is a security property: no fuzzy/offset hunks, path stripping, symlink following,
  external filters, shell interpolation, or partial application is allowed.
- The static image is trusted infrastructure; candidate contents and configuration are not. Use a
  fixed entrypoint and fixed tool arguments. Ruff isolation, mypy configuration/plugin suppression,
  and Bandit configuration/baseline suppression must prevent a repository from changing what runs
  or what counts as a failure.
- Static containers inherit all Task 0.1.3c controls: Linux, numeric non-root user, network none,
  read-only root, explicit tmpfs only, read-only candidate mount, CPU/memory/PID/time/output bounds,
  dropped capabilities, `no-new-privileges`, seccomp required and never unconfined, unique name, and
  removal on every path.
- Never mount application/model/GitHub credentials, proxy variables, developer home, project root,
  benchmark evaluator directories, hidden tests, reference patches, or Docker socket. Supply a
  small allowlisted fixed environment rather than forwarding the host environment.
- Compilation means generating an in-memory code object only inside the container. Do not write
  `.pyc`, import modules, run decorators, evaluate annotations, load entry points, invoke build
  backends, discover pytest plugins, or install dependencies.
- Tool output may echo secrets or source code. Bound it, parse it inside the trusted runner, emit
  only safe metadata, and discard raw output. Do not include raw diff/source/tool text, absolute
  paths, exception text, or environment data in results, errors, logs, assertions, or snapshots.
- Any candidate finding, tool crash, unexpected exit, malformed/truncated JSON, timeout, OOM,
  cleanup failure, post-tool candidate mutation, or inability to prove the changed-file set blocks
  progression.

## 11. Failure Cases

The implementation must produce stable typed blocking outcomes for at least:

- wrong runtime type, Pydantic-invalid/mutated preparation, proposal, policy result, request,
  runner result, or Docker protocol document;
- policy result rejected, internally inconsistent, empty, or otherwise not an approved Task 0.1.7
  result;
- prepared path missing, moved, aliased, protected, not a directory, changed since preparation, or
  mismatched to its recorded fingerprint;
- invalid/protected candidate workspace root, unsafe destination name, collision, escape,
  source/destination overlap, or inability to create private staging;
- unsafe source/candidate entry, symlink, junction/reparse point, hard link, special file,
  case-fold alias, inspection race, copy/fingerprint/read/write/rename error, or cleanup failure;
- malformed/unsupported diff, inconsistent proposal/diff paths, binary/mode/rename/copy metadata,
  invalid UTF-8, mixed/lone-CR newline structure, missing source file, unexpected existing new file,
  non-empty deletion result, hunk coordinate/context/removal mismatch, overlapping/repeated hunk,
  path escape, or partial-application attempt;
- actual added/modified/deleted set differs from the proposal, a declared change is a no-op, an
  undeclared file changes, an entry type changes unexpectedly, or the pristine preparation changes;
- Python compile failure and AST parse failure, each attributable to normalized changed-file
  metadata without retaining source text;
- Ruff finding, mypy finding, or Bandit finding, including multiple findings across tools;
- no surviving changed Python file, represented only as `not_applicable` for the five language/tool
  checks while patch and changed-file validation still run;
- static image missing, Docker CLI/daemon failure, insecure/non-Linux daemon, container create/start/
  inspect/wait/kill/remove failure, timeout, OOM, output truncation, invalid exit mapping, or cleanup
  failure;
- tool executable missing, incompatible version/protocol, invocation failure, signal termination,
  unexpected exit code, uncontrolled extra output, malformed/oversized JSON, invalid path/line/rule
  metadata, duplicate/unsorted findings, or attempted absolute-path disclosure;
- candidate or pristine-tree mutation detected after the container run or before publication.

Candidate findings return `candidate_failed`; failures in trusted tooling, Docker, protocol,
filesystem integrity, or cleanup return `infrastructure_diagnostic`. Both block progression and
return no candidate path. Process-control exceptions such as `KeyboardInterrupt` and `SystemExit`
must not be converted into ordinary candidate findings.

## 12. Acceptance Criteria

1. One typed static-validation service accepts the existing preparation/proposal/approved-policy
   contracts and uses injected typed filesystem/fingerprint and static-container boundaries.
2. The original prepared failing snapshot and benchmark fixture remain byte-identical. Patch work
   occurs only in a fresh contained staging copy, and only a fully passing candidate is published.
3. Patch application supports v0.1 text modification/addition/deletion with exact coordinates,
   context, removed lines, UTF-8, and newline semantics; every unsupported or mismatched patch fails
   atomically without Git, `patch`, shell, fuzz, offset, or partial application.
4. Changed-file validation proves the actual byte-level added/modified/deleted set equals the
   proposal and parsed diff before and after static tooling; undeclared/no-op/unsafe changes block.
5. Every surviving changed Python file receives separate Python 3.14 compilation and AST parsing
   inside the static container without import or execution.
6. Ruff, strict mypy, and Bandit run against all surviving changed Python paths with fixed
   TraceFix-owned settings and no candidate config, plugins, cache, exclusions, baselines, fixes,
   package installation, or network.
7. Any compile, AST, Ruff, mypy, or Bandit finding blocks progression. Independent findings are
   aggregated in fixed check/path/location/rule order; absence of changed Python is the only
   `not_applicable` case.
8. Candidate findings are distinct from tool/infrastructure diagnostics. Malformed, truncated,
   missing, incompatible, or unexpected tool evidence can never be interpreted as a pass.
9. Results are strict, frozen, deterministic, JSON-serializable Pydantic v2 contracts containing
   only bounded safe constants and normalized metadata. They never retain source/diff text, raw
   tool output, secrets, exception text, or absolute host/container paths.
10. Static analysis uses a fresh Linux container with all existing sandbox security/resource/output/
    cleanup controls and a fixed command surface. No candidate code or candidate-controlled tool
    configuration executes on the host or in the container.
11. A passing result contains exactly one validated candidate path and fingerprint and transfers
    cleanup ownership to the caller. Every non-pass contains neither and removes task-created
    staging/candidate content; cleanup failure remains visible and blocking.
12. Unit tests can trigger each check and each overall outcome independently through injected fakes.
    Docker integration tests demonstrate a clean pass and an isolated failure for compile, AST,
    Ruff, mypy, Bandit, tool error, timeout, and malformed output.
13. Existing planning, policy, preparation, sandbox, benchmark, and security behavior remains
    unchanged, including the pytest-only `tracefix-sandbox:0.1.3a` contract.
14. Formatting, linting, strict typing, dependency integrity, focused unit/integration tests, the
    full suite, canonical validation, and diff checks pass under Python 3.14.
15. No candidate tests, hidden tests, evaluation, graph/routing, CLI/artifact, persistence, retry,
    provider, adjacent/future behavior, unrelated dependency, commit, or push is introduced.

## 15. Definition of Done

- All seven execution-plan checks exist as strict typed deterministic results; every applicable
  failure and every tool/infrastructure error blocks progression.
- A policy-approved patch is applied exactly and atomically to a fresh candidate copy, the actual
  byte-level changed set is proven to match the proposal/diff, and neither fixture nor original
  prepared snapshot changes.
- Compilation, AST parsing, Ruff, strict mypy where applicable, and Bandit run only in the dedicated
  fixed-command hardened container and cannot be configured by candidate content.
- A clean candidate produces one immutable passing result with candidate path and fingerprint for
  Task 0.1.9. Every non-pass returns no candidate path, removes task-created workspace content, and
  exposes only safe structured evidence; cleanup failure is itself visible and blocking.
- Every check, result branch, patch/apply failure, changed-file mismatch, tool failure, malformed
  evidence, container failure, and cleanup path has focused unit or integration evidence.

  and the pytest-only sandbox image behavior is unchanged.

  images and runs the real Docker integration suite without secrets or untrusted network access.

## Assumptions Requiring Human Review

1. **Static-tool isolation:** approve a dedicated `tracefix-static-checks:0.1.8` image and fixed
   typed Docker adapter, while leaving the existing pytest-only sandbox image/command contract
   unchanged. This is the strict interpretation of “untrusted code must never execute on the host.”
2. **Candidate workspace lifecycle:** approve copying the prepared failing snapshot into a private
   staging tree, publishing only a passing candidate, cleaning every failed candidate, and
   transferring successful candidate cleanup to the later workflow owner. The execution plan does
   not state whether Node 8 may mutate the Task 0.1.4 preparation in place.
3. **Patch semantics:** approve the exact, no-offset/no-fuzz in-process UTF-8 text applicator for
   modify/add/delete patches and explicit rejection of Git metadata, rename/copy/mode/binary,
   non-UTF-8, and mixed-newline cases. The plan requires patch-apply validation but does not select
   Git, `patch`, a library, or matching semantics.
4. **Changed-file meaning:** approve byte/existence comparison of pristine and candidate trees, with
   the actual case-insensitive added/modified/deleted set required to equal both proposal and diff;
   a declared no-op is a failure. Directory and ordinary mode metadata are not repair changes.
5. **Analysis scope:** approve running the five Python/tool checks only on surviving changed `.py`
   and `.pyi` files. This avoids pre-existing repository findings and candidate-controlled project
   configuration; broader whole-repository regression behavior remains Task 0.1.9 testing.
6. **Not-applicable behavior:** approve `not_applicable` for compilation, AST, Ruff, mypy, and Bandit
   only when no changed Python file survives. Patch application and changed-file validation are
   always required.
7. **Ruff/mypy configuration:** approve fixed TraceFix-owned Python 3.14 Ruff rules and strict mypy
   settings, with candidate config/plugins/caches ignored. Ordinary import discovery may inspect
   source within the disposable candidate copy but may not import or execute it.
8. **Bandit policy and dependency:** approve `bandit>=1.9,<2` as a development/static-image
   dependency and treat every Bandit finding as blocking, with no severity/confidence threshold,

10. **Safe evidence:** approve retaining normalized path/location and bounded Ruff/mypy/Bandit rule
