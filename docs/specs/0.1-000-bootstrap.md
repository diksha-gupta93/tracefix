# Task 0.1.0 — Repository Bootstrap

## 1. Goal

Establish the smallest reviewable Python 3.14 repository foundation needed for later TraceFix v0.1 tasks. The implementation of this specification must create the agreed directory layout, packaging metadata, developer quality tooling, bootstrap documentation, and basic continuous integration without adding application or production behavior.

## 2. Context

TraceFix v0.1 is planned as a local, single-attempt repair agent, but Task 0.1.0 is only its repository bootstrap. Later specifications will introduce schemas, benchmark defects, sandbox execution, model integration, graph behavior, and evaluation behavior. This task must provide a consistent development baseline for Windows and Linux while preserving the one-task/one-specification discipline in `AGENTS.md` and `docs/plan/tracefix-execution-plan.md`.

The repository already contains the governing `AGENTS.md` and execution plan. They are inputs to this task and must not be replaced or modified.

## 3. In Scope

- Create the initial package and project directory skeleton described below.
- Add `pyproject.toml` as the single source of Python project metadata and configuration for Ruff, mypy, and pytest.
- Require Python 3.14 and define an editable development installation.
- Add development dependencies sufficient to run Ruff, mypy, and pytest.
- Add `scripts/check.py` as the single cross-platform validation entry point.
- Add a basic GitHub Actions CI workflow that installs the project and runs the same validation entry point used locally.
- Add a bootstrap `README.md` with prerequisites, editable-install instructions, validation instructions, current scope, and deferred behavior.
- Add `.gitignore` for Python, virtual-environment, test, type-checker, coverage, build, editor, and operating-system artifacts.
- Add `.gitattributes` with repository text normalization and explicit LF rules for source, configuration, documentation, scripts, and workflow files.
- Add only empty package markers or placeholder files where required to make the package importable or retain an otherwise empty required directory in Git.

## 4. Out of Scope

Task 0.1.0 must not add or implement:

- Pydantic application schemas.
- Benchmark defect implementations, manifests, fixture repositories, hidden tests, or reference patches.
- Docker sandbox implementation or Docker execution configuration.
- LangGraph nodes or graph wiring.
- Model-provider integrations.
- FastAPI.
- PostgreSQL.
- Redis or a worker queue.
- GitHub App integration.
- Observability services, tracing backends, metrics systems, or dashboards.
- Production application behavior, CLI behavior, repair behavior, or evaluation behavior.
- Runtime dependencies for future tasks.
- `.dockerignore`; it is deferred to Task 0.1.3a because that task will define the Docker build context.
- Changes to `AGENTS.md`, `docs/plan/tracefix-execution-plan.md`, or adjacent task specifications.
- Git commits or pushes.

## 6. Python and Packaging Requirements

- The supported interpreter is CPython 3.14. `pyproject.toml` must declare `requires-python = ">=3.12,<3.13"` so local and CI behavior use the same Python minor version.
- Use a PEP 517 build backend supported by Python 3.14. The selected backend and its build requirement must be declared in `[build-system]`.
- Package discovery must include `app` and its subpackages and must not package `tests`, `benchmarks`, `docs`, or `scripts`.
- The distribution name must be `tracefix`. The import package remains `app` because the execution plan explicitly establishes the `app/...` layout.
- Runtime dependency declarations must remain empty in this task.
- Define a `dev` optional dependency group containing Ruff, mypy, and pytest. Versions must be bounded to compatible major versions or otherwise constrained reproducibly; the exact selected constraints must be reported during implementation.
- A new development environment must be installable from the repository root with:

  ```text
  python -m pip install --editable ".[dev]"
  ```

- The editable installation must make `import app`, `import app.agent`, `import app.sandbox`, and `import app.evaluation.deterministic` succeed.
- Do not define a console-script entry point in this task.

## 7. Development Tool Requirements

- Ruff must provide formatting checks and linting. Configuration belongs in `pyproject.toml` and must target Python 3.14.
- mypy must provide strict static type checking for `app`, `benchmarks`, and `scripts`. Configuration belongs in `pyproject.toml` and must target Python 3.14.
- pytest must be the test runner. Configuration belongs in `pyproject.toml`, with discovery rooted in `tests` and separate `unit` and `integration` directories available for later tasks.
- `scripts/check.py` must invoke tools using the active interpreter (`sys.executable`) and `python -m ...` semantics, without depending on Bash, Make, PowerShell, or globally installed command shims.
- Validation must fail immediately with a non-zero exit code if any command fails and must propagate that failure to CI.
- The validation sequence must be deterministic and include, in order:

  1. `python -m ruff format --check .`
  2. `python -m ruff check .`
  3. `python -m mypy app benchmarks scripts`
  4. `python -m pytest`

- Tool exclusions, if needed for generated or environment directories, must be explicit in `pyproject.toml`; they must not suppress checks over project-owned Python source.

## 8. Cross-Platform Requirements

- The supported development platforms for the bootstrap are Windows and Linux with Python 3.14.
- The canonical validation command from the repository root must be:

  ```text
  python scripts/check.py
  ```

- `scripts/check.py` must use `pathlib`, `subprocess` argument lists, and `sys.executable`; it must not use shell command strings, platform-specific shell syntax, executable suffix assumptions, or hard-coded path separators.
- The script must resolve the repository root from its own file location and run correctly even when invoked from a different current working directory.
- `.gitattributes` must normalize text files and require LF for repository-controlled text formats, including Python, Markdown, TOML, YAML, JSON, and shell scripts. It must identify common binary formats as binary rather than normalizing them.
- Documentation commands must use forms valid in both PowerShell and POSIX shells. Environment activation may be documented separately by platform, but activation must not be required to understand the canonical command.
- CI must validate on Linux. Local Windows compatibility is established through platform-neutral implementation and documented manual validation; a Windows CI matrix is not required for this basic workflow.

## 9. GitHub Actions CI Requirements

- Add one basic workflow at `.github/workflows/ci.yml`.
- Trigger it for pushes and pull requests.
- Use an Ubuntu runner and an official Python setup action configured for Python 3.14.
- Grant only read access to repository contents through explicit workflow permissions.
- Check out the repository, install the editable development environment, and run `python scripts/check.py`.
- The workflow must not require secrets, model credentials, Docker, network access at test execution time, external services, databases, caches, or live-model calls.
- Action references must be pinned to immutable full commit SHAs. A nearby comment may identify the corresponding release tag for maintainability.
- CI must not duplicate the individual quality commands in workflow YAML; `scripts/check.py` is the shared local/CI entry point.
- Dependency installation from the Python package index is acceptable during workflow setup. Validation itself must be self-contained after installation.

## 10. Security Considerations

- This task executes no untrusted code and introduces no Docker execution path.
- Do not add secrets, credentials, tokens, secret-shaped examples, or environment dumps to source, documentation, tests, or CI.
- CI permissions must follow least privilege and must not use privileged events or write permissions.
- Development and build artifacts, environment files, credentials, private keys, and common local secret files must be excluded by `.gitignore`; provide a safe exception for intentionally committed example environment files if such files are introduced later.
- No dependency may be added for adjacent functionality. Bootstrap dependencies are limited to the chosen build backend and the three required development tools.
- Empty package markers must not perform imports, filesystem access, subprocess execution, network access, logging, or other side effects.
- Docker security requirements from `AGENTS.md` remain binding for later sandbox work but are not implemented here.
- `.dockerignore` is deliberately deferred to Task 0.1.3a, where the Docker build context and its exclusion policy will be defined together.

## 11. Failure Cases

Implementation is incomplete or invalid if any of the following occurs:

- The project installs or runs with an unsupported Python version without a clear packaging rejection.
- Editable installation fails on Python 3.14.
- Required directories are absent from the reviewed tree because empty directories were not retained.
- Package imports fail after editable installation.
- Ruff, mypy, pytest, or their configuration is missing.
- The validation script depends on a specific shell, current working directory, or operating-system path syntax.
- The validation script ignores a failed subprocess or returns success before every required check passes.
- Local validation and CI use different command paths.
- CI requires secrets, Docker, live services, or production integrations.
- CI actions use mutable tag references or receive unnecessary permissions.
- Line-ending configuration permits platform-specific churn in repository-controlled text files.
- Application behavior or any item listed in Out of Scope is introduced.
- `.dockerignore` is required or created before its build context is defined in Task 0.1.3a.
- Existing governing documentation is modified as part of bootstrap implementation.

## 12. Acceptance Criteria

1. The repository contains exactly the bootstrap structure required by Section 5, in addition to pre-existing files that are outside this task's ownership.
2. `pyproject.toml` declares Python `>=3.12,<3.13`, a PEP 517 build backend, distribution metadata, package discovery for `app`, an empty runtime dependency set, a `dev` extra, and Ruff/mypy/pytest configuration.
3. `python -m pip install --editable ".[dev]"` succeeds in a clean Python 3.14 virtual environment on a supported platform.
4. The four required package imports succeed after installation.
5. `python scripts/check.py` runs all four required checks in order and returns zero only when all pass.
6. Ruff formatting and lint checks pass over the bootstrap repository.
7. Strict mypy checking passes for `app`, `benchmarks`, and `scripts`.
8. pytest executes successfully even though Task 0.1.0 defines no application behavior. Any bootstrap-only test added to make empty-suite behavior explicit must test only bootstrap mechanics and must not anticipate later behavior.
9. The GitHub Actions workflow runs on pushes and pull requests using Ubuntu and Python 3.14, installs the editable `dev` environment, then invokes only the shared validation command.
10. The workflow has read-only contents permission, immutable action references, and no dependency on secrets or external services during validation.
11. `README.md` accurately documents the bootstrap state, Python requirement, editable installation, canonical validation command, and explicit absence of application behavior.
12. `.gitignore` and `.gitattributes` satisfy Sections 3, 8, and 10.
13. No out-of-scope application, infrastructure, integration, or production behavior is added.
14. `.dockerignore` is absent and its deferral to Task 0.1.3a is recorded in the README or implementation completion report as well as this specification.
15. `AGENTS.md`, the execution plan, and this approved specification are not modified during implementation.

## 13. Tests and Validation Commands

Run implementation validation from a clean Python 3.14 virtual environment. The implementation report must list the exact commands used and their results.

```text
python --version
python -m pip install --editable ".[dev]"
python -c "import app; import app.agent; import app.sandbox; import app.evaluation.deterministic"
python scripts/check.py
git diff --check
git status --short
```

`python scripts/check.py` is the required cross-platform quality-gate command and must execute formatting checks, linting, type checking, unit tests, and applicable integration tests through the configured pytest run. No Docker or live-service integration test applies to Task 0.1.0.

The final two Git commands are review checks: `git diff --check` detects whitespace errors, and `git status --short` provides evidence that only approved bootstrap files changed. They are not part of `scripts/check.py` because the validation entry point must also work outside a Git checkout and must not interpret unrelated reviewer worktree changes as a project-quality failure.

## 15. Definition of Done

Task 0.1.0 implementation is done only when:

- Every in-scope artifact exists and contains only bootstrap concerns.
- Every acceptance criterion has recorded evidence.
- Formatting, linting, strict type checking, unit tests, and applicable integration tests pass through `python scripts/check.py` on Python 3.14.
- Editable installation and required imports have been validated.
- The basic CI workflow matches the local validation path and meets the stated security constraints.
- Windows/Linux compatibility decisions and selected dependency constraints are reported.
- No application behavior, adjacent-task artifact, `.dockerignore`, or unrelated dependency has been introduced.
- The implementation completion report lists files changed, commands executed, test results, acceptance-criteria evidence, packaging and architecture decisions, security considerations, assumptions, and remaining risks or deferred work.
- No commit or push has been performed; the human reviewer retains responsibility for Git operations.
