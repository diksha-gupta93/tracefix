# Task 0.1.3c — Security Hardening and Adversarial Tests

## 1. Goal

Harden the existing resource-bounded Docker pytest runner against hostile repository content and
host-resource exposure. Complete the v0.1 sandbox controls assigned to Task 0.1.3c and prove them
with deterministic unit tests and bounded adversarial Docker integration tests.

This task extends the existing runner; it does not introduce a new execution system, arbitrary
command support, or later repair-workflow behavior.

## 2. Context

Tasks 0.1.3a and 0.1.3b already provide a typed Docker CLI adapter, strict pytest-command grammar,
a fixed project-owned Linux image, a read-only repository input mount, container-local writable
workspace, non-root execution, disabled networking, a read-only root filesystem, resource and
output limits, unique names, and exact-container cleanup. Task 0.1.3c closes the remaining sandbox
hardening gap defined by the execution plan.

The prepared repository is untrusted. Docker is an external system and remains accessible only
through the injected typed adapter. The Docker daemon and project-owned sandbox image are trusted
infrastructure prerequisites; this task does not claim protection from a malicious daemon, image,
host administrator, or Docker engine vulnerability.

Docker applies its built-in default seccomp profile when no seccomp override is supplied. This task
must require a daemon that reports seccomp support, prohibit `seccomp=unconfined`, and retain the
built-in default. A project-owned profile is permitted by the execution plan but is not required by
this specification.

## 3. In Scope

- Preserve and verify `--network none`, `--read-only`, numeric non-root execution, CPU/memory/PID
  limits, bounded output, unique container names, and cleanup in `finally`.
- Add `--cap-drop ALL` and `--security-opt no-new-privileges=true` to every execution container.
- Require a usable Linux Docker daemon with seccomp enabled and use Docker's built-in default
  seccomp profile without an untrusted or caller-controlled override.
- Reject any effective Docker configuration containing `seccomp=unconfined`.
- Keep the existing fixed image, entrypoint, user, mount targets, environment, and Docker flags
  under trusted application control.
- Strengthen prepared-repository validation before any container creation:
  - accept one absolute, existing, stable, repository-only directory;
  - reject a top-level symlink or junction/reparse-point alias;
  - reject nested filesystem entries that are symlinks, junctions, or other reparse points;
  - reject the repository root, developer home itself, Docker socket/config locations, SSH and
    cloud credential directories, common credential files, and any source that is equal to or an
    ancestor of those protected locations;
  - reject sources that cannot be completely inspected or whose identity changes during
    validation;
  - bind exactly that validated source read-only at the fixed input target.
- Pass only a fixed minimal allowlist of non-secret environment assignments. Do not inherit or
  forward the host environment into the container.
- Add adversarial unit and Docker integration coverage for every case listed in the execution plan.
- Update CI and user documentation only as needed to execute and accurately describe these tests.

Protected host locations must be derived cross-platform without reading their contents. At
minimum, policy must recognize the repository root; the current user's home directory itself;
`~/.ssh`, `~/.docker`, `~/.aws`, `~/.config/gcloud`, and `~/.azure`; common netrc, npm, and PyPI
credential files; `/var/run/docker.sock`, `/run/docker.sock`, and the Windows Docker named-pipe
form. Merely living elsewhere beneath a user profile is not sufficient for rejection, because
ordinary Windows temporary directories commonly do so.

## 4. Out of Scope

- A custom seccomp profile or restrictive Python syscall allowlist.
- Rootless Docker, user namespaces, AppArmor/SELinux policy, gVisor, Firecracker, Kubernetes, or
  protection from a compromised Docker daemon.
- Docker SDK adoption, Docker-in-Docker, Docker socket mounting, or arbitrary caller-supplied Docker
  options, images, mounts, environments, users, entrypoints, or commands.
- Dependency installation, controlled network-enabled preparation, package registry access, or
  support for repositories whose tests need additional dependencies.
- Patch policy, protected repair paths, secret scanning of proposed patches, static analysis,
  hidden-test staging, or benchmark evaluator materialization.
- LangGraph, repair logic, model providers, CLI behavior, FastAPI, persistence, queues, GitHub,
  tracing, metrics, or later-version security documentation.
- Solving cleanup after abrupt host-process termination, operating-system crash, or Docker daemon
  loss. This task covers exceptions and crashes represented within the runner process.
- Reclassifying resource outcomes already specified by Task 0.1.3b.

## 6. Python and Packaging Requirements

- Continue to require CPython `>=3.14,<3.15` and use the existing `.venv`.
- Add no runtime or development dependency. Continue using the Docker CLI behind the existing typed
  protocol with argument sequences and `shell=False`.
- Keep all interfaces fully typed. Do not use `Any`, implicit dictionaries across module
  boundaries, unparameterized collections, or new type-checking suppressions.
- Represent protected-path and security-option policy with immutable typed values or focused typed
  functions. Do not accept free-form security options or mount collections from callers.
- Path comparison must be component-aware and platform-aware; string-prefix comparison is
  insufficient. Validation must fail closed on filesystem inspection errors.
- Do not read credential files or log protected paths, environment values, repository contents, or
  secrets while validating the source.
- Preserve the existing `SandboxLimits`, `SandboxResult`, completion classifications, and approved
  pytest-command contract.
- Keep the fixed project-owned image tag unless a change is essential. If changed, update the
  runner, CI, README, and validation commands together.

## 7. Development Tool Requirements

- Ruff formatting/linting, strict mypy, pytest, and `scripts/check.py` remain authoritative.
- Write failing tests first where practical and add tests for every new validation and security
  behavior.
- Unit tests must use the fake Docker adapter and temporary paths; they must not require Docker,
  network access, credentials, or mutation of real protected locations.
- Integration tests must use the fixed prebuilt image and real Docker CLI. They must not build or
  pull an image, install dependencies, mount credentials, mount the Docker socket, or require host
  secrets.
- Adversarial workloads must be synthetic, bounded by small test-specific resource/time limits,
  and safe for developer machines and CI runners.
- Existing 0.1.3a/3b tests and controls must remain intact. Do not weaken assertions, markers,
  strictness, skips, or security settings to make adversarial tests pass.

## 8. Cross-Platform Requirements

- Host behavior must work on Windows and Linux with Docker Linux containers, including Docker
  Desktop on Windows.
- Use `pathlib`, filesystem metadata, and argument lists; do not use host shell syntax, quoting,
  executable mode assumptions, or POSIX-only host commands.
- Detect Windows drive/UNC/named-pipe forms and filesystem reparse points as well as POSIX symlinks.
  Case comparison must follow the host platform's path semantics.
- Continue passing a mount source containing spaces as one Docker argument. Container targets and
  pytest paths remain fixed POSIX paths.
- Tests for protected paths must account for platform availability and must create safe synthetic
  aliases where a real symlink/junction can be created. A platform-specific capability absence may
  skip only that alias-construction assertion, not the broader invalid-mount suite.
- Security assertions inside the container must use Python standard-library operations rather than
  assuming utilities such as `curl`, `sudo`, `mount`, or a shell are installed.
- LF rules in `.gitattributes` remain authoritative.

## 9. GitHub Actions CI Requirements

- Preserve `ubuntu-latest`, Python 3.14, pinned actions, and workflow-level `contents: read`.
- Continue installing with `python -m pip install --editable ".[dev]"`, building the fixed sandbox
  image before validation, and running `python scripts/check.py`.
- Ordinary CI must execute the complete adversarial Docker integration suite. It must fail if the
  Linux daemon lacks seccomp support, a required security flag is absent/rejected, an adversarial
  probe succeeds, or a generated container remains.
- CI must not use repository/environment secrets, credentials, network-dependent test targets,
  privileged containers, service containers, registry login, Docker socket mounts into execution
  containers, or third-party actions added for this task.
- Network-blocking tests must prove absence of a usable network interface/route or deterministic
  connection failure without depending on availability of an external Internet host.
- Do not add a matrix, separate workflow, live-model call, or scheduled/manual benchmark.

## 10. Security Considerations

- Validation must complete before Docker container creation. Invalid commands, mounts, daemon
  security posture, or security options fail closed without starting untrusted code.
- The only host bind mount is the fully validated prepared repository, read-only. The Docker socket,
  project root, home directory, credential stores, GitHub/model credentials, and additional host
  paths must never be mounted.
- Nested links/reparse points are rejected so a repository cannot smuggle a reference to a host
  path into the bind mount. Validation reduces path-confusion risk but cannot eliminate a hostile
  local process racing filesystem changes; callers must prepare workspaces in trusted storage.
- The container environment must be constructed from a fixed allowlist. At minimum, retain only
  the current deterministic Python settings if needed; do not forward `os.environ`, proxy settings,
  tokens, cloud variables, Docker configuration, or credential-related variables.
- `--cap-drop ALL`, `no-new-privileges`, numeric non-root execution, default seccomp, no network,
  read-only root, bounded tmpfs locations, and Task 0.1.3b resource limits are defense in depth and
  must be applied before container start.
- Do not use `seccomp=unconfined`. Do not invent a narrow allowlist without workload analysis. If a
  project-owned profile is later selected, it requires a separately reviewable architecture
  decision and tests; it is not needed to complete this task.
- Cleanup targets only the collision-resistant name generated for the current execution and remains
  in `finally`. Never use broad Docker prune, prefix deletion, or cleanup of unrelated containers.
- Error messages and logs may identify a generated container name or rejected policy category but
  must not reveal environment values, protected path values, or repository contents.

## 11. Failure Cases

The runner must fail closed, without starting untrusted code, for:

- a mount source rejected by any Section 3 rule, including inaccessible entries or link/reparse
  points;
- an attempt to use more than the single fixed bind source or to alter a mount target/mode;
- a Docker option set containing `seccomp=unconfined`, caller-controlled security options, mounts,
  environment, image, user, entrypoint, or networking;
- a daemon that is unavailable, is not serving Linux containers, or does not report seccomp
  support;
- Docker rejecting capability, privilege, seccomp-default, read-only, network, user, resource, or
  mount controls;
- malformed Docker security or inspection output;
- inability to create, start, inspect, wait for, kill, or remove the exact generated container;
- a negative duration or malformed typed result, as already required by prior tasks.

During adversarial execution, attempted network access, privileged operations, process explosion,
or writes outside writable locations may surface as expected permission/operation failures or an
ordinary failing pytest result. The host boundary is successful only when the forbidden operation
does not succeed and cleanup completes.

If execution and cleanup both fail, preserve evidence of both using the existing chained/combined
error behavior. Cleanup failure must never be hidden. Runner-process exceptions after container
creation must still execute the exact-container `finally` cleanup path.

## 12. Acceptance Criteria

1. Every execution container uses the existing network, read-only, non-root, resource, output,
   unique-name, and exact-cleanup controls plus `--cap-drop ALL` and
   `--security-opt no-new-privileges=true`.
2. Docker's built-in default seccomp profile remains active; daemon seccomp support is checked and
   no execution path can select `seccomp=unconfined`.
3. No custom syscall allowlist or caller-controlled security-profile interface is introduced.
4. Exactly one validated repository source is mounted read-only at the fixed input target; no
   Docker socket, home, credential, project-root, or additional host mount is possible.
5. Mount validation rejects protected sources, ancestors of protected sources, top-level and nested
   links/reparse points, unstable paths, and inspection failures before container creation.
6. Container environment construction is a fixed non-secret allowlist and does not inherit host
   environment variables, credentials, or proxy settings.
7. Docker integration tests prove networking is blocked, host credentials and Docker socket are
   inaccessible, and writes outside the designated workspace/temp locations fail.
8. Docker integration tests prove the process remains numeric non-root, capability/privilege
   escalation attempts fail, and process explosion is bounded by the configured PID limit.
9. Unit and integration tests prove a runner exception after container creation still removes the
   exact container and leaves no TraceFix container behind.
10. Invalid mount tests prove rejection occurs before any container is created.
11. Unit tests inspect the complete Docker create arguments and prove no secret or unexpected host
    environment value or mount appears.
12. Adversarial tests are deterministic, bounded, run in ordinary CI, and require no secrets or
    external network service.
13. Existing 0.1.3a/3b result, timeout, resource, output, command-validation, and cleanup behavior
    remains passing.
14. No adjacent patch-policy, workflow, dependency-preparation, API, persistence, GitHub, model, or
    observability behavior is added.
15. Formatting, linting, strict typing, unit tests, applicable Docker integration tests, and diff
    checks pass with the existing Python 3.14 environment.

## 13. Tests and Validation Commands

Add or extend unit tests covering at minimum:

- exact presence of network-none, read-only, numeric-user, CPU/memory/PID, capability-drop, and
  no-new-privileges arguments;
- absence of `seccomp=unconfined`, caller-controlled Docker options, additional mounts, and inherited
  environment;
- daemon/Linux/seccomp prerequisite validation before container creation;
- fixed environment allowlist despite synthetic secret/proxy variables in the host test process;
- valid repository-only source acceptance;
- rejection of repository root, home, credential paths, Docker socket forms, protected-path
  ancestors, top-level aliases, nested symlinks/reparse points, inaccessible trees, and unstable
  sources;
- invalid mount rejection without a Docker create call;
- unique names and exact cleanup after pass, test failure, adapter failure, malformed response,
  timeout/resource failure, and injected runner exception after creation;
- preservation of simultaneous execution and cleanup failure evidence.

Add or extend Docker integration tests covering at minimum:

- network interface/route or local connection attempts cannot provide container network access;
- representative host credential paths are absent without mounting or reading real credentials;
- `/var/run/docker.sock` and `/run/docker.sock` are absent and unusable;
- writes to `/`, `/root`, the read-only input, and another non-workspace root path fail, while the
  fixed workspace and required temporary directory remain writable;
- UID/GID remain `10001:10001`, effective capabilities are empty, `no-new-privileges` is observable,
  and a representative privilege-gaining operation fails;
- process creation is bounded by a deliberately small `pids_limit`;
- an injected runner crash after container creation triggers cleanup and leaves no matching
  container;
- no synthetic host secret or proxy variable appears in the container environment;
- an invalid mount is rejected without container creation;
- all existing timeout, memory, output, normal pass/fail, and cleanup scenarios still pass.

Use standard-library probes and `/proc` only where available in the required Linux container. Tests
must assert the security property, not a particular incidental error string.

Run from the repository root using the existing environment:

```text
.venv\Scripts\python.exe --version
docker version
docker info --format "{{json .SecurityOptions}}"
docker build --tag tracefix-sandbox:0.1.3a --file docker/sandbox/Dockerfile .
.venv\Scripts\python.exe -m pytest tests/unit/test_sandbox_results.py tests/unit/test_sandbox_runner.py
.venv\Scripts\python.exe -m pytest tests/integration/test_sandbox_runner.py
.venv\Scripts\python.exe -m ruff format --check .
.venv\Scripts\python.exe -m ruff check .
.venv\Scripts\python.exe -m mypy app benchmarks scripts
.venv\Scripts\python.exe -m pytest
.venv\Scripts\python.exe scripts/check.py
git diff --check
git status --short
```

POSIX uses `.venv/bin/python` for the same Python commands. The canonical cross-platform gate
remains `python scripts/check.py`. The image build remains an explicit prerequisite. A local Docker
skip caused by an unavailable Linux daemon must be reported as validation risk; ordinary CI must
execute, not skip, the security integration tests.
