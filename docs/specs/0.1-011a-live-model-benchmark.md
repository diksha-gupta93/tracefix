# Task 0.1.11a — Live-Model Benchmark Command and Report

## 1. Goal

Add the separate, explicitly invoked v0.1 live-model benchmark path. The installed command

```text
tracefix benchmark --split development --provider <provider>
```

must run the five existing development cases through the real single-attempt TraceFix pipeline
using an explicitly configured live provider, then publish one strict JSON report and one
human-readable report. The reports record each repair outcome and aggregate model latency, input
tokens, output tokens, and estimated USD cost.

A valid but unsuccessful repair is benchmark evidence, not a command failure. A platform or
provider infrastructure failure is an execution failure. Live evaluation must remain independent
of required ordinary CI and must be available through a manual GitHub Actions
`workflow_dispatch` workflow.

## 2. Context

Tasks 0.1.0 through 0.1.10b already provide:

- Python 3.14 packaging, Ruff, strict mypy, pytest, `python scripts/check.py`, and ordinary CI;
- exactly five validated cases in `benchmarks/development`, with trusted evaluator data separated
  from model-safe context;
- a hardened Docker sandbox and static-check image;
- a typed, dependency-injected `ModelProvider` boundary with strict configuration, requests,
  responses, prompts, and safe diagnostics;
- the eleven-node, one-attempt LangGraph workflow and stable terminal outcomes;
- deterministic candidate evaluation with nullable model latency, token, and exact Decimal-USD
  fields;
- safe, metadata-only per-run JSON artifacts and the installed `tracefix repair <case_id>` command;
  and
- the `tracefix-fake` provider and all-five-case deterministic integration test in ordinary CI.

The fake-model path answers whether the platform behaves correctly. This task answers how a
specific live model performs on the development benchmark. It must reuse the same prompts,
context isolation, patch policy, static checks, sandbox verification, evaluation, terminal routing,
and cleanup behavior. A benchmark-specific shortcut, relaxed policy, exposed reference answer, or
host execution would invalidate the comparison.

The current `ModelProviderResponse` contains only raw JSON. The current graph can accept aggregate
`CandidateModelUsage`, but ordinary provider calls do not yet supply it. This task may minimally
extend the typed provider/measurement boundary so live call latency and provider-reported token
usage can be accumulated across planning and patch generation without exposing provider SDK
objects to business logic. The existing fake provider continues to report no synthetic usage.

The first approved live adapter for this specification is named `openai`. It uses the official
OpenAI Python SDK and Responses API behind the existing project-owned `ModelProvider` protocol.
The provider and SDK choice is an explicit human-review assumption at the end of this
specification; it is not a general multi-provider framework commitment.

## 3. In Scope

- Add the installed command exactly in the form:

  ```text
  tracefix benchmark --split development --provider openai
  ```

- Accept exactly the implemented split `development`. Reject missing, blank, differently cased,
  unknown, or extra split/provider values before loading cases, creating workspaces, contacting a
  provider, starting Docker, or writing reports.
- Load the split through the existing trusted benchmark loader and execute all five cases in its
  deterministic case-ID order. Execution is sequential; v0.1 must not parallelize model calls or
  repair cases.
- Run every attempted case through the same real eleven-node pipeline used by `tracefix repair`.
  Do not invoke the deterministic fake provider, use reference patches, inject successful graph
  nodes, or create a benchmark-only repair path.
- Add one concrete `openai` adapter behind `ModelProvider`:
  - use the official provider SDK only inside the adapter;
  - use the configured model name, temperature, maximum output tokens, prompt version, operation,
    attempt number, case identity, and existing rendered prompt;
  - request a strict JSON response for the operation's existing Pydantic schema;
  - disable tools, hosted search, file access, code execution, streaming, and automatic retries;
  - apply a finite request timeout; and
  - convert SDK results and failures into project-owned typed responses or existing safe model
    diagnostics before returning across the adapter boundary.
- Read the live credential only in the provider factory from `OPENAI_API_KEY`. Do not add the key
  to `ModelConfiguration`, graph state, provider requests, reports, artifacts, diagnostics, or
  logs.
- Continue to use the existing model configuration variables:
  - `MODEL_PROVIDER`;
  - `MODEL_NAME`;
  - `MODEL_TEMPERATURE`;
  - `MODEL_MAX_TOKENS`; and
  - `PROMPT_VERSION`.
- Require `--provider` to equal `MODEL_PROVIDER` exactly and require the supported prompt version
  `repair-v1.0`. The benchmark command must not silently select, substitute, or fall back to a
  provider or model.
- Add strict benchmark-only configuration for:
  - `MODEL_REQUEST_TIMEOUT_SECONDS`, a provider request timeout in seconds in the inclusive range
    `1..300`;
  - `MODEL_INPUT_PRICE_USD_PER_MILLION_TOKENS`, the input-token price in USD per one million
    tokens; and
  - `MODEL_OUTPUT_PRICE_USD_PER_MILLION_TOKENS`, the output-token price in USD per one million
    tokens.
  These values may be supplied by dedicated environment variables so the required command surface
  remains the one named by the execution plan. Missing or invalid values are preflight execution
  failures; no current provider price may be hard-coded as a permanent truth.
- Measure each provider call's elapsed wall-clock latency at the trusted adapter boundary with a
  monotonic clock. Capture provider-reported input and output token counts from the same response.
  Aggregate the two operation measurements actually performed for a case. Do not infer tokens from
  text length or `MODEL_MAX_TOKENS`.
- Calculate estimated cost with `Decimal` arithmetic using the explicitly supplied per-million
  input and output rates:

  ```text
  estimated_cost_usd =
      input_tokens * input_rate_usd_per_million / 1_000_000
    + output_tokens * output_rate_usd_per_million / 1_000_000
  ```

  Preserve the configured rates and exact unrounded Decimal result in JSON. Human-readable display
  formatting must not change the stored value.
- Keep measurement state invocation-local and case-local. Use typed dependency injection; do not
  use module globals, ambient mutable registries, provider SDK objects in graph state, or untyped
  dictionaries across module boundaries.
- Make aggregate usage available to existing candidate evaluation when evaluation is reached, and
  to the benchmark result for earlier valid model-repair failures such as malformed structured
  output. The benchmark report, rather than the pre-existing per-run artifact, is the canonical
  complete live-usage record for this task.
- Preserve the existing `tracefix repair` behavior, output, artifact schema, exit codes, and
  deterministic fake-provider profile. A benchmark implementation may extract a typed internal
  repair-run result for reuse, but it must not duplicate or bypass the repair pipeline.
- Define strict frozen Pydantic v2 report contracts with an explicit schema version. The JSON
  report must contain at least:
  - benchmark run ID, split, provider, model, prompt version, one-attempt limit, UTC start and
    completion timestamps, and overall execution status;
  - the exact configured timeout and pricing rates used for the run;
  - one ordered case result per development case, or an explicit `not_run` marker after a
    fail-fast execution failure;
  - case ID, terminal repair outcome when available, benchmark classification, per-case model
    latency, input tokens, output tokens, estimated USD cost, and safe relative run-artifact path
    when publication succeeded;
  - counts for attempted, not-run, repair-success, repair-failure, and execution-failure cases;
  - success rate over completed repair results only; and
  - aggregate model latency, token counts, and estimated USD cost for completed provider calls.
- Use these benchmark classifications:
  - `repair_success`: terminal outcome `success`;
  - `repair_failure`: terminal outcome `candidate_failure`, `policy_violation`,
    `static_check_failure`, or `malformed_model_output`; and
  - `execution_failure`: provider/SDK/authentication/transport/timeout/usage failure, platform
    `infrastructure_failure`, `baseline_not_reproducible`, report/publication failure, or internally
    inconsistent evidence.
- Treat a split as successfully executed, with process exit `0`, when every case produces either
  `repair_success` or `repair_failure` and both reports publish successfully. Repair success is not
  required for benchmark command success.
- Fail fast after the first `execution_failure`, mark remaining ordered cases `not_run`, attempt to
  publish the partial report, and return exit `6`. Invalid command input returns exit `2` without a
  report. `KeyboardInterrupt` remains exit `130` after safe cleanup and must not be represented as a
  successful benchmark.
- Publish atomically, without overwrite, beneath an invocation-relative directory:

  ```text
  .tracefix/benchmarks/<benchmark_run_id>/report.json
  .tracefix/benchmarks/<benchmark_run_id>/report.md
  ```

  Use a validated random run ID and safe relative paths. The Markdown report must present the same
  identities, classifications, per-case measurements, and aggregates as JSON; JSON is canonical if
  presentation differs.
- Print one concise safe benchmark summary containing split, provider, model, counts, overall
  execution status, exit code, and the two relative report paths. Do not print per-case prompts,
  responses, diffs, exceptions, credentials, or absolute paths.
- Add a separate manual `.github/workflows/live-benchmark.yml` workflow triggered only by
  `workflow_dispatch`. It must install the live optional dependency, build the existing fixed
  Docker images, run the benchmark, upload the generated JSON/Markdown and safe per-case artifacts,
  then preserve the benchmark command's success/failure status.
- Add deterministic unit and integration tests for new behavior without making a real provider
  request. A real credentialed manual workflow run is separate acceptance evidence.

## 4. Out of Scope

- Adding any second live provider, generic plugin discovery, entry-point loading, dynamic imports,
  provider fallback, model routing, or provider/model comparison.
- Changing the five fixtures, manifests, visible tests, hidden tests, evaluator bundles, reference
  patches, bug categories, or development split membership.
- Validation or locked-test splits, ten additional cases, category expansion, ambiguous/unfixable
  cases, or benchmark partition redesign; those begin in v0.2.
- Confidence intervals, repeated trials, `success@2`, `success@3`, p50/p95 reporting, statistical
  significance, leaderboard generation, or cost-per-success analysis; those belong to v0.2
  evaluation reporting.
- Multiple repair attempts, model retries, infrastructure retries, retry backoff, fallback models,
  checkpoints, persistence, databases, queues, workers, FastAPI, GitHub repair integration,
  LangSmith, OpenTelemetry, Prometheus, or Grafana.
- Scheduled or push/pull-request live benchmarks. Only explicit manual dispatch is included.
- Making live-model repair success a required CI/release gate or weakening deterministic ordinary
  CI when a live provider is unavailable.
- Changing the prompt version, prompt content, context selection, graph topology, terminal route
  set, patch policy, static checks, sandbox limits/security, verification logic, or evaluator rules.
- Treating provider response confidence as proof, executing generated code on the host, exposing
  network access to execution containers, or exposing benchmark answers to the model.
- Fetching pricing dynamically, claiming billed cost, reconciling invoices, accounting for provider
  discounts/cached-token tiers beyond the explicitly configured two-rate estimate, or promising
  permanent model availability/pricing.
- Publishing results to a branch, pull request, release, dashboard, database, or external service
  other than GitHub Actions run artifacts.
- Broad README/release documentation and the v0.1 release checklist; those are Task 0.1.11b.

## 6. Python and Packaging Requirements

- Use only the existing CPython `>=3.14,<3.15` environment and `.venv`. On Windows invoke
  `.venv\Scripts\python.exe`; on POSIX invoke `.venv/bin/python`.
- Keep setuptools as the build backend and preserve the installed `tracefix` entry point.
- Add the official `openai` Python SDK only as a bounded optional dependency named `live`, proposed
  as `openai>=2,<3`. Do not add it to the core runtime dependency list or make ordinary fake-model
  CI require provider credentials or a live endpoint.
- Import the optional SDK only inside the concrete adapter/factory. Missing optional dependencies
  must become a safe benchmark preflight execution failure, not an import-time failure for
  `tracefix repair`, `tracefix --help`, unit tests, or ordinary CI.
- Do not add LangChain, a provider multiplexer, an HTTP/retry library, a tokenizer, a pricing
  library, dotenv, a reporting framework, or another runtime.
- Use Pydantic v2 strict, extra-forbidding, frozen models for cross-module live call usage,
  benchmark configuration, case results, aggregate results, report paths, and report publication.
- Fully type public and cross-module interfaces. Do not use `Any`, implicit dictionaries, raw SDK
  objects outside the adapter, stringly typed outcomes, or casts that bypass strict validation.
- Reuse `ModelProvider`, `ModelProviderRequest`, `ModelProviderResponse`, `ModelConfiguration`,
  `CandidateModelUsage`, `CandidateEvaluationResult`, `RunArtifact`, `TerminalOutcome`,
  `TrustedCase`, and the existing repair graph. Extend them minimally rather than creating
  competing meanings.
- Token counts are strict nonnegative integers. Timeout and latency are finite nonnegative values
  with a strictly positive bounded timeout. Pricing and cost use finite nonnegative `Decimal`
  values denominated explicitly in USD.
- JSON serialization must use UTF-8, stable field names, deterministic case order, and a trailing
  newline. Decimal values must round-trip exactly; do not serialize cost through binary float.
- Keep the existing provider response UTF-8 size limit and strict structured-output parsing. A live
  adapter must not relax schema validation or extract JSON from Markdown/prose.

## 8. Cross-Platform Requirements

- CLI parsing, report contracts, ordering, cost arithmetic, Markdown rendering, and path validation
  must behave equivalently on Windows and Linux.
- Use `pathlib`/`PurePosixPath` for validated report identities and invocation-relative published
  paths. Reject absolute, drive-relative, UNC/device, backslash, empty, dot, traversal, NUL-bearing,
  case-fold-colliding, symlinked, junction/reparse-point, or pre-existing alias destinations.
- Write JSON and Markdown as UTF-8 with LF line endings. Do not depend on locale encoding or native
  newline translation.
- Invoke subprocesses in tests and workflows with argument vectors, never a constructed shell
  command. Provider, model, split, price, and timeout inputs must not be interpolated into shell
  syntax.
- Measure request latency with `time.monotonic()` or an injected equivalent, never by subtracting
  wall-clock timestamps.
- Atomic publication must use the existing no-overwrite/owned-temporary-file security pattern and
  clean partial output on Windows and Linux. A partially published pair is an execution failure;
  the summary must not claim a complete report pair.
- Live model access occurs from the trusted host runner through the typed adapter. All benchmark
  repository/test execution remains in fresh hardened Linux containers with network disabled.
- The portable activated commands are `python scripts/check.py` and
  `tracefix benchmark --split development --provider openai`.

## 10. Security Considerations

- The live provider is an external system and must be accessed only through the typed adapter.
  Business/graph/reporting logic must not import the SDK, read credentials, or issue ad hoc network
  calls.
- `OPENAI_API_KEY` remains in the trusted provider process only. Never pass it, proxy variables, the
  host environment, model credentials, application secrets, GitHub credentials, or provider SDK
  configuration into Docker execution containers.
- Preserve every sandbox control: non-root execution, disabled network, read-only root filesystem,
  explicit writable temporary directories, CPU/memory/PID/time/output limits, dropped capabilities,
  `no-new-privileges`, default seccomp, validated mounts, no Docker socket, no home mount, unique
  containers, and cleanup.
- Send only the existing bounded rendered prompts. Hidden tests, reference patches, evaluator
  directories, manifests, expected/forbidden-file metadata, secrets, unrelated repository files,
  and absolute host paths must remain outside provider requests and reports.
- Treat provider text, refusal content, plan fields, patch fields, diffs, SDK metadata, and error
  bodies as untrusted. Strictly validate and bound them; never execute, log, echo, upload, or include
  raw values in safe diagnostics/reports.
- The provider has no tools. Disable hosted browsing/search, file retrieval, code interpreter,
  function calling, remote MCP, computer use, and any provider-side capability beyond generating
  the requested strict structured response.
- Disable automatic provider retries in v0.1. An uncertain request must be reported as an execution
  failure; do not silently issue a duplicate paid request or claim exactly-once semantics.
- Validate provider-reported usage before cost calculation. Reject negative, non-integer,
  non-finite, missing required, overflowed, or internally inconsistent measurements. Never trust
  model-generated token/cost claims.
- Price values are trusted operator inputs but still strictly validated and recorded in the report.
  Label the result `estimated_cost_usd`; never label it billed, invoiced, or exact provider cost.
- Bound spend structurally: one attempt, five cases, sequential execution, at most planning and
  generation calls per case, configured maximum output tokens, no retries, finite timeout, and
  fail-fast on the first execution failure.
- Publish reports through owned, private, atomic, no-overwrite paths. Reports contain safe
  metadata only: no prompt, raw response, patch/diff, exception text, stdout/stderr, credential,
  environment dump, absolute path, or hidden/reference content.
- GitHub Actions inputs and artifacts are visible to authorized repository users. The workflow must
  not print secret-derived values and must use least privilege and pinned actions.

## 11. Failure Cases

The implementation must fail closed for at least:

- missing/unknown command, split, provider, unexpected argument, provider/configuration mismatch,
  or unsupported prompt version;
- missing, blank, malformed, wrong-type, non-finite, negative, zero/out-of-range timeout, token
  price, model setting, or credential;
- optional live dependency missing, wrong SDK major version, client construction failure, invalid
  provider/model access, authentication/authorization failure, rate limit, connection/DNS/TLS
  failure, provider 5xx, request timeout, or provider cancellation;
- automatic retry enabled, more than two model calls attempted for one case, more than one repair
  attempt, parallel case execution, or fallback provider/model selection;
- provider returns the wrong SDK/result shape, no terminal response, a refusal/incomplete response,
  oversized text, wrong content type, multiple outputs, invalid structured JSON, or an invalid
  project response envelope;
- token usage missing after a completed provider response, Boolean/coerced/negative/overflow token
  count, inconsistent totals, non-finite latency, or unsafe price/cost arithmetic;
- benchmark loader failure, wrong case count/order/identity, changed split membership, baseline not
  reproducible, graph/platform infrastructure route, Docker/image/seccomp failure, sandbox timeout/
  OOM/protocol failure, workspace/container cleanup uncertainty, or run-artifact publication
  failure;
- any repair outcome/report classification disagreement, success-rate denominator including
  `not_run` or execution failures, aggregate count/usage/cost disagreement, duplicate/missing case,
  or report schema inconsistency;
- unsafe report path, pre-existing destination, symlink/junction/reparse alias, temporary-file
  collision, partial write, flush/sync/close/rename failure, one report without the other, or output
  outside the invocation directory;
- stdout/stderr failure, report upload failure, interruption, or an exception that cannot be mapped
  to a safe typed diagnostic; and
- regression in existing fake-provider behavior, repair CLI behavior, graph routes, artifacts,
  benchmark isolation, sandbox security, tests, formatting, linting, typing, packaging, or ordinary
  CI.

A provider call that completed but returned malformed/refused/incomplete model content maps to the
existing `malformed_model_output` repair failure when safe evidence proves the provider operation
completed. Failure to establish a completed response or trustworthy usage is provider
infrastructure failure. Raw provider error/content must never be used to make this distinction in
the report.

## 12. Acceptance Criteria

1. The installed CLI accepts `tracefix benchmark --split development --provider openai` and rejects
   unsupported input before side effects with exit `2`.
2. The benchmark loads exactly the five existing development cases in deterministic case-ID order
   and runs them sequentially through the unchanged real one-attempt graph and hardened execution
   boundaries.
3. One concrete `openai` adapter implements the existing typed provider contract. Provider SDK
   types and credentials do not cross the adapter boundary, and no tools, streaming, fallback, or
   retry is enabled.
4. Live credentials are required only for the benchmark composition, are read only by the provider
   factory, and never enter prompts, state, containers, diagnostics, console output, reports, or
   artifacts.
5. Planning and generation use the existing model-safe context, prompts, schemas, configuration,
   and attempt `1`; hidden tests and reference answers remain isolated.
6. Each completed provider call contributes trusted-adapter latency plus strict provider-reported
   input/output tokens. Per-case and aggregate usage are arithmetically consistent.
7. Estimated USD cost uses exact Decimal arithmetic and the exact recorded operator-supplied rates;
   no price is fetched, guessed, or permanently hard-coded.
8. Existing candidate evaluation receives aggregate live usage when it is reached. Earlier valid
   repair failures retain their completed call usage in the benchmark report.
9. Every case is classified exactly as `repair_success`, `repair_failure`, `execution_failure`, or
   `not_run` according to Section 3. A repair failure does not make the benchmark command fail.
10. The first execution failure stops further paid/model work, marks the remaining ordered cases
    `not_run`, publishes a partial safe report when possible, and returns exit `6`.
11. A successful benchmark execution publishes exactly one versioned strict JSON report and one
    equivalent Markdown report at safe invocation-relative no-overwrite paths and prints one safe
    summary. JSON/Markdown contain no prohibited content.
12. Report counts, denominator, success rate, totals, timestamps, identities, configuration,
    pricing, per-case outcomes, usage, and artifact references validate as one internally
    consistent typed record.
13. `tracefix repair`, its seven outcome codes, its safe artifact schema, and the exact
    `tracefix-fake` profile remain compatible. Fake responses do not invent usage or cost.
14. Deterministic tests cover the CLI, configuration, adapter mapping, usage aggregation, cost
    calculation, outcome semantics, partial failure, reporting, publication, cleanup, and secret/
    hidden-data exclusion without a real provider request.
15. Ordinary push/pull-request CI remains secret-free, deterministic, blocking, and live-provider
    independent. Live tests use injected transports and are collected by `python scripts/check.py`.
16. A separate least-privilege, pinned-action, manually dispatched workflow installs `.[dev,live]`,
    validates the platform, builds both images, runs the paid benchmark, uploads safe evidence, and
    fails only for execution/infrastructure/publication failure rather than repair failure.
17. At least one human-authorized manual workflow dispatch against an explicitly selected model
    produces downloadable JSON and Markdown evidence. The measured repair success rate may be
    zero; the workflow need only execute without infrastructure failure.
18. Formatting, linting, strict typing, dependency integrity, focused unit/integration tests,
    applicable Docker tests, the full suite, canonical validation, installed CLI smoke, workflow
    review, and diff checks pass under Python 3.14.
19. README and progress documentation receive only the focused Task 0.1.11a updates. Governing
    documents, prior specifications, fixture/evaluator assets, Docker security contracts, and this
    approved specification remain unchanged during implementation.
20. No v0.2/v1.0 behavior, second provider, scheduled benchmark, statistical reporting, unrelated
    abstraction/dependency, alternate runtime, test weakening, commit, or push is included.

## Assumptions Requiring Human Review

1. **First live provider:** approve `openai` as the only Task 0.1.11a live adapter. The execution
   plan requires a real provider but does not name one; adding a second adapter is out of scope.
2. **SDK and API:** approve the official OpenAI Python SDK as an optional `live` extra with proposed
   range `openai>=2,<3`, using the Responses API and strict structured output. The exact range must
   be checked against Python 3.14 and the selected account/model immediately before approving the
   specification because SDK availability is time-sensitive.
3. **Model selection:** approve requiring the human dispatcher to supply `MODEL_NAME` with no
   default. The execution plan does not select a model, and silently tracking a moving alias would
   make reports less reproducible.
4. **Credential contract:** approve `OPENAI_API_KEY` as the sole live credential and GitHub Actions
   secret name. Organization/project identifiers, if the selected account requires them, need a
   separate explicit spec revision rather than ambient pass-through.
5. **Pricing contract:** approve required operator-supplied input/output USD-per-million-token
   rates and the two-rate Decimal formula. Provider pricing is not treated as stable, dynamically
   fetched, or exact billed cost; cached/reasoning/batch discounts are not modeled in v0.1.
6. **Latency meaning:** approve `model_latency_seconds` as the sum of trusted wall-clock durations
   for planning and generation calls actually made, not total case duration or provider-reported
   server latency.
7. **Usage transport:** approve a minimal typed call-usage extension/measurement boundary around
   `ModelProviderResponse`. The fake provider retains null usage; benchmark reporting can record
   completed live-call usage even when the graph terminates before candidate evaluation.
8. **Report location and formats:** approve paired
   `.tracefix/benchmarks/<benchmark_run_id>/report.json` and `report.md` outputs, with JSON canonical
   and existing per-case `.tracefix/artifacts` referenced rather than copied.
9. **Outcome classification:** approve policy, static, candidate, and malformed-model outcomes as
   valid repair failures; approve baseline-not-reproducible as a platform execution failure. The
   execution plan states the high-level distinction but does not enumerate every existing route.
10. **Fail-fast behavior:** approve stopping paid/model work after the first execution failure and
    marking the remaining cases `not_run`. This bounds cost but means infrastructure-failed reports
    may not contain attempts for all five cases.
11. **Manual acceptance evidence:** approve requiring one human-authorized `workflow_dispatch` run
    before implementation completion. Repair success is not required, but credential/provider,
    platform, reporting, and artifact upload must execute successfully.
12. **Workflow inputs and retention:** approve manual inputs for model, timeout, and current prices,
    plus normal GitHub Actions artifact retention. No result is committed, published externally, or
    made a required ordinary status check in this task.
