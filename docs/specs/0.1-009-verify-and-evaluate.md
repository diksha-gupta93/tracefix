# Task 0.1.9 — Sandbox Verification and Candidate Evaluation

## 1. Goal

Implement the two bounded operations required by Task 0.1.9 for one statically validated v0.1
candidate:

1. verify the candidate inside the hardened Docker sandbox, in order, against the original
   targeted visible test, the full visible suite, and the trusted hidden regression tests; and
2. calculate a strict deterministic candidate evaluation containing the functional outcome, patch
   size, sandbox duration, and optional model-usage measurements that are already available.

This task establishes typed callable Node 9 and Node 10 behavior only. It does not assemble the
LangGraph workflow, route terminal outcomes, expose a CLI, write a run artifact, provide a fake or
live model adapter, aggregate benchmark reports, or introduce repair retries.

## 2. Context

Task 0.1.8 publishes a candidate only after exact patch application, changed-file validation,
Python compilation, AST parsing, Ruff, strict mypy, and Bandit pass. Its passing
`StaticValidationResult` contains a `ValidatedCandidate` with an absolute candidate repository path
and versioned SHA-256 fingerprint. A static pass is a prerequisite, not proof that the original
failure is fixed or that the candidate has no regression.

The trusted benchmark loader from Task 0.1.2 provides visible-test paths, hidden-test paths, and
reference-patch metadata. Hidden tests and reference patches live outside the repository snapshot
and are absent from model-safe context. Task 0.1.4 established that the original targeted failure
means all paths declared by `manifest.visible_tests`, in manifest order. The current five cases
each declare one visible test file.

The existing `SandboxRunner` provides the hardened pytest execution controls required by Tasks
0.1.3a–0.1.3c. Its ordinary repository input contains no evaluator material. Hidden verification
therefore needs a typed trusted adapter path that supplies only validated hidden-test files to the
container without copying them into the candidate or mounting the case's evaluator directory or
reference patch. The existing baseline and static runner contracts must remain unchanged.

The architecture requires verification in increasing scope:

1. original targeted failing test;
2. full visible test suite;
3. hidden regression tests.

A normal nonzero pytest result is a failed repair candidate. A timeout, OOM termination, sandbox
validation/execution/cleanup failure, malformed result, candidate-integrity failure, or trusted
evaluator-boundary failure is an infrastructure diagnostic and must not be counted as a functional
repair failure.

The current `TestResult` and `EvaluationResult` schemas are intentionally small and cannot express
the complete ordered verification and infrastructure evidence needed here. Task 0.1.9 may add
strict task-specific Pydantic models. It must not silently change the meaning of the existing
schemas or wire them into `LocalRepairCaseState`; state integration belongs to Task 0.1.10a.

The current model-provider response contains no latency, token, or cost fields. Candidate
evaluation must therefore accept an optional typed model-usage measurement supplied by an upstream
caller, preserve available values, and represent unavailable values explicitly as `null`. It must
not infer token usage from configured limits, query provider pricing, or add provider-specific
logic.

## 3. In Scope

### 3.1 Typed verification contracts

- Add strict, frozen Pydantic v2 contracts for:
  - `VerificationStage` with the fixed order `targeted`, `visible_suite`, `hidden_suite`;
  - per-stage status: `passed`, `failed`, `not_run`, or `infrastructure_error`;
  - overall verification outcome: `passed`, `candidate_failed`, or
    `infrastructure_diagnostic`;
  - safe verification diagnostic codes and constant messages;
  - one per-stage result;
  - one complete verification result; and
  - one request containing the case identity, passing static-validation result, and an explicitly
    supplied private verification-workspace root.
- Require exactly three stage results in enum order. Later stages that were not eligible to run
  must be present as `not_run` with a prerequisite diagnostic.
- Preserve only bounded safe evidence from sandbox execution:
  - stage;
  - stage status;
  - sandbox completion where execution produced one;
  - exit code where valid;
  - stdout/stderr truncation flags;
  - nonnegative finite duration; and
  - a safe constant diagnostic where applicable.
- Do not retain stdout, stderr, traceback text, exception text, source text, hidden-test names,
  hidden-test paths, absolute host/container paths, or environment values in public verification
  results.
- Revalidate public models at service boundaries so mutated or subclassed inputs cannot bypass
  strict validation.

### 3.2 Verification prerequisites and integrity

- Accept only `StaticValidationOutcome.PASSED` with exactly one valid `ValidatedCandidate` and no
  static diagnostic. Candidate-failed or infrastructure static outcomes must be rejected before
  Docker interaction.
- Load the requested case only through the injected trusted benchmark loader.
- Require the request `case_id` to match the loaded manifest case ID.
- Revalidate the candidate repository as an absolute contained ordinary directory and require its
  current fingerprint to equal `ValidatedCandidate.fingerprint`:
  - before the first sandbox run;
  - between every sandbox run; and
  - after the final run or failure mapping.
- Treat candidate mutation, replacement, aliasing, unsafe entry types, or fingerprint mismatch as
  a blocking infrastructure diagnostic.
- Verification receives read-only ownership of the Task 0.1.8 candidate. It must never modify,
  move, delete, or transfer ownership of that candidate. Cleanup of a successful static candidate
  remains the later workflow owner's responsibility.

### 3.3 Ordered sandbox verification

- Execute no more than the following three stages and always in this order:
  1. **Targeted:** run exactly all manifest-declared visible-test paths in manifest order, using
     the candidate repository and the fixed `python -m pytest <paths...>` command.
  2. **Visible suite:** after targeted success, run `python -m pytest` with no candidate-controlled
     command or flag, so pytest collects the complete visible suite from the candidate repository.
  3. **Hidden suite:** after visible-suite success, run exactly the trusted hidden-test files from a
     separately prepared evaluator bundle while the candidate remains the working repository.
- A stage passes only when sandbox completion is normal and pytest exits `0`.
- A stage is a candidate failure only when sandbox completion is normal and pytest exits nonzero.
- Stop after the first candidate failure. Mark every later stage `not_run`.
- Stop after the first infrastructure diagnostic. Mark every later stage `not_run`.
- A passing overall verification requires all three stages to pass.
- A `candidate_failed` overall result requires exactly one earliest normally completed failed
  stage, no infrastructure-error stage, and all later stages `not_run`.
- An `infrastructure_diagnostic` overall result requires an infrastructure-error stage or a
  pre-execution input/integrity/evaluator failure. It must never be converted into
  `candidate_failed`.

### 3.4 Trusted hidden-test bundle and sandbox adapter

- Add a typed verification sandbox boundary separate from the existing baseline runner's public
  command surface.
- Reuse the existing project-owned `tracefix-sandbox:0.1.3a` Python 3.14/pytest image. Do not change
  its tag, Dockerfile, entrypoint behavior for existing callers, or existing `SandboxRunner` tests.
- The verification adapter may override the image entrypoint only with a TraceFix-owned fixed
  argument vector required to support the hidden-test mount. Neither benchmark metadata, model
  output, repository content, nor callers may provide an entrypoint, executable, pytest option,
  shell fragment, or arbitrary command.
- For visible stages, expose only the validated candidate repository as the existing read-only
  input mount.
- For the hidden stage:
  - create a fresh private host bundle beneath the validated verification-workspace root;
  - copy only the loader-validated hidden-test ordinary-file bytes into deterministic
    TraceFix-owned names in that bundle;
  - do not copy the evaluator directory, manifest, reference patch, or unrelated case files;
  - mount the bundle read-only at a fixed container path separate from the writable candidate
    copy;
  - pass only fixed container paths generated by the adapter to pytest; and
  - remove the host bundle on every success, candidate failure, infrastructure failure, and
    process-control path where safe cleanup is possible.
- Hidden tests must remain on a read-only container mount. Candidate code may execute alongside
  them but must not be able to replace, remove, or rewrite their files.
- Preserve all existing sandbox controls: Linux container, numeric non-root user, no network,
  read-only root filesystem, explicit tmpfs only, CPU/memory/PID/time/output limits, dropped
  capabilities, `no-new-privileges`, required seccomp, fixed allowlisted environment, unique
  container name, bounded Docker CLI output, and forced removal on every outcome.
- Do not mount the Docker socket, project root, benchmark root, whole case directory, evaluator
  directory, reference patch, developer home, credentials, Docker configuration, application/model/
  GitHub secrets, or proxy variables.
- Access Docker only through a typed injected adapter. Do not invoke a shell.

### 3.5 Candidate evaluation

- Add a pure deterministic evaluator that consumes:
  - the case ID;
  - the exact `PatchProposal` associated by the caller with the passing static result;
  - the complete verification result; and
  - optional typed aggregate model-usage measurements.
- Add strict frozen evaluation contracts containing:
  - functional status: `passed`, `failed`, or `not_evaluated`;
  - normalized deterministically ordered files changed;
  - total lines added;
  - total lines removed;
  - total sandbox execution duration;
  - model latency where available;
  - input tokens where available;
  - output tokens where available; and
  - estimated cost in USD where available.
- Derive files and line counts by strictly reparsing `PatchProposal.unified_diff` with the existing
  inert parser. The proposal path set and parsed diff path set must match exactly. Count added and
  removed hunk lines separately; do not count headers, context, or no-newline markers.
- Define total sandbox duration as the sum of durations for verification stages that actually
  produced sandbox evidence. Do not include baseline, static-check, model, queue, or end-to-end
  time.
- Map verification `passed` to functional `passed`, `candidate_failed` to functional `failed`, and
  `infrastructure_diagnostic` to `not_evaluated`.
- Optional model measurements must use strict nonnegative finite numeric values and strict
  nonnegative integer token counts. Estimated cost must use a finite nonnegative `Decimal` value
  denominated explicitly in USD; it must serialize deterministically without binary-float cost
  rounding.
- Preserve supplied measurements exactly after validation. Missing measurements remain `null`.
  Zero is a valid observed value and must not be treated as missing.
- The evaluator must perform no filesystem, Docker, environment, network, provider, pricing, or
  clock access.
- Evaluation failure caused by malformed inputs is a typed diagnostic or domain error and must not
  fabricate a candidate result.

### 3.6 Dependency injection and tests

- Inject the trusted case loader, candidate fingerprinter/filesystem boundary, verification
  sandbox boundary, evaluator-bundle filesystem boundary, and identifier factory or clock where
  used.
- Unit tests must exercise all logic without Docker through typed fakes.
- Docker integration tests must execute the existing fixture-shaped candidates only through the
  real hardened verification adapter.
- Add tests for every new model, result invariant, execution branch, metric calculation, security
  boundary, cleanup path, and failure mapping specified here.

## 10. Security Considerations

- Treat the candidate repository, proposal, static result, manifest values, test output, Docker
  output, and model measurements as untrusted. Revalidate typed values and filesystem identities at
  every external boundary.
- A verified candidate must originate from a currently valid passing Task 0.1.8 result. There is no
  override for candidate-failed, infrastructure, malformed, missing, or stale static evidence.
- Generated/candidate code must never execute on the host. Host code may validate, copy, hash, and
  compare inert bytes only. Pytest and all imports, fixtures, hooks, and candidate code execute only
  in the hardened Linux container.
- Hidden tests are trusted evaluator input but protected content. Copy only declared hidden-test
  files into a private bundle, mount that bundle read-only, never mount the whole evaluator tree,
  and never include reference-patch bytes.
- Candidate code may observe hidden tests while they execute in the isolated no-network container;
  it must not receive their content through model context, public verification/evaluation results,
  raw logs, or later retry input. Raw hidden output must be discarded before crossing the sandbox
  adapter boundary used by business logic.
- Public diagnostics and assertions must use safe constants. Do not expose raw stdout/stderr,
  traceback/source lines, hidden file names, exception strings, Docker output, absolute paths,
  environment variables, prompts, responses, credentials, or secrets.
- Preserve non-root execution, no network, read-only root, explicit tmpfs, resource and output
  bounds, dropped capabilities, `no-new-privileges`, seccomp, fixed environment, unique container
  identity, and unconditional cleanup. Never use `seccomp=unconfined`.
- Do not mount application, model-provider, GitHub, proxy, Docker, or developer credentials; home
  directories; the Docker socket; the project/benchmark root; or arbitrary caller paths.
- Candidate-controlled repository configuration and pytest hooks remain untrusted code and execute
  only inside the sandbox. Callers cannot supply pytest options, environment overrides, plugins,
  commands, or entrypoints through this task's public interfaces.
- Verify candidate fingerprint integrity before, between, and after runs. Any uncertainty, race,
  replacement, or mutation blocks success.
- Hidden bundle cleanup is mandatory. Cleanup failure is a visible infrastructure diagnostic and
  cannot be downgraded because tests passed or failed.
- Estimated cost is evidence supplied by a trusted upstream measurement boundary, not executable
  pricing configuration. Never evaluate expressions, fetch pricing, or read provider credentials
  while evaluating a candidate.
- Structured logs added by this task must be JSON and include `case_id`; logs must contain only the
  same bounded safe metadata permitted in public results. No new logging framework is required.

## 11. Failure Cases

The implementation must fail closed with stable typed evidence for at least:

- wrong runtime type, subclass, Pydantic-invalid/mutated request, static result, candidate,
  fingerprint, sandbox result, verification result, proposal, or usage measurement;
- non-passing, inconsistent, empty, malformed, or stale static-validation result;
- missing, malformed, mismatched, or unloadable case ID/manifest;
- candidate path missing, relative, protected, aliased, replaced, moved, not a directory, unsafe,
  changed since static validation, or mismatched to its recorded fingerprint;
- candidate mutation or fingerprint change before, between, or after sandbox stages;
- invalid visible-test declaration, missing target file, target escape, unsafe path, or target not
  present in the candidate;
- missing/empty hidden-test declaration, hidden test outside the evaluator boundary, wrong entry
  type, symlink/junction/reparse point, hard-link alias, special file, duplicate/case alias, read
  failure, or source mutation while bundling;
- invalid/protected verification-workspace root, candidate/workspace overlap, destination escape,
  generated-name collision, bundle creation/copy/hash failure, or cleanup failure;
- attempted inclusion or mount of manifest, evaluator directory, reference patch, benchmark root,
  project root, home, credential path, Docker socket/configuration, or undeclared file;
- sandbox command/entrypoint/environment/mount injection or arbitrary pytest option;
- Docker CLI/daemon unavailable, non-Linux daemon, missing seccomp, prohibited unconfined seccomp,
  missing image, create/start/inspect/wait/kill/remove failure, malformed Docker evidence, runner
  crash, or container cleanup failure;
- timeout, OOM termination, output truncation metadata inconsistency, malformed exit code, malformed
  `SandboxResult`, negative/non-finite duration, or impossible completion/exit combination;
- normal nonzero targeted result, with visible and hidden stages not run;
- targeted success followed by normal nonzero visible-suite result, with hidden stage not run;
- targeted and visible success followed by normal nonzero hidden result;
- proposal/diff path mismatch, malformed diff, ignored/unsupported diff content, duplicate/case-aliased
  paths, or invalid line accounting;
- negative, boolean-coerced, non-integral, non-finite, oversized, or otherwise malformed duration,
  latency, token, or cost measurements;
- verification/functional-status mismatch or duration total inconsistent with stage evidence.

Normal pytest nonzero results are candidate failures, not infrastructure exceptions. Sandbox,
Docker, evaluator-boundary, filesystem-integrity, protocol, timeout, OOM, malformed-result, and
cleanup failures are infrastructure diagnostics, not failed repair attempts. `KeyboardInterrupt`
and `SystemExit` must not be converted into ordinary candidate or infrastructure results; best-
effort container/bundle cleanup must occur before they propagate.

## 12. Acceptance Criteria

1. One typed verification service accepts only a passing Task 0.1.8 candidate and uses injected
   trusted-loader, fingerprint/filesystem, and sandbox boundaries.
2. Candidate identity and fingerprint are revalidated before, between, and after stages; the
   candidate and prepared benchmark snapshot remain byte-identical throughout verification.
3. The service runs the manifest-declared targeted visible tests first, the complete visible suite
   second, and trusted hidden tests third, with no later stage executed after a failure.
4. All three stages pass only on normal exit `0`. A normal nonzero exit maps to candidate failure;
   timeout, OOM, sandbox/Docker/protocol, integrity, evaluator, and cleanup failures map distinctly
   to infrastructure diagnostics.
5. Hidden execution mounts only a fresh validated read-only bundle of declared hidden-test files.
   It never mounts or copies a reference patch, manifest, whole evaluator directory, benchmark
   root, project root, or credentials.
6. All candidate code and pytest behavior execute only in fresh hardened Linux containers with the
   existing network, user, filesystem, capability, seccomp, resource, output, environment, and
   cleanup controls.
7. Verification results contain exactly three ordered typed stage entries, deterministically mark
   nonexecuted prerequisites, serialize round-trip, and expose no raw output, hidden material,
   secrets, exception text, or absolute paths.
8. The candidate evaluator deterministically reports functional status, normalized changed files,
   separate added/removed line counts, and the sum of executed verification-stage durations.
9. Available model latency, input/output token, and USD cost measurements are validated and
   preserved; unavailable measurements are `null`, and no provider/pricing lookup or estimate is
   fabricated.
10. Real Docker integration tests demonstrate the full pass path for at least two distinct seeded
    cases and a full candidate-fail path for at least two distinct seeded cases.
11. Integration or focused boundary tests demonstrate targeted failure, a visible regression after
    targeted success, hidden-test failure after visible success, and sandbox infrastructure
    failure mapping.
12. Unit tests independently trigger every stage status, overall outcome, diagnostic mapping,
    metric calculation, malformed input, integrity failure, hidden-bundle failure, and cleanup
    path.
13. Existing preparation, benchmark isolation, sandbox, planning, policy, static-validation, and
    security behavior remains unchanged and passing. The baseline runner and both existing image
    contracts remain compatible.
14. Formatting, linting, strict typing, dependency integrity, focused unit/integration tests, the
    full suite, canonical validation, and diff checks pass under Python 3.14.
15. No graph/routing, CLI/artifact, fake/live provider, benchmark aggregation, retry, persistence,
    API, GitHub, observability, adjacent/future behavior, unrelated dependency, commit, or push is
    introduced.

## 15. Definition of Done

- A passing static candidate is verified in the fixed targeted → visible-suite → hidden-suite order
  only inside the hardened sandbox, with deterministic short-circuiting and integrity checks around
  every run.
- Hidden tests are supplied through a fresh private read-only bundle containing only declared test
  files; evaluator directories, manifests, reference patches, source benchmark roots, secrets, and
  host-sensitive paths are never mounted or disclosed.
- Passing, functional candidate failure, and infrastructure diagnostic are strict distinct typed
  outcomes. Every result contains exactly three ordered stage entries and safe bounded evidence;
  no raw test output or hidden content crosses the business-logic boundary.
- Candidate evaluation deterministically reports functional outcome, files changed, lines added,
  lines removed, sandbox duration, and validated optional model latency/token/cost values without
  external access or fabricated data.
- At least two seeded cases demonstrate the full real-Docker pass path, at least two demonstrate a
  full candidate-fail path, and targeted, regression, hidden-failure, and infrastructure mappings
  have explicit test evidence.
- Every schema invariant, stage branch, integrity check, evaluator-bundle path, Docker security
  control, cleanup branch, failure classification, and metric calculation has focused unit or
  integration coverage.
- Existing benchmark isolation, preparation, baseline, sandbox, planning, policy, and static-check
  contracts remain passing and neither existing image contract is weakened.
- All Section 13 quality gates pass in the existing Python 3.14 environment. Ordinary CI requires
  no secrets or live provider and runs applicable real-Docker tests.
- README and progress documentation are updated during implementation; governing documents and the
  approved specification remain unchanged.
- No Task 0.1.10+ behavior, unrelated abstraction/dependency, alternate runtime, commit, or push is
  included.
- The implementation completion report lists files changed, commands executed, test results,
  acceptance evidence, architecture decisions, security controls, assumptions, and remaining
  risks/deferred work.

## Assumptions Requiring Human Review

1. **Targeted-test meaning:** approve retaining Task 0.1.4's interpretation that the “original
   targeted failing test” is every `manifest.visible_tests` path in manifest order. The present
   corpus has one path per case.
2. **Full-visible-suite command:** approve `python -m pytest` with no caller/model-supplied flags for
   the full visible stage. The v0.1 fixture repositories contain only visible tests under their
   repository snapshots; evaluator-only hidden tests remain outside them.
3. **Hidden-test execution boundary:** approve a dedicated typed verification adapter that reuses
   `tracefix-sandbox:0.1.3a` but supplies a private hidden-only bundle on a separate read-only mount
   through a fixed TraceFix-owned entrypoint override. Existing `SandboxRunner` behavior and image
   entrypoint for baseline callers remain unchanged.
4. **Runtime hidden-test visibility:** approve allowing candidate code to observe hidden tests only
   during isolated no-network execution. Their files are read-only, their raw output is discarded,
   and no hidden content is returned to models or public results. Stronger secrecy from executing
   candidate code is not possible while using hidden tests to evaluate that code in the same
   process/container.
5. **Stage short-circuiting:** approve stopping at the first normal test failure or infrastructure
   diagnostic and representing later stages as typed `not_run` results. This implements “in
   increasing scope” without spending resources or exposing hidden tests after a known failure.
6. **Timeout and OOM classification:** approve treating timeout and memory-limit termination as
   infrastructure diagnostics, consistent with the existing baseline/static contracts, rather
   than counting them as functional candidate failures. Later routing/retry policy remains out of
   scope.
7. **Safe verification evidence:** approve discarding raw stdout/stderr for every candidate stage,
   especially hidden verification, while retaining completion, exit, truncation, duration, stage,
   and safe diagnostic metadata. This protects hidden content and secrets but gives later routing
   less failure detail.
8. **Model-usage handoff:** approve optional aggregate `model_latency_seconds`, `input_tokens`,
   `output_tokens`, and `estimated_cost_usd` input to the pure evaluator. Task 0.1.9 does not alter
   the Task 0.1.6 provider protocol to produce those measurements; fake/live provider wiring may
   supply them in later tasks, and unavailable values remain `null`.
9. **Cost representation:** approve finite nonnegative `Decimal` USD values serialized
   deterministically. This task does not choose a provider price source, currency-conversion rule,
   or historical pricing policy.
10. **Proposal/static-result pairing:** approve retaining the existing orchestrator invariant that
    the proposal passed to evaluation is the proposal that produced the passing static result.
    Task 0.1.8 does not embed a proposal digest in `StaticValidationResult`; Task 0.1.9 reparses and
    validates the proposal but does not revise the prior result schema solely to add that linkage.
11. **Candidate ownership:** approve read-only use of the published candidate and mandatory cleanup
    only for Task 0.1.9's private hidden-test bundle. Candidate and prepared-workspace cleanup stays
    with the later workflow owner after routing/artifact creation.
