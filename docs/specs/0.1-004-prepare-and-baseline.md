# Task 0.1.4 — Prepare Repository and Run Baseline Nodes

## 1. Goal

Implement the two bounded workflow operations required by Task 0.1.4:

1. prepare one trusted development benchmark case in a fresh isolated workspace, validate and
   record its requested revision identity, and compute a deterministic repository fingerprint; and
2. execute only that case's declared visible failing tests through the existing hardened Docker
   sandbox, retaining complete typed baseline evidence and producing a terminal diagnostic outcome
   when the reported failure is not reproducible.

This task establishes callable node-level behavior only. It does not assemble a LangGraph graph,
invoke a model, classify a failure, select model context, generate or apply a patch, or expose a CLI.

## 2. Context

Task 0.1.2 introduced five trusted development cases and a loader that validates manifests,
repository paths, visible tests, evaluator-only hidden tests, and reference patches. Tasks 0.1.3a
through 0.1.3c introduced a typed Docker adapter and sandbox runner that validate a prepared host
repository and execute strictly constrained pytest paths with non-root execution, no network,
read-only root filesystem, bounded writable locations, resource/output limits, default seccomp,
fixed environment variables, and guaranteed container cleanup.

The canonical architecture orders repository preparation before baseline execution. Baseline
execution must happen before any model operation, because a passing baseline is evidence that the
reported failure is not reproducible and must terminate the repair path.

The current benchmark manifests contain symbolic `base_revision` and `failing_revision` values,
but the repository snapshots contain no `.git` directory, Git bundle, or commit objects. For this
task, “checkout” therefore means materializing the validated repository snapshot associated with
the manifest's exact `failing_revision` into a new workspace and recording both that declared
revision and a content-derived fingerprint. It must not pretend that the symbolic value is a Git
SHA. Introducing real fixture history or changing the fixture format requires human approval; see
the assumptions at the end of this specification.

## 3. In Scope

- Add typed preparation and baseline interfaces under `app/agent/` without adding graph assembly.
- Load a case through the trusted benchmark loader; do not bypass or duplicate its validation.
- Require the requested revision to match the case's declared `failing_revision` exactly.
- Create a fresh caller-owned or preparer-created workspace beneath an explicitly supplied,
  validated workspace root.
- Copy only the validated repository snapshot into the isolated workspace without following links
  or allowing source/destination escape.
- Reject an absent requested revision, an unsupported revision, an invalid workspace root, an
  existing/non-empty destination, aliases/reparse points, and any containment or filesystem
  inspection failure.
- Record the case ID, requested revision, revision kind, absolute prepared repository path, and
  deterministic repository fingerprint in a frozen typed result.
- Compute the fingerprint from a documented canonical stream containing normalized relative POSIX
  paths, entry type, file length, and raw file bytes in deterministic path order. Use SHA-256 and a
  versioned fingerprint prefix. Do not include absolute paths, timestamps, ownership, permissions,
  workspace names, cache files, or other host-specific metadata.
- Preserve bytes exactly when copying. Reject filesystem entry types other than ordinary
  directories and regular files.
- Derive sandbox test arguments only from the trusted case's visible-test paths, expressed relative
  to the prepared repository.
- Execute the baseline exclusively with the existing `SandboxRunner` boundary and its security
  defaults. Dependency installation or any pytest execution on the host is prohibited.
- Map the `SandboxResult` into typed baseline evidence without discarding completion status,
  nullable exit code, stdout/stderr, truncation flags, or duration.
- Distinguish these outcomes explicitly:
  - reproduced failure: normal sandbox completion with a nonzero pytest exit code;
  - not reproducible: normal sandbox completion with exit code zero;
  - infrastructure diagnostic: timeout, memory-limit termination, sandbox validation/execution
    failure, or an invalid/malformed execution result.
- On an unexpected pass, return a terminal typed diagnostic artifact containing case ID, commit
  identity, fingerprint, baseline evidence, a stable diagnostic code, and a human-readable message.
- Make the baseline result usable to populate `LocalRepairCaseState.baseline_result`, while adding
  only the minimum typed structures needed to retain sandbox completion/truncation and preparation
  evidence that the existing `TestResult` cannot represent.
- Use dependency injection for the benchmark loader, workspace/filesystem preparation boundary, and
  sandbox runner so unit tests do not require Docker or mutate real benchmark fixtures.
- Add unit and applicable Docker integration tests for every behavior introduced here.

## 4. Out of Scope

- Real Git clone/fetch, creation or rewriting of fixture Git history, GitHub access, mutable branch
  handling, or immutable pull-request SHA validation.
- Checkout of `base_revision`; patch generation begins from the declared failing revision only.
- LangGraph dependency installation, graph construction, routing, checkpoints, persistence, worker
  queues, FastAPI, Redis, PostgreSQL, or a CLI.
- Failure classification and model-context selection from Task 0.1.5.
- Model providers, prompts, repair plans, patch generation, patch policy, static checks, candidate
  verification, hidden-test execution, evaluation, or artifacts for later tasks.
- Exposing hidden tests or reference patches to a model-safe view or copying evaluator-only files
  into the prepared repository.
- Installing project dependencies in the workspace or sandbox, resolving lock files, or enabling
  sandbox networking.
- Changing sandbox limits, command policy, image behavior, security controls, or cleanup semantics.
- Supporting arbitrary repositories, languages, test runners, commands, or multiple repair attempts.
- Updating the canonical architecture unless implementation reveals a new decision that must first
  receive human approval.

## 6. Python and Packaging Requirements

  extra fields, and be frozen where mutation is not part of their contract.
- All public and internal interfaces must be fully typed. Do not use `Any` or pass implicit untyped
  dictionaries across module boundaries.
- Prefer standard-library `pathlib`, `hashlib`, `shutil`, and explicit binary I/O. Do not use shell
  string construction.
- Do not add a runtime or development dependency unless the requirements cannot be met with the
  existing dependencies; any proposed dependency requires explicit human review.
- Keep the existing setuptools package discovery and project metadata unless a demonstrated import
  problem requires a separately reviewed packaging change.
- Do not add LangGraph in this task; these are ordinary typed functions/services that later graph
  assembly can call.
- If a Git-backed interpretation is approved instead, access Git through a typed injected adapter,
  invoke it with argument sequences rather than a shell, and record the resolved full commit SHA.

## 8. Cross-Platform Requirements

- Preparation and fingerprinting must behave identically on supported Windows and Linux developer
  hosts. Use `pathlib` for host paths and canonical POSIX relative paths in fingerprints and typed
  identities.
- Reject absolute paths, `..`, empty or dot components, drive-relative paths, UNC/device paths,
  alternate separators used to disguise traversal, and case-insensitive aliases where relevant.
- Reject symlinks on every platform and Windows junctions/reparse points before and during copying;
  fail closed when an entry cannot be inspected reliably.
- Validate that the resolved workspace destination remains strictly below the approved workspace
  root and is distinct from the benchmark source, repository root, developer home, `.git`, Docker
  sockets/configuration, credential paths, and existing sandbox-protected roots.
- Do not depend on Unix-only copy flags, inode semantics, file modes, shell commands, or line-ending
  conversion. Hash and copy raw bytes.
- Fingerprints for identical repository bytes and relative paths must match across Windows and
  Linux despite different absolute workspace paths and path separators.
- Windows commands use `.venv\Scripts\python.exe`; POSIX uses `.venv/bin/python`. The portable
  documented command remains `python scripts/check.py` from an activated environment.
- Docker integration tests require a usable Linux-container daemon. Local skips are permitted only
  under the repository's existing daemon-unavailable policy and must be reported; CI must execute
  the integration tests.

## 10. Security Considerations

- Treat benchmark repository content as untrusted. Host-side preparation may inspect and copy bytes
  but must never import, execute, compile, test, or invoke repository code.
- All baseline code execution must use the existing hardened `SandboxRunner`; preserve every
  network, user, mount, environment, filesystem, capability, seccomp, resource, output, and cleanup
  control from Task 0.1.3c.
- Only the prepared repository may be passed to the sandbox. Never mount the benchmark corpus,
  evaluator directory, project root, workspace root, home directory, `.git`, Docker socket, secrets,
  credentials, or model-provider configuration.
- The preparation boundary must fail closed on traversal, link/reparse-point entries, special files,
  destination collision, source mutation detected during copying/fingerprinting, or uncertain path
  identity. Validate before use and revalidate the materialized tree before returning it.
- Use collision-resistant SHA-256 with unambiguous length-delimited canonical encoding. A
  fingerprint identifies prepared content; it is not a signature or proof that the content is safe.
- Do not log or include absolute host paths, file contents, environment variables, or credentials in
  diagnostics. In v0.1, structured logs added by this task must include `case_id`; no logging
  framework expansion is required.
- Hidden tests and reference patches remain evaluator-only and must not enter the prepared checkout
  or baseline command.
- An unexpected pass is a terminal safety outcome. No downstream callable supplied by this task
  may invoke a model, and tests must prove the terminal result requires no model dependency.

## 11. Failure Cases

The implementation must produce typed, stable errors or diagnostic outcomes for at least:

- unknown, malformed, or unloadable case ID;
- malformed manifest or unsafe benchmark path rejected by the existing loader;
- missing requested revision, empty revision, or a revision other than exact `failing_revision`;
- absence of a materializable repository snapshot for the declared failing revision;
- missing, non-directory, protected, aliased, inaccessible, or otherwise invalid workspace root;
- destination escape, source/destination overlap, pre-existing or non-empty destination;
- traversal, absolute/drive/UNC/device path, symlink, junction/reparse point, special file, filesystem
  inspection error, copy error, or source mutation;
- fingerprint failure or nondeterministic/colliding canonical entry representation;
- a declared visible test that is absent from or escapes the prepared repository;
- sandbox validation, execution, timeout, memory-limit, malformed-result, or cleanup failure;
- normal pytest exit zero, represented as `baseline_not_reproducible` with complete evidence;
- normal pytest nonzero exit, represented as reproduced baseline evidence rather than an
  infrastructure exception;
- truncated stdout/stderr, retained with the existing truncation flags and marker;
- inability to remove a preparer-created failed workspace. The primary and cleanup failures must
  both remain observable, and successful workspaces need an explicit ownership/cleanup contract.

No failure may fall back to host execution, broaden the command, expose evaluator-only material,
invoke a model, or leave a partially prepared repository eligible for baseline execution.

## 12. Acceptance Criteria

1. A typed preparation operation loads each existing trusted case and materializes its declared
   failing snapshot into a fresh contained workspace without modifying the source fixture.
2. The preparation result records case ID, exact declared failing revision, an explicit non-SHA
   snapshot revision kind, prepared path, fingerprint algorithm/version, and SHA-256 digest.
3. Preparation rejects a missing or mismatched revision, invalid workspace, destination collision,
   traversal, aliases/reparse points, unsupported entry types, and inspection/copy failures before
   the result can be used.
4. Fingerprints are stable across repeated preparations and different absolute workspace paths,
   change when a file path or byte changes, and use deterministic POSIX relative-path ordering.
5. The baseline operation supplies only all declared visible test paths to the existing sandbox as
   validated repository-relative pytest arguments; it never supplies hidden tests or reference
   patches.
6. All five seeded cases reproduce their known visible failure in fresh prepared workspaces through
   the real Docker sandbox.
7. Baseline evidence preserves sandbox completion, exit code, stdout, stderr, truncation flags, and
   duration and can populate the existing local repair state without untyped conversion.
8. A normal exit code of zero returns a terminal `baseline_not_reproducible` diagnostic containing
   preparation identity and complete baseline evidence; no model interface is imported or called.
9. Timeout, OOM, sandbox validation/execution, and cleanup failures are distinguished from a
   reproduced test failure and an unexpected pass.
10. Host-side application code never executes fixture code, and all existing Task 0.1.3c sandbox
    controls remain enforced and tested.
11. Unit tests cover preparation, fingerprinting, baseline mapping, unexpected pass, missing commit,
    invalid workspace, and relevant failure/cleanup paths; integration tests cover all five cases.
12. Existing schema, benchmark-loader, sandbox, and adversarial tests remain passing.
13. Formatting, linting, strict typing, unit tests, Docker integration tests, the cross-platform
    validation script, and diff checks pass under the existing Python 3.14 environment.
14. No Task 0.1.5 or later behavior, unrelated dependency, alternative runtime, commit, or push is
    introduced.

## 13. Tests and Validation Commands

Add unit tests covering at minimum:

- successful materialization through an injected trusted-case loader;
- exact requested-to-declared failing revision validation and missing/mismatched revision errors;
- fresh workspace creation and rejection of invalid roots, existing destinations, overlap, escape,
  links/reparse points, special entries, inspection errors, copy errors, and source mutation;
- raw-byte copy preservation and absence of evaluator-only files;
- fingerprint repeatability across different workspace roots, separator-independent canonical
  paths, deterministic ordering, and sensitivity to changed path/content;
- all visible tests converted to safe prepared-repository-relative pytest paths in manifest order;
- sandbox dependency injection and proof that no host pytest/subprocess execution occurs;
- reproduced failure, unexpected pass, timeout, memory-limit, truncation, sandbox exception, and
  cleanup-failure mapping;
- complete typed serialization/validation of new result and diagnostic structures;
- proof that the unexpected-pass path has no model dependency or continuation callback.

Add Docker integration tests covering at minimum:

- prepare and run the declared visible baseline for each of the five development cases;
- assert normal sandbox completion and nonzero pytest exit for every known failing snapshot;
- assert prepared repositories are distinct temporary copies and source fixtures remain unchanged;
- preserve the existing local daemon skip policy while requiring execution in ordinary CI.

Run from the repository root with the existing environment:

```text
.venv\Scripts\python.exe --version

docker info --format "{{json .SecurityOptions}}"
docker build --tag tracefix-sandbox:0.1.3a --file docker/sandbox/Dockerfile .
```

test filenames, substitute those exact files. Docker skips caused by a locally unavailable Linux
daemon must be reported as remaining validation risk; CI must execute the integration tests.

## 15. Definition of Done

- Every in-scope preparation and baseline behavior is implemented through typed, injected
  boundaries and every acceptance criterion has unit, integration, CI, or inspection evidence.
- Each of the five declared failing snapshots is prepared in an isolated temporary workspace,
  receives a deterministic versioned SHA-256 content fingerprint, and reproduces its visible
  failure only inside the hardened Docker sandbox.
- Missing/mismatched revision, invalid workspace, unsafe filesystem entry, copy/fingerprint failure,
  unexpected pass, timeout, OOM, sandbox error, and cleanup failure paths fail closed with typed

  no fixture code executes on the host and no existing sandbox control is weakened.
- All Section 13 quality gates pass in the existing Python 3.14 environment, including ordinary-CI
  execution of the five-case Docker baseline integration test.
- README and progress documentation are updated during implementation; governing documents and the
  approved specification remain unchanged unless a separately approved architecture decision is

## Assumptions Requiring Human Review

1. **Revision semantics:** approve treating each current repository directory as the immutable
   snapshot associated with its manifest's symbolic `failing_revision`, while recording that value
   explicitly as a non-SHA snapshot identity. If literal Git checkout is required, Task 0.1.2's
   fixture representation must first be amended through an approved specification/architecture
   decision to provide real commits or bundles.
2. **Workspace lifecycle:** approve preparer-created, pytest-temporary workspaces for tests and an
   explicit caller-owned cleanup contract after a successful preparation. The preparer cleans up
   only partial destinations it created when preparation fails; a later workflow owner cleans
   successful workspaces after downstream nodes finish.
3. **Baseline test scope:** approve running every path in `manifest.visible_tests` in one sandbox
   invocation. The current five manifests each declare one test file, while this rule remains
   correct if a bounded case later declares multiple visible failing test files.
4. **Unexpected-pass artifact boundary:** approve introducing a minimal typed in-memory diagnostic
   result in this task. Persistent/JSON run artifact writing remains deferred to the later routing
   and CLI task.
5. **State compatibility:** approve minimally extending typed state/result structures when needed to
   retain commit/fingerprint and sandbox completion/truncation evidence; do not overload the current
   `TestResult` in ways that discard evidence or silently change its established meaning.
