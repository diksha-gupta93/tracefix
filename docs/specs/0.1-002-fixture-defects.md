# Task 0.1.2 — Fixture Repository with Five Seeded Defects

## 1. Goal

Create a deterministic development benchmark containing exactly five small Python 3.14 projects
that use `pytest`, each with one seeded defect from the execution plan, and add a typed loader that
validates benchmark metadata without exposing evaluator-only material to future model-context
selection.

This task provides benchmark data and its loading boundary only. It does not execute fixture code,
prepare sandbox workspaces, invoke a model, or implement the repair workflow.

## 2. Context

TraceFix v0.1 operates on seeded local fixtures before GitHub ingestion exists. Task 0.1.2 supplies
the five cases consumed by later repository-preparation, sandbox, workflow, and evaluation tasks.
The system architecture requires visible tests to be usable as repair context while hidden tests,
reference patches, secrets, unrelated files, and generated evaluation artifacts remain excluded.

The benchmark bug taxonomy is metadata and is separate from the runtime `FailureCategory` enum in
`app/agent/schemas.py`. This task must not modify or reuse that runtime enum for benchmark labels.

The repository currently packages only `app` through setuptools. `benchmarks` is a repository-local
typed development package checked by mypy and used directly from the repository checkout; making it
part of the installed TraceFix distribution is not required by this task.

## 3. In Scope

- Add exactly five cases under `benchmarks/development/`, one for each required category:
  1. `incorrect_conditional`
  2. `boundary_condition`
  3. `incorrect_return_value`
  4. `exception_handling`
  5. `fixture_or_mocking`
- Give every case a small, self-contained Python repository snapshot at its failing revision.
- Include visible tests that demonstrate the reported failure and hidden tests that distinguish the
  intended repair from an incomplete or overfitted repair.
- Include, for every case, a manifest with:
  - unique `case_id`;
  - repository snapshot path;
  - base revision identifier;
  - failing revision identifier;
  - visible-test paths;
  - hidden-test paths;
  - issue description;
  - expected behavior;
  - reference-patch path;
  - expected changed files;
  - forbidden changed files;
  - bug category;
  - difficulty;
  - risk level.
- Include evaluator-only reference patches that transform the failing snapshot into the expected
  repair and apply cleanly to that snapshot.
- Add `benchmarks/loader.py` with Pydantic v2 models and typed public loader results.
- Provide distinct loader views for trusted evaluation and model-safe context selection. The
  model-safe view must make hidden-test paths/content and reference-patch paths/content
  unrepresentable, rather than relying on callers to delete dictionary keys.
- Validate all manifest-derived relative paths before returning a loaded case.
- Add unit tests for the loader and deterministic validation tests for the five fixture cases.

## 4. Out of Scope

- Docker images, Docker invocation, sandboxing, or execution of untrusted code in this task's
  loader tests.
- Running fixture code through the future sandbox runner.
- LangGraph nodes, model providers, prompts, context-ranking logic, patch generation, or repair
  attempts.
- CLI commands or evaluation artifact generation.
- GitHub, FastAPI, PostgreSQL, Redis, queues, checkpoints, tracing, or metrics.
- Expanding beyond five cases or adding validation/locked benchmark splits; those belong to v0.2.
- Dependency installation from fixture metadata or arbitrary command execution.
- Changes to `LocalRepairCaseState` or the existing core schemas.
- Packaging each fixture as a separately published Python distribution.
- Adding security tooling, Docker configuration, or unrelated development dependencies.

## 5. Expected Repository Structure

The implementation must use this shape (case slugs may be prefixed with stable numeric ordering):

```text
benchmarks/
├── __init__.py
├── loader.py
└── development/
    ├── incorrect_conditional/
    │   ├── manifest.json
    │   ├── repository/
    │   │   ├── src/<small_package>/...
    │   │   └── tests/test_*.py
    │   └── evaluator/
    │       ├── hidden_tests/test_*.py
    │       └── reference.patch
    ├── boundary_condition/
    │   └── ...
    ├── incorrect_return_value/
    │   └── ...
    ├── exception_handling/
    │   └── ...
    └── fixture_or_mocking/
        └── ...
tests/
└── unit/
    ├── test_benchmark_loader.py
    └── test_benchmark_fixtures.py
```

Each `repository/` is the failing repository snapshot and must not contain evaluator-only files.
Each `evaluator/` directory is outside that snapshot. Manifests are trusted benchmark metadata and
must not be copied into a model-visible repository workspace by this task.

`base_revision` and `failing_revision` are immutable, nonblank revision identifiers recorded in the
manifest. For Task 0.1.2 they are fixture identities, not a requirement to embed nested `.git`
directories or invoke Git. They must differ. Later workspace preparation may map these identities
to materialized Git commits without changing the loader's isolation contract.

Paths stored in a manifest must be POSIX-style relative paths. Visible-test paths and expected or
forbidden changed-file paths are relative to `repository/`. Hidden-test and reference-patch paths
are relative to the case directory and must resolve beneath `evaluator/`.

## 6. Python and Packaging Requirements

- Use the repository's supported CPython range, `>=3.12,<3.13`.
- Use Pydantic v2 for manifest validation and immutable typed boundary models.
- Fully annotate public and internal functions; strict mypy must pass.
- Do not use `Any`, implicit untyped dictionaries, or raw dictionaries across the loader boundary.
- Use `pathlib.Path` for filesystem operations.
- Define explicit enums for the five bug categories and for the selected difficulty and risk
  vocabularies. Enum values must serialize as stable lowercase snake-case strings.
- Models must reject unknown fields, blank semantic strings, unsupported enum values, absolute
  paths, and malformed types.
- Returned collection fields must not permit callers to mutate shared loader state.
- Use only the standard library and the existing Pydantic dependency. Do not add a runtime or
  development dependency.
- Keep `benchmarks` importable from the repository checkout. Do not change setuptools package
  discovery unless implementation proves that CI cannot import it under the existing editable
  installation.
- Fixture projects must be self-contained and require only Python and `pytest`; they must not
  require network access or third-party runtime libraries.

## 7. Development Tool Requirements

- Continue using the existing Ruff, strict mypy, pytest, and `scripts/check.py` configuration.
- Invoke all Python tools with the active environment's interpreter and `python -m` convention.
- On Windows use `.venv\Scripts\python.exe`; on POSIX use `.venv/bin/python`.
- Tests must create malformed or adversarial cases under pytest-managed temporary directories.
  They must not alter the committed benchmark corpus.
- No formatter, linter, type-checker, or test configuration may be weakened.
- The implementation must not install or download another Python runtime.

## 8. Cross-Platform Requirements

- Loader behavior must be identical on Windows and Linux.
- Manifest paths use `/` as the serialized separator and are converted safely with `pathlib`.
- Reject Windows drive-qualified paths, UNC paths, POSIX absolute paths, empty paths, `.` or `..`
  traversal components, and paths whose resolved target escapes its allowed root, including through
  symlinks or junction-like filesystem indirection where resolution exposes the escape.
- Path comparisons used for policy checks must not depend on the host's current working directory.
- Fixture filenames must differ under case-insensitive comparison and avoid Windows-reserved names.
- Fixture source and metadata must be UTF-8 text with LF line endings, consistent with
  `.gitattributes`.
- Tests must not assume a POSIX shell, shell utilities, executable permission bits, or platform-
  specific path separators.

## 9. GitHub Actions CI Requirements

- The existing `ubuntu-latest` Python 3.14 workflow remains the ordinary CI entry point.
- `python scripts/check.py` must discover and run the new loader and fixture validation tests.
- CI must not use model credentials, external services, network-dependent fixture behavior, Docker,
  or live-model evaluation for this task.
- No workflow change is required if the existing workflow exercises all added checks. If a workflow
  change becomes necessary, it must remain minimal, preserve read-only `contents` permission, and
  pin third-party actions by full commit SHA.

## 10. Security Considerations

- Treat all manifest content and paths as untrusted loader input even though the initial corpus is
  committed to the repository.
- Resolve and validate a requested case identifier without interpolating it into an unchecked path.
  Case lookup must reject traversal, absolute paths, separators, and unknown identifiers.
- Never execute fixture source, import fixture modules, invoke pytest, apply patches, invoke Git, or
  spawn subprocesses while loading or validating metadata.
- Keep evaluator-only assets physically outside `repository/` and outside the model-safe return
  type. Model-safe loading must not read their contents as an intermediate convenience.
- Do not accept commands, environment variables, dependency-install instructions, or executable
  hooks from a manifest.
- Reject symlinks or other resolvable links used by declared files to escape the case root or
  repository root.
- Reference patches and hidden tests are protected benchmark assets. Expected/forbidden path
  policy metadata may be available to trusted evaluation code but must not be included in the
  model-safe context view unless a later specification explicitly requires it.
- This task does not authorize running untrusted fixture code on the host. Fixture behavior tests
  may use static inspection and patch parsing; actual baseline and repaired test execution is
  deferred to Docker sandbox tasks.

## 11. Failure Cases

The loader must fail closed with a specific typed/domain exception (preserving the underlying cause
where useful) for at least:

- unknown or syntactically invalid case identifier;
- missing case directory or manifest;
- invalid JSON or non-object manifest root;
- missing, extra, blank, or incorrectly typed fields;
- unsupported bug category, difficulty, or risk value;
- duplicate case IDs in the development corpus;
- manifest `case_id` not matching its containing case directory's declared identity;
- identical base and failing revision identifiers;
- absolute, drive-qualified, UNC, empty, traversal, or escaping paths;
- a declared file that is missing, has the wrong kind, or resolves outside its permitted root;
- visible tests outside `repository/` or not matching a test-file path;
- hidden tests or reference patch outside `evaluator/`;
- evaluator-only content found inside `repository/`;
- overlap between visible and hidden tests;
- duplicate entries, or overlap between expected and forbidden changed files;
- expected/forbidden changed paths that target benchmark metadata, evaluator assets, tests, CI,
  security configuration, or another case;
- a manifest whose bug category does not match the required five-case corpus uniqueness rule.

Errors must not return a partially populated case or fall back to permissive defaults. Error
messages must identify the case and invalid field without including hidden-test or reference-patch
contents.

## 12. Acceptance Criteria

1. Exactly five development cases exist, covering each required defect category exactly once.
2. Every case contains a failing repository snapshot, visible tests, isolated hidden tests, issue
   description, expected behavior, reference patch, expected and forbidden changed-file lists, base
   and failing revision identifiers, difficulty, and risk.
3. Each seeded defect is small and localized; its reference patch changes only expected files and
   changes no forbidden file.
4. Visible tests document the reported failure, while hidden tests add meaningful regression or
   anti-overfitting coverage not duplicated verbatim by visible tests.
5. `benchmarks.loader` returns a fully typed trusted evaluation representation for a valid case.
6. A separate typed model-safe representation includes only model-eligible metadata and repository
   paths/content; its schema has no hidden-test, reference-patch, or trusted policy fields.
7. Model-safe loading neither reads nor returns hidden-test or reference-patch content.
8. Missing cases and malformed manifests fail closed with deterministic exceptions.
9. All declared paths are containment-checked, and adversarial absolute/traversal/escape paths are
   rejected on supported platforms.
10. Loading performs no code execution and launches no subprocess.
11. No existing core schema or future workflow/sandbox behavior is changed.
12. Formatting, linting, strict typing, unit tests, and applicable fixture validation tests pass in
    the existing Python 3.14 environment and in ordinary GitHub Actions CI.

## 13. Tests and Validation Commands

Tests must cover at minimum:

- valid loading of all five cases and all required fields;
- missing case;
- malformed JSON and structurally malformed manifests;
- unknown fields and invalid enum/type values;
- hidden-test isolation in both type shape and observed file reads;
- reference-patch isolation in both type shape and observed file reads;
- invalid case IDs and absolute, drive-qualified, UNC, traversal, symlink/escape paths;
- missing declared artifacts and wrong file/directory kinds;
- corpus uniqueness for case IDs and bug categories;
- separation of visible tests, hidden tests, and evaluator metadata;
- reference-patch metadata consistency with expected and forbidden changed files;
- static confirmation that each case has the intended small failing implementation, visible
  expectation, hidden regression expectation, and correcting reference patch without executing the
  fixture on the host.

Run from the repository root with the existing virtual environment:

```text
.venv\Scripts\python.exe -m pytest tests/unit/test_benchmark_loader.py tests/unit/test_benchmark_fixtures.py
.venv\Scripts\python.exe -m ruff format --check .
.venv\Scripts\python.exe -m ruff check .
.venv\Scripts\python.exe -m mypy app benchmarks scripts
.venv\Scripts\python.exe -m pytest
.venv\Scripts\python.exe scripts/check.py
```

POSIX equivalents use `.venv/bin/python`. The canonical cross-platform command remains:

```text
python scripts/check.py
```

No host-side command may execute code from a fixture repository. Actual failing-before/passing-after
pytest execution becomes an integration check only after the Docker sandbox exists.
