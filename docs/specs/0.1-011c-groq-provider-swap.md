# Task 0.1.11c — Groq Live-Provider Swap

## 1. Goal

Replace only the committed Task 0.1.11a live provider-specific seam:

```text
OpenAI
→ Groq
```

The installed live benchmark command becomes:

```text
tracefix benchmark --split development --provider groq
```

Task 0.1.11c is a bounded migration of the existing live adapter, credential, dependency,
provider identity, configuration, workflow, focused documentation, and provider-specific tests.
It is not a new benchmark implementation, a multi-provider framework, or a redesign of Task
0.1.11a.

Deterministic implementation and review must make no real Groq request. Final live acceptance is
one separately human-authorized Groq benchmark over the unchanged five development cases.

## 7. Groq Request Mapping

The Groq adapter must construct one synchronous, non-streaming Chat Completions call per existing
provider operation.

- Pass the existing `rendered_prompt` byte-for-byte unchanged as the content of exactly one user
  message:

  ```text
  messages=[{"role": "user", "content": rendered_prompt}]
  ```

- Do not introduce a system, developer, assistant, tool, or second user message.
- Pass the exact configured model `openai/gpt-oss-120b`.
- Map generic `max_output_tokens` at the adapter boundary to Groq's supported
  `max_completion_tokens` parameter. For the approved profile the value is exactly `4096`.
- Read and validate `MODEL_REASONING_EFFORT` only as provider-local configuration and send
  `reasoning_effort="low"`. Do not add it to generic graph state, `ModelConfiguration`, or
  `ModelProviderRequest`.
- Generate strict JSON Schema from the existing operation-specific Pydantic type: `RepairPlan` for
  repair planning and `PatchProposal` for patch generation.
- Send the schema through Groq's Chat Completions `response_format` JSON Schema shape with the
  operation name, `strict: true`, and the generated schema. Do not hand-maintain, loosen, or fork
  the operation schemas.
- Explicitly disable tools and tool choice. Do not enable built-in tools, functions, search,
  browsing, code execution, remote MCP, file access, or parallel tool calls.
- Explicitly set streaming to false.
- Construct the SDK client with `max_retries=0` and the validated finite timeout. The request may
  also receive the same explicit timeout if required by the supported SDK. No project retry loop
  may be added.
- Preserve existing monotonic latency measurement around exactly the SDK transport call.

The exact outbound request must contain only Groq-supported Chat Completions fields required by
this contract. Do not carry OpenAI Responses API fields such as `input`, `text`, `store`, Responses
API output shapes, or `max_output_tokens` into the Groq call. Do not copy OpenAI-specific metadata
or response parsing into the new adapter.

The existing generic temperature field must not be removed or redefined. It is not an additional
operator-controlled Groq profile setting in this task and must not be added to the approved
`.env.example` block or used to alter rendered prompt content. The Groq adapter must not send it
unless deterministic SDK compatibility evidence proves it is required by the approved Groq
contract; such evidence would require human review before expanding the exact request shape.

## 8. Groq Response Validation and Failure Semantics

The SDK boundary must validate responses deterministically before projecting them into
project-owned types. It must validate all of the following:

- the object is the expected official SDK Chat Completion response type for the supported SDK
  version;
- `choices` is an actual list containing exactly one permitted completion choice;
- the sole choice has the expected integer index `0`;
- the choice message has assistant role;
- the choice has the terminal successful completion status required by Chat Completions (the
  approved normal finish reason is `stop`);
- no tool call, legacy function call, or function/tool payload is present;
- refusal, content-filtered, length-truncated, cancelled, incomplete, or otherwise non-successful
  output is not accepted as successful model content;
- assistant structured content is a non-empty string within the existing response-size bound;
- usage exists and contains prompt token count, completion token count, and total token count;
- each token count has exact built-in integer type, is not Boolean/coerced, is non-negative, and is
  within the existing overflow bound; and
- `prompt_tokens + completion_tokens == total_tokens` exactly.

Map validated `prompt_tokens` to the existing `input_tokens` meaning and validated
`completion_tokens` to the existing `output_tokens` meaning. Do not derive usage from text,
reasoning content, model claims, limits, or local tokenization.

The Task 0.1.11a failure distinction remains unchanged:

- A trustworthy completed provider response with trustworthy usage but refusal, incomplete/
  non-terminal content, empty content, or content that fails the existing strict operation-schema
  parsing is valid model-content failure and maps through the existing
  `malformed_model_output`/repair-failure path.
- Authentication, authorization, timeout, rate limit, connection, DNS/TLS, SDK transport, client
  construction, unsupported SDK, unexpected response type/shape, missing or malformed usage,
  contradictory token totals, or inability to prove a completed trustworthy response is a
  provider/infrastructure execution failure.
- `KeyboardInterrupt` and `SystemExit` retain existing propagation/cleanup semantics.

Exception mapping must use safe constant project diagnostics. Raw provider exception text,
response bodies, request bodies, headers, request IDs, reasoning, or SDK object representations
must not cross the adapter boundary or appear in logs, console output, reports, or artifacts.

```text

```

Pricing remains required benchmark input, strictly validated, recorded in the report, and used by
the unchanged exact `Decimal` formula. Do not permanently hard-code Groq or model pricing in
application logic, README commands, workflow defaults, or tests as a current pricing truth.

`MODEL_REASONING_EFFORT` must accept exactly `low` for this task. Missing, blank, differently
cased, or any other value is a preflight configuration failure before case loading, workspace
creation, Docker, report writing, or provider contact.

The live optional dependency must contain the official `groq` package instead of `openai`. The
implementation must select and document a bounded compatible range after verifying its installed
version, Python 3.14 support, `Groq` client constructor, typed Chat Completion response, strict JSON
Schema request shape, timeout, and `max_retries=0` behavior. Missing or unsupported SDK versions
must fail safely at benchmark preflight and must not break imports for `tracefix repair`, CLI help,
ordinary tests, or normal CI.

Do not add LangChain, an OpenAI-compatibility client, a provider multiplexer, a retry library,
dotenv, a tokenizer, a pricing library, or an alternate Python runtime.

## 10. Security and Workflow Requirements

- Read `GROQ_API_KEY` only at the trusted live provider factory/boundary. Pass it explicitly to the
  official SDK client and do not retain or expose it through project-owned models.
- The credential must never enter graph state, prompts, provider requests as content, reports,
  artifacts, Docker containers, logs, diagnostics, exception text, command arguments, cache keys,
  annotations, or uploaded files.
- Do not pass the host environment, proxy configuration, application secrets, GitHub credentials,
  or model credentials into execution containers.
- Do not accept an environment-controlled provider endpoint. Do not read or honor a custom base
  URL. If the supported SDK can infer an endpoint override from ambient environment, force the
  official Groq HTTPS API endpoint from trusted code or reject the override before client
  construction, and test that an ambient override cannot redirect the credential. Any alternate
  endpoint requires a separately approved specification and explicit validation.
- Preserve all Docker and report-publication security controls from Task 0.1.11a.
- Keep `.github/workflows/live-benchmark.yml` manual-only (`workflow_dispatch`), least-privilege
  (`contents: read`), pinned to full action SHAs, finite-timeout, non-overlapping, and independent
  of required ordinary CI.
- Scope `GROQ_API_KEY: ${{ secrets.GROQ_API_KEY }}` only to the paid live benchmark step. There
  must be no workflow-level or job-level `GROQ_API_KEY`, and no credential in deterministic
  installation, validation, Docker build, or artifact upload steps.
- Use fixed workflow choices for `development`, `groq`, `openai/gpt-oss-120b`, `low`, and `4096`.
  Keep timeout and both prices explicit operator inputs. Do not introduce a provider/model free
  text path or automatic fallback.
- Preserve the benchmark exit status after safe evidence upload. A valid report containing repair
  failures may succeed; provider/infrastructure/publication/upload failure must fail the workflow.
- Normal CI remains secret-free, network-independent with respect to model providers, and
  unchanged.
