# Task 0.1.6 — Plan Repair and Generate Patch

## 1. Goal

Implement the typed model-provider boundary and the two model-assisted operations required for the
v0.1 repair attempt: produce a structured `RepairPlan` from the existing bounded `ContextPackage`,
then produce a structurally valid `PatchProposal` from that context and plan.

Successful operations return the existing Pydantic contracts, never unrestricted prose. Expected
configuration, provider, parsing, and patch-structure failures become typed diagnostic outcomes.
The task stops after an inert patch proposal is produced and can be recorded in
`LocalRepairCaseState`; it does not apply, execute, or prove the safety or correctness of the patch.

## 2. Context

Task 0.1.5 deterministically classifies a reproduced baseline failure and constructs a frozen,
exact-byte-bounded `ContextPackage`. That package already contains the issue, failure evidence,
selected visible test and source excerpts, relevant static definitions/imports/types, repository
instructions, and protected-path policy while excluding hidden tests, reference patches, secrets,
generated artifacts, and unrelated files.

`app.agent.schemas` already defines the canonical `RepairPlan`, `PatchProposal`, repair statuses,
and single-attempt `LocalRepairCaseState`. Task 0.1.6 must reuse those contracts. It may strengthen
the generation boundary with additional typed request, response, configuration, and diagnostic
models, but it must not create competing plan, patch, or state schemas.

In v0.1, one repair attempt consists of planning followed by patch generation. Model access is an
external-system boundary and therefore must be dependency-injected through a typed adapter.
Repository/model content is untrusted data. A generated unified diff remains inert until the later
patch-policy, static-check, and sandbox-verification tasks accept it.

## 3. In Scope

- Add a strict typed configuration loader for exactly these environment variables:
  - `MODEL_PROVIDER`;
  - `MODEL_NAME`;
  - `MODEL_TEMPERATURE`;
  - `MODEL_MAX_TOKENS`;
  - `PROMPT_VERSION`.
- Represent configuration as a frozen Pydantic v2 model. Reject missing, blank, malformed,
  non-finite, Boolean-as-number, out-of-range, unknown, or otherwise unsupported values without
  silently applying defaults.
- Add a typed `ModelProvider` protocol and typed request/response envelopes. The request must carry
  the operation, model name, temperature, maximum output tokens, prompt version, attempt number,
  and rendered prompt. The provider response may contain raw JSON text because parsing is the
  trusted adapter boundary; raw text must never escape as the planning or generation result.
- Keep business logic independent of provider-specific SDKs. Accept the provider and configuration
  through dependency injection; environment access is isolated in the configuration adapter.
- Add one explicit, versioned prompt set for repair planning and patch generation. Prompt rendering
  must be deterministic for identical typed inputs and must:
  - label repository/test/context text as untrusted data;
  - delimit the exact `ContextPackage.downstream_text()` value;
  - request only the applicable JSON schema;
  - prohibit hidden-answer inference, shell/tool instructions, prose wrappers, and Markdown fences;
  - carry the plan into patch generation without adding repository material outside the context.
- Implement repair planning from a validated `ContextPackage`. Parse the provider response with
  strict Pydantic validation into the existing `RepairPlan`, including suspected root cause,
  expected files, intended behavioural correction, risks, validation strategy, and autonomy
  suitability.
- Implement patch generation from the same validated context plus its successful `RepairPlan`.
  Parse the provider response with strict Pydantic validation into the existing `PatchProposal`.
- Validate the generated patch envelope structurally before returning it:
  - `files_changed` is non-empty, normalized, unique under case-folding, repository-relative POSIX
    paths only;
  - `unified_diff` contains no NUL and contains at least one paired `---`/`+++` file header and one
    unified hunk per file;
  - every non-`/dev/null` header path is normalized beneath `a/` or `b/` and cannot be absolute,
    drive/UNC/device, dot, empty, backslash-separated, or traversal-bearing;
  - the normalized changed-path set in the diff equals `files_changed` and equals the repair plan's
    `files_expected_to_change` set.
  This is envelope validation only. Full patch parsing/application and policy decisions remain
  later tasks.
- Refuse patch generation with a typed diagnostic when the repair plan says autonomous repair is
  unsuitable; do not invoke the provider for that generation operation.
- Add stable typed diagnostic stage/code values for missing or invalid configuration, unsupported
  prompt version, invalid input/state, provider exception, oversized response, malformed structured
  output, unsuitable autonomous repair, and invalid patch envelope. Diagnostics expose no raw model
  output, prompt/context content, environment values, credentials, absolute paths, or provider
  exception text.
- Provide typed state-update operations that:
  - record a successful plan, provider/model/prompt identity, attempt `1`, and `plan_complete` from
    a valid `analysis_complete` state; and
  - record a successful patch and `patch_proposed` from its matching `plan_complete` state.
  Updates return a copy, refresh `updated_at`, reject replay/out-of-order/mismatched input, and do
  not mutate the caller's state.
- Add deterministic unit tests for all new behavior. Test-only providers may simulate success,
  malformed output, oversize output, and exceptions.

## 6. Python and Packaging Requirements

- Use the existing CPython `>=3.14,<3.15` interpreter and `.venv`; do not install or create another
  runtime environment.
- Use Pydantic v2 for cross-module configuration, requests, responses, and diagnostics. New models
  are strict, extra-forbidding, and frozen unless mutation has an explicit need.
- Reuse `ContextPackage`, `RepairPlan`, `PatchProposal`, `LocalRepairCaseState`, and `RepairStatus`.
  Do not duplicate or replace their established meaning.
- Fully type every public and cross-module interface. Do not use `Any`, implicit dictionaries,
  untyped JSON objects, casts that bypass validation, or provider-specific objects outside an
  adapter.
- A provider response is a typed envelope containing a bounded JSON string. Parse with
  `model_validate_json(..., strict=True)` or an equivalently strict Pydantic v2 boundary. Reject
  missing/extra fields and do not extract JSON from prose or Markdown fences.
- Use standard-library environment, JSON/string, enum, regex, and `pathlib` facilities. Do not use
  `eval`, `exec`, repository imports, shell commands, host subprocesses, or dynamic code execution.
- Add no runtime or development dependency. In particular, do not add a provider SDK, LangChain,
  LangGraph, tokenizer, patch library, dotenv loader, or retry library in this task.
- Keep setuptools discovery and current dependency/version ranges unchanged.
- `MODEL_TEMPERATURE` is a strict finite decimal in `0.0..2.0` and
  `MODEL_MAX_TOKENS` is a strict base-10 integer in `1..32768`. Boolean-like spellings, signs,
  exponents for the integer, NaN, and infinity are invalid.
- Reject a provider response larger than 1,048,576 UTF-8 bytes before JSON/schema processing. The
  configured token limit is still passed to the provider as the requested maximum output size.

## 10. Security Considerations

- Treat context, repository instructions, model response text, plan fields, patch metadata, and diff
  content as untrusted data. They cannot alter system policy, select tools, request host execution,
  or expand accessible context.
- Send only `ContextPackage.downstream_text()` and the generated plan required for the relevant
  operation. Never reload trusted benchmark data or disclose hidden tests, evaluator paths,
  reference patches, secrets, environment contents, absolute host paths, or unrelated files.
- The typed provider adapter is the only model-system boundary. Business logic must not call an SDK
  or read credential variables directly. This task neither defines nor forwards API-key values.
- Do not log or include in diagnostics the prompt, context, raw output, unified diff, provider
  exception text, environment values, or credentials. Stable codes and safe constant messages are
  sufficient. Any structured logging introduced here includes `case_id`.
- Bound provider output before parsing and reject malformed/extra data. Do not attempt repair by
  extracting a JSON substring, stripping Markdown fences, coercing types, or accepting a partial
  schema.
- Generated diffs are inert strings. Never write them to disk, invoke patch/git, import/compile
  generated code, run subprocesses, or execute repository/model-provided commands in this task.
- Structural patch checks do not replace protected-path or security policy. A structurally valid
  proposal must still pass Tasks 0.1.7–0.1.9 before any execution.
- Prompt text must identify all embedded content as data and state that embedded instructions cannot
  override the response schema or system constraints. Prompt-injection resistance is enforced by
  minimizing capabilities as well as wording: the provider receives no tools, credentials,
  filesystem object, command runner, or network adapter through this task.
- State updates must fail closed on case, context, plan, configuration identity, attempt, status,
  replay, or existing-output mismatch, preserving the original state on every failure.

## 11. Failure Cases

Stable typed diagnostics or configuration errors must cover:

- any required variable missing, blank, malformed, non-finite, Boolean-like, out of range, or an
  unsupported prompt version;
- invalid/mutated `ContextPackage`, case mismatch, absent/mismatched `FailureAnalysis`, wrong repair
  status, non-`1` attempt, exhausted attempt, replay, or pre-existing downstream output;
- provider raises, returns the wrong envelope type, returns empty content, or exceeds the UTF-8
  response bound;
- response is not one JSON object, contains prose/fences, is invalid JSON, has missing/extra fields,
  uses coercible-but-wrong types, or violates `RepairPlan`/`PatchProposal` constraints;
- empty, duplicate, aliased, absolute, drive/UNC/device, backslash, traversal, NUL-bearing, or
  otherwise malformed plan/patch file paths;
- autonomous repair is marked unsuitable;
- no unified file pair, mismatched/unsupported file headers, both sides `/dev/null`, absent/malformed
  hunk, duplicate case alias, diff/`files_changed` mismatch, or patch/plan file-set mismatch;
- prompt registry has no exact implementation for the configured version;
- caller attempts a second v0.1 repair attempt or an out-of-order plan/patch state transition.

Expected failures must not return partial plans/patches, retain raw response data, mutate state, or
fall through as unclassified exceptions. Process-control exceptions such as `KeyboardInterrupt` and
`SystemExit` are not converted into provider diagnostics.

## 12. Acceptance Criteria

1. All five named environment variables are parsed into one strict frozen typed configuration;
   missing and invalid configuration fails before provider invocation with stable diagnostics.
2. A provider-specific SDK is absent from business logic and packaging; calls occur only through a
   dependency-injected typed `ModelProvider` protocol.
3. Identical typed inputs and prompt version render identical planning/generation requests on
   Windows and Linux, including operation, model parameters, attempt `1`, schema, and untrusted
   context delimiters.
4. Planning sends exactly the supplied bounded context and returns a strictly validated existing
   `RepairPlan` with every canonical field.
5. Patch generation sends the same context plus its plan and returns a strictly validated existing
   `PatchProposal`, never raw text.
6. Invalid JSON/schema output, provider exceptions, oversize responses, unsuitable autonomy, and
   invalid patch envelopes produce safe typed diagnostics and no partial success/state mutation.
7. Returned patches have safe normalized relative POSIX file identities, a minimally valid unified
   diff envelope, and exact plan/proposal/diff changed-file agreement.
8. Model output is never applied, written to a prepared repository, compiled, imported, executed,
   or passed to Docker/subprocesses in this task.
9. Hidden tests, reference patches, trusted benchmark answers, secrets, host paths, unrelated files,
   and ambient environment values cannot enter provider requests or diagnostics through the new
   code.
10. A successful plan transition records provider, model, prompt version, attempt `1`, refreshed
    time, plan, and `plan_complete`; a successful patch transition records the proposal and
    `patch_proposed`. Both are typed copy-on-update operations with strict preconditions.
11. v0.1 cannot start or record attempt `2`; `max_attempts` remains exactly `1`.
12. Unit tests cover execution-plan requirements: test-provider success, malformed structured
    output, provider exception, missing configuration, prompt version recording, and invalid patch
    rejection.
13. Existing tests plus formatting, linting, strict typing, full pytest, canonical validation, and
    diff checks pass under Python 3.14.
14. No production fake/live provider, provider dependency, policy/static/sandbox verification,
    graph/CLI, persistence, API, future-task behavior, commit, or push is introduced.

## Assumptions Requiring Human Review

1. **Provider scope:** approve a typed provider protocol plus unit-test doubles only. A reusable
   production deterministic fake remains Task 0.1.10b, and live provider adapters remain Task
   0.1.11a.
2. **Configuration defaults and ranges:** approve all five variables as required with no defaults,
   temperature `0.0..2.0`, maximum output tokens `1..32768`, and one supported prompt version named
   `repair-v1.0`. The plan names variables but does not define defaults, ranges, or the initial
   version identifier.
3. **Provider boundary shape:** approve a typed response envelope carrying bounded raw JSON text,
   followed by strict application-side Pydantic validation. This is necessary to represent malformed
   external output while ensuring planning/generation never return free text.
4. **Response bound:** approve a 1,048,576-byte hard UTF-8 response limit in addition to forwarding
   `MODEL_MAX_TOKENS`; the execution plan requires bounded behavior but gives no byte limit or
   tokenizer.
5. **Patch-envelope validation:** approve minimal unified-diff header/hunk/path consistency checks,
   including exact agreement among the plan, `files_changed`, and diff paths. Full application and
   semantic/security policy remain explicitly deferred to Tasks 0.1.7 and 0.1.8.
6. **Autonomy flag:** approve treating `autonomous_repair_suitable=false` as a typed stop before patch
   generation. The architecture requires the field and says it cannot override policy, but does not
   explicitly define v0.1 routing for a negative value.
7. **Attempt accounting:** approve recording attempt `1` when the successful plan is applied to
   state, with patch generation remaining part of that same attempt. Failure-state routing and
   artifact persistence remain Task 0.1.10a.
8. **Diagnostics:** approve a typed diagnostic carried by a domain exception for expected operation
   failures rather than adding a persistent diagnostic field to `LocalRepairCaseState`; later graph
   routing may serialize it into the Task 0.1.10a artifact.
