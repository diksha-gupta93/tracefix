# Task 0.1.11d — Deterministic Groq Live-Benchmark Request Pacing

## Goal

Add only deterministic request pacing to the existing Groq live benchmark. The current Groq
organization limit is 8,000 tokens per minute, and the latest authorized live run accumulated
8,477 combined input and output tokens in under ten seconds before a provider infrastructure
failure. The implementation must conservatively separate consecutive real Groq request starts
without changing benchmark evaluation semantics.

## Required policy

- The fixed live-benchmark pacing interval is `61.0` seconds between consecutive Groq provider
  request start times in one benchmark application/process.
- The first request starts immediately.
- Each later request waits only for the remaining portion of the interval according to a
  monotonic clock.
- One pacer is created by the benchmark application factory and shared by every Groq provider
  instance, covering planning, patch generation, and case boundaries.
- The pacer uses dependency-injected monotonic-clock and sleeper functions, does not persist
  state, and serializes access so concurrent requests cannot bypass the gate.
- Pacing delay is outside provider latency measurement. Existing latency continues to measure
  only the provider transport call.
- Pacing clock or sleeper failures fail closed through existing safe infrastructure-failure
  handling without exposing exception details.

## Preserved behavior

This task adds no retries and does not enable Groq SDK retries. It does not retry HTTP 429 or
change fail-fast behavior, benchmark cases or order, prompts, schemas, graph behavior, repair
classification, usage/cost accounting, reports, sandbox behavior, static checks, the
deterministic fake provider, or ordinary CI. Provider exceptions remain sanitized. The SDK
continues to use `client.chat.completions.create`, `max_retries=0`, streaming disabled, tools
disabled, reasoning effort `low`, and 4,096 maximum completion tokens.

## Deterministic acceptance

Tests must use injected clocks, sleepers, and transports; they must never wait 61 real seconds or
make a Groq network request. Evidence must cover first and subsequent requests, remaining-delay
calculation, start-to-start semantics, already-elapsed intervals, latency exclusion, sharing
across provider instances and cases, planning-to-patch pacing, safe pacing failures, unchanged
fake-provider behavior, and unchanged fail-fast behavior.

The authorized live benchmark has not yet completed successfully. After deterministic review,
Linux CI, and human authorization, exactly one new live benchmark may be performed.
