## Generation Contract

`PatchProposal.unified_diff` must contain only parser-compatible unified-diff text:

1. Paths are normalized, repository-relative POSIX paths: no absolute paths, drives, backslashes,
   empty/`.`/`..` segments, surrounding whitespace, controls, or case-fold aliases.
2. Modifications use paired `--- a/<path>` and `+++ b/<path>` headers. Additions use
   `--- /dev/null` with `+++ b/<path>`. Deletions use `--- a/<path>` with `+++ /dev/null`.
   Non-null old and new paths must identify the same file, and file identities must be unique.
3. Every file pair has at least one hunk. Hunk headers use
   `@@ -<old_start>,<old_count> +<new_start>,<new_count> @@`; `,1` may be omitted, and a zero start
   is allowed only when its corresponding count is zero.
4. Every hunk body line starts with exactly one space (context), `-` (removed), or `+` (added).
   Old/new body totals exactly match the declared counts.
5. `\ No newline at end of file` may appear only immediately after an affected hunk body line and
   may not repeat for the same old/new side.
6. The field contains raw diff text only: no Markdown fences, explanatory prose, shell commands,
   XML, or nested JSON wrappers.
7. `files_changed`, parsed diff paths, and the repair plan's `files_expected_to_change` agree
   exactly.

The prompt must remain concise and use no benchmark case path, source, expected fix, hidden test, or
reference patch as an example. The schema structure and validation semantics of `RepairPlan` and
`PatchProposal`, including `PatchProposal.confidence`, remain unchanged.

## Prompt Version Decision

Keep `repair-v1.0`. The repository supports exactly that version across model configuration,
deterministic fixtures, CLI, workflow, and reports, and contains no policy requiring a version bump
for this corrective clarification. This task repairs the documented behavior of the existing
generation operation; it does not introduce a second prompt profile or change version semantics.

## Tests and Acceptance

- Prompt tests assert every production parser-boundary rule above.
- Generic parser-contract tests cover modification, addition, deletion, multiple hunks, a valid
  no-final-newline marker, fenced input, missing paired headers, unsupported prefixes, malformed
  hunk headers, count mismatch, body content outside a hunk, path mismatch, and duplicate identity.
- A deterministic provider response following the documented contract must parse as
  `PatchProposal`, pass `parse_unified_diff`, pass envelope validation, and reach patch policy in the

  and stop before policy.
- Existing metadata-only tracing must not export prompts, raw proposals, or unified diffs.
- Focused and full validation must make no real Groq, LangSmith, OTEL, or paced-wait request.

No paid live benchmark is authorized by this task. A later separately authorized live run is needed
before claiming autonomous repair works.
