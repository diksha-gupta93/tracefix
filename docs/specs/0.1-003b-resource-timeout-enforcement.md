# Task 0.1.3b — Resource, Timeout, and Output Enforcement

## 1. Goal

Extend the Task 0.1.3a Docker sandbox with typed, configurable execution limits and typed
termination information. Every approved pytest execution must have bounded CPU allocation,
memory, process count, wall-clock duration, returned stdout, and returned stderr while preserving
the existing isolation and unconditional cleanup behavior.

This task implements only the resource, timeout, output, and result-classification requirements
assigned to Task 0.1.3b by the execution plan.

## 2. Context

Task 0.1.3a introduced:

- `SandboxRunner` and an injected typed Docker CLI adapter;
- an immutable, strictly validated pytest command;
- a fresh Linux container per execution;
- a read-only repository bind mount and container-local writable workspace;
- non-root execution, disabled networking, and a read-only root filesystem;
- structured stdout, stderr, exit code, and duration;
- exact-container cleanup after success and failure.

Those controls do not yet bound resource consumption, execution time, or returned output. This
task closes only that gap. It retains the Docker CLI adapter architecture already present; adopting
the Docker SDK or redesigning the entire sandbox boundary is not required.

Docker provides reliable post-execution OOM evidence through container inspection. It does not
provide an equally reliable portable signal proving that an arbitrary nonzero test exit was caused
by CPU throttling or PID exhaustion. Therefore this specification requires positive memory-limit
classification when Docker reports OOM termination, but does not infer a resource failure merely
from exit code `137` or another nonzero exit. CPU and PID limits must still be configured and
verified behaviorally.

## 3. In Scope

- Add a strict, immutable Pydantic v2 `SandboxLimits` model.
- Give `SandboxLimits` these defaults:
  - `cpu_count=1.0`;
  - `memory_bytes=536_870_912` (512 MiB);
  - `pids_limit=128`;
  - `timeout_seconds=120.0`;
  - `stdout_bytes=1_048_576` (1 MiB);
  - `stderr_bytes=1_048_576` (1 MiB).
- Require callers to pass limits through the typed runner boundary, with the default model used
  when limits are omitted.
- Translate limits into Docker create arguments using explicit CPU, memory, and PID flags.
- Enforce wall-clock timeout from the host-side monotonic deadline; timeout must not depend on code
  inside the untrusted container cooperating.
- On timeout, forcibly terminate the exact generated container, collect the available result
  evidence where possible, classify the result as timed out, and still perform final removal.
- Bound returned stdout and stderr independently by encoded byte length.
- Append a fixed, documented ASCII truncation marker to a stream only when bytes from that stream
  were omitted. The complete encoded returned stream, including the marker, must not exceed that
  stream's configured limit.
- Decode retained bytes as UTF-8 with replacement and avoid emitting malformed partial UTF-8 text.
- Extend `SandboxResult` with strict typed completion classification and truncation indicators.
- Distinguish at minimum normal completion, wall-clock timeout, and Docker-reported memory resource
  failure. A normal nonzero pytest exit remains normal completion.
- Preserve elapsed monotonic duration, existing validation, injected external-system boundary,
  fresh-container behavior, and cleanup error semantics.
- Add focused unit and Docker integration tests for all new behavior.
- Update CI, README, and progress documentation only as needed for this task.

## 4. Out of Scope

- Task 0.1.3c controls: capability dropping, `no-new-privileges`, explicit seccomp selection,
  sensitive-host-path policy expansion, credential discovery tests, and the full adversarial suite.
- A custom seccomp profile, syscall allowlist, Docker socket mount, or Docker-in-Docker.
- Disk, filesystem-size, tmpfs-size, I/O bandwidth, GPU, or network-bandwidth quotas.
- Guaranteed identification of CPU throttling or PID-limit pressure as the cause of an arbitrary
  test failure.
- Streaming output to callers, persistent logs, log aggregation, or observability services.
- FastAPI, queues, workers, databases, LangGraph, model providers, repair behavior, GitHub
  integration, or later-version features.
- Supporting arbitrary commands, shells, pytest options, Windows containers, or non-Docker
  runtimes.
- Changing fixture repositories or exposing hidden evaluator content.
- Adding dependencies unrelated to the bounded implementation.

## 6. Python and Packaging Requirements

- Use the repository's required CPython `>=3.14,<3.15` and existing `.venv`.
- Use Pydantic v2 for `SandboxLimits`, configured with strict validation, `extra="forbid"`, and
  immutable instances.
- All limit fields must reject booleans, strings, NaN, infinity, zero, negative values, unknown
  fields, and coercion. Integer byte/PID limits must be strict integers. CPU and timeout values must
  be strict finite floats.
- `SandboxResult` additions must also be fully typed, strict, immutable, and serializable through
  Pydantic v2. Use enums or equally explicit typed values; do not use free-form status strings.
- Do not use `Any` or implicit dictionaries across module boundaries.
- Keep Docker behind an injected typed protocol. If timeout-aware adapter operations or typed
  inspection records are needed, express them explicitly in that protocol.
- Invoke subprocesses as token sequences with `shell=False`. A timeout raised by the host Docker
  CLI subprocess must be translated into a sandbox-domain outcome or typed infrastructure error;
  raw `subprocess` objects must not cross the adapter boundary.
- The result contract must represent:
  - optional exit code, because a timed-out or OOM-killed execution may not yield a meaningful
    pytest exit code;
  - completion classification;
  - stdout and stderr;
  - independent stdout/stderr truncation booleans;
  - non-negative finite duration.
- Normal completion requires an exit code. Timeout and Docker-confirmed resource termination may
  use `None`; invalid field combinations must be rejected by model validation.
- Reuse existing dependencies. Adding a package requires an explicit, task-specific justification
  and human approval; no new dependency is expected.
- Do not change the project version or broaden package discovery.

## 7. Development Tool Requirements

- Docker integration tests must use deliberately small limits and short bounded workloads so they

## 8. Cross-Platform Requirements

- The host runner and unit tests must work from Windows PowerShell and POSIX shells.
- Docker integration requires a usable Linux-container Docker daemon; Docker Desktop on Windows is
  supported.
- Generate Docker CLI arguments as sequences, never shell-quoted command strings.
- CPU values passed to Docker must use locale-independent decimal formatting.
- Memory and output limits must use byte counts rather than platform-dependent unit parsing in
  public Python contracts.
- Timeout measurement must use a monotonic clock and must not depend on wall-clock time zones.
- Output truncation must be deterministic across CRLF/LF hosts and must operate on captured bytes
  before text decoding.
- Preserve existing Windows-safe absolute repository mount handling.
- POSIX validation commands use `.venv/bin/python`; Windows commands use
  `.venv\Scripts\python.exe`.

## 10. Security Considerations

- All untrusted workload code continues to execute only in the Docker container, never on the host.
- Apply CPU, memory, and PID limits at container creation, before untrusted code starts.
- Enforce timeout independently on the trusted host. On deadline expiry, target only the unique
  generated container and force termination; never issue a broad Docker cleanup command.
- Returned output must be bounded independently for stdout and stderr. Truncation must not allow
  the marker or UTF-8 decoding to exceed the configured byte cap.
- Capturing output only after an unbounded Docker logging operation is insufficient. The
  implementation must ensure the host-side Docker CLI capture and returned in-memory payload are
  bounded; it must also configure a bounded project-owned container logging mechanism where the
  selected Docker mechanism supports it. If Docker cannot enforce the specified independent
  per-stream storage caps, the implementation must at minimum use a bounded aggregate daemon log
  configuration and preserve the independent returned caps, documenting the distinction.
- Never infer a resource-limit event solely from an attacker-controlled exit code or output.
  Memory resource classification requires trusted Docker inspection evidence such as
  `State.OOMKilled=true`.
- Do not mount the Docker socket, credentials, a home directory, or additional host paths into the
  execution container.
- Preserve non-root execution, disabled networking, read-only root filesystem, read-only input
  mount, explicit writable temporary locations, exact unique names, and cleanup in `finally`.
- Cleanup failure remains visible. If execution and cleanup both fail, retain evidence of both.
- Do not pull forward Task 0.1.3c controls or weaken current controls to simplify tests.

## 11. Failure Cases

The implementation must handle and test, where deterministic:

- malformed, coercible, non-finite, zero, negative, or unknown `SandboxLimits` values;
- Docker rejecting CPU, memory, PID, or log-limit arguments;
- host timeout before the container reaches a terminal state;
- failure to terminate a timed-out container;
- timeout racing with natural container completion;
- Docker-reported OOM termination;
- a nonzero pytest exit that is not a timeout or trusted resource event;
- malformed or missing Docker wait/inspection data;
- output below, exactly at, and above each independent byte limit;
- multibyte UTF-8 cut at the truncation boundary and undecodable output;
- a configured output limit too small to contain the full truncation marker;
- failure while collecting bounded output;
- monotonic clock regression;
- cleanup failure after success, pytest failure, timeout, resource failure, or another execution
  failure;
- simultaneous execution/termination failure and cleanup failure.

Limits that cannot safely contain the fixed marker must be rejected during `SandboxLimits`
validation. Empty output is valid. A normal nonzero pytest result is not an infrastructure or
resource failure. Infrastructure failures must remain exceptions rather than being mislabeled as
workload timeout/resource outcomes.

## 12. Acceptance Criteria

1. A strict immutable `SandboxLimits` model provides exactly the defaults in Section 3 and rejects
   invalid or coercible values.
2. `SandboxRunner.execute` accepts typed limits, uses defaults when omitted, and applies explicit
   Docker CPU, memory, and PID flags before container start.
3. A host-side monotonic deadline terminates an infinite workload within a small documented grace
   interval and returns a typed timeout classification.
4. Docker-confirmed OOM termination returns a typed resource-failure classification; exit code
   alone is not treated as proof of OOM.
5. PID-limit integration evidence shows a workload cannot exceed the configured process bound.
   CPU-limit argument construction is unit tested and normal execution under the default CPU quota
   is integration tested.
6. Returned stdout and stderr are capped independently, include the fixed marker only when
   truncated, expose independent truncation booleans, remain within the configured encoded-byte
   caps, and handle UTF-8 boundaries deterministically.
7. Normal passing and failing pytest execution remains classified as normal completion and retains
   its exit code, output, and duration.
8. The result model rejects inconsistent combinations of completion classification, exit code, and
   truncation metadata.
9. Timeout, resource failure, output truncation, and Docker-operation failure all preserve exact
   generated-container cleanup; integration tests observe no matching leftover containers.
10. Unit tests use typed fakes to cover argument mapping, timeout races, inspection mapping,
    truncation, malformed evidence, and combined execution/cleanup failures without real sleeps.
11. Docker integration tests cover infinite-loop timeout, bounded memory exhaustion, bounded
    process creation, stdout truncation, stderr truncation, unaffected normal execution, and
    cleanup.
12. Existing command validation and Task 0.1.3a isolation behavior remain intact.
13. CI builds the sandbox image and executes the complete unit and Docker integration suite without
    secrets or external services.
14. No Task 0.1.3c hardening or adjacent workflow behavior is implemented or claimed.
15. Formatting, linting, strict typing, unit tests, integration tests, and repository review checks
    pass with the existing Python 3.14 environment.

## 13. Tests and Validation Commands

Add or extend unit tests covering at minimum:

- default and custom `SandboxLimits` construction and serialization;
- rejection of every invalid limit class described in Sections 6 and 11;
- exact Docker CPU, memory, PID, and bounded-logging arguments;
- default-limit use and explicit-limit forwarding;
- timeout enforcement, natural-completion race handling, and forced termination;
- positive OOM inspection classification and rejection of exit-code-only inference;
- valid and invalid `SandboxResult` state combinations;
- stdout-only, stderr-only, and simultaneous truncation;
- below-limit, exactly-at-limit, above-limit, very-small-limit, invalid UTF-8, and split-multibyte
  boundaries;
- preservation of existing passing/failing execution behavior;
- cleanup after completion, timeout, OOM, output handling failure, and Docker failure;
- preservation of both execution and cleanup errors.

Add or extend Docker integration tests covering at minimum:

- an infinite loop stopped by a short wall-clock timeout and classified as timed out;
- memory consumption bounded by a deliberately small container limit and classified from Docker
  OOM evidence;
- incremental child-process creation unable to exceed a deliberately small PID limit;
- stdout and stderr independently truncated with correct markers and flags;
- a normal passing execution unaffected by the default limits;
- a normal failing pytest execution still classified as normal completion;
- no leftover generated container after every tested outcome.
