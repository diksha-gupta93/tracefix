# Task 0.1.1 — Core Pydantic Schemas

## 1. Goal

Define the small, fully typed Pydantic v2 schema layer required to carry one local repair case through the future v0.1 pipeline. This task establishes data contracts only; it does not implement workflow, sandbox, model, benchmark, CLI, or evaluation behavior.

## 2. Context

Task 0.1.0 created an importable `app` package, Python 3.12 packaging, shared quality checks, and basic CI without application behavior. The execution plan requires Task 0.1.1 to introduce `TestResult`, `FailureAnalysis`, `RepairPlan`, `PatchProposal`, `EvaluationResult`, and `LocalRepairCaseState` before later tasks consume them.

These schemas are in-memory and serialization contracts for v0.1. They are not database entities, LangGraph checkpoint definitions, external-provider payloads, or stable public API contracts. Later tasks may add behavior around them only through their own approved specifications.

## 3. In Scope

- Add Pydantic v2 as the sole runtime dependency introduced by this task.
- Create `app/agent/schemas.py` containing the six required models and their supporting string enums.
- Define the following bounded fields:
  - `TestResult`: `status`, `exit_code`, `stdout`, `stderr`, and `duration_seconds`.
  - `FailureAnalysis`: `category` and `summary`.
  - `RepairPlan`: `summary` and `files_to_modify`.
  - `PatchProposal`: `diff` and `files_changed`.
  - `EvaluationResult`: `status` and `summary`.
  - `LocalRepairCaseState`: every field required by the execution plan, using the nested models above.
- Define `TestStatus` with `passed`, `failed`, `timed_out`, and `error` values.
- Define `RepairStatus` with `pending`, `baseline_complete`, `analysis_complete`, `plan_complete`, `patch_proposed`, `verified`, and `failed` values.
- Define `FailureCategory` with `incorrect_conditional`, `boundary_condition`, `incorrect_return_value`, `exception_handling`, `fixture_or_mocking`, and `unknown` values.
- Define `EvaluationStatus` with `passed` and `failed` values.
- Use timezone-aware UTC timestamps for state creation and update defaults.
- Reject unknown fields on every model and validate assignments after construction.
- Add focused unit tests for construction, malformed-input rejection, serialization round trips, enum validation, timestamp behavior, defaults, and independent mutable defaults.

## 4. Out of Scope

- LangGraph graphs, reducers, annotations, checkpointing, or persistence.
- FastAPI, PostgreSQL, Redis, queues, workers, GitHub, tracing, or metrics.
- Docker execution, subprocess execution, command validation, resource limits, or sandbox result classification.
- Fixture repositories, manifests, benchmark loading, hidden-test handling, or reference patches.
- Failure classification logic, context selection, prompt construction, model adapters, provider calls, patch generation, patch application, or verification.
- CLI commands and JSON artifact writers.
- Retry behavior beyond representing `attempt_number` and the v0.1 `max_attempts=1` invariant.
- Database identifiers, delivery or idempotency identifiers, trace identifiers, audit records, checkpoint metadata, and other v0.2 fields.
- General-purpose schema bases, compatibility layers, custom serializers, or unrelated abstractions.
- Changes to the existing CI workflow, validation script, architecture documents, progress log, execution plan, or `AGENTS.md`.

## 6. Python and Packaging Requirements

- Continue to require CPython `>=3.12,<3.13`.
- Add `pydantic>=2,<3` to `[project].dependencies`; do not add other runtime or development dependencies.
- Use Pydantic v2 APIs only, including `model_dump`, `model_dump_json`, and `model_validate_json` where applicable.
- Every field and public declaration must be explicitly typed. `Any`, unparameterized collections, implicit dictionaries across module boundaries, and Pydantic v1 compatibility APIs are prohibited.
- Models must use `ConfigDict(extra="forbid", validate_assignment=True)` or an equivalently typed per-model configuration.
- Use `StrEnum` for JSON-compatible enum values.
- Use `list[...]` fields with `Field(default_factory=list)` when a collection defaults to empty.
- Do not add a console entry point or change package discovery, build backend, distribution name, or development-tool version constraints.

`LocalRepairCaseState` must have these types and defaults:

| Field | Type | Default/constraint |
| --- | --- | --- |
| `case_id` | `str` | Required, non-empty after whitespace stripping |
| `status` | `RepairStatus` | `RepairStatus.pending` |
| `attempt_number` | `int` | `0`, range `0..1` |
| `max_attempts` | `Literal[1]` | `1` |
| `baseline_result` | `TestResult \| None` | `None` |
| `failure_analysis` | `FailureAnalysis \| None` | `None` |
| `repair_plan` | `RepairPlan \| None` | `None` |
| `candidate_patch` | `PatchProposal \| None` | `None` |
| `verification_results` | `list[TestResult]` | Independent empty list |
| `evaluation_results` | `list[EvaluationResult]` | Independent empty list |
| `model_provider` | `str \| None` | `None`; when present, non-empty after stripping |
| `model_name` | `str \| None` | `None`; when present, non-empty after stripping |
| `prompt_version` | `str \| None` | `None`; when present, non-empty after stripping |
| `created_at` | `datetime` | Current timezone-aware UTC time |
| `updated_at` | `datetime` | Current timezone-aware UTC time |

All free-text scalar fields must reject blank values after trimming. Durations must be finite and non-negative. `TestResult.exit_code` is required because every represented result in this task is a completed, timed-out, or failed execution result; detailed absence semantics are deferred to the sandbox specifications.

## 7. Development Tool Requirements

- Existing Ruff formatting and linting configuration remains authoritative and must pass without exclusions or ignores added for the schemas.
- Existing strict mypy configuration remains authoritative. The models and tests must not introduce `Any`, type suppressions, or unjustified casts.
- Existing pytest configuration remains authoritative.
- Tests must exercise public Pydantic behavior rather than private internals.
- `scripts/check.py` must remain the shared local and CI validation entry point and must not be changed for this task.

## 8. Cross-Platform Requirements

- Schema behavior must be independent of filesystem paths, locale, local timezone, shell, and operating system.
- Timestamp tests must not depend on exact clock equality or local timezone settings. They must assert timezone awareness, UTC offset, ordering within captured bounds, and round-trip preservation.
- JSON round-trip tests must use UTF-8-safe string content and Pydantic APIs, without platform-specific path or newline assumptions.
- The canonical validation command remains `python scripts/check.py`; on Windows, the existing environment must be invoked with `.venv\Scripts\python.exe` when it is not activated.

## 9. GitHub Actions CI Requirements

- The existing `.github/workflows/ci.yml` remains unchanged.
- Editable installation in CI must install Pydantic from the declared runtime dependencies.
- The existing Ubuntu/Python 3.12 job must discover and run the new unit tests through `python scripts/check.py`.
- Tests must require no secrets, Docker daemon, model provider, network access after dependency installation, database, queue, or external service.
- No additional workflow, job, matrix entry, permission, cache, or action is required.

## 10. Security Considerations

- Treat all model inputs as untrusted structured data: reject unknown fields, invalid enum values, invalid types, blank required strings, negative or non-finite durations, and invalid attempt limits.
- Do not execute, import, apply, or otherwise interpret patch text, test output, model metadata, or summaries. They are inert data in this task.
- Do not read environment variables, files, credentials, developer home directories, or external services from validators or default factories.
- Do not log schema contents; stdout, stderr, diffs, and future model-derived text may contain sensitive data.
- Timestamp default factories may obtain the current UTC time only and must have no other side effects.
- This task does not execute untrusted code. The Docker controls in `AGENTS.md` remain mandatory for later execution tasks and must not be weakened or pre-implemented here.

## 11. Failure Cases

Implementation is incomplete or invalid if any of the following occurs:

- A required model or required `LocalRepairCaseState` field is absent or renamed.
- A field, collection element, public boundary, or serializer relies on `Any` or an untyped dictionary.
- Unknown fields or invalid enum strings are accepted.
- Boolean values are accepted for integer fields such as `exit_code` or `attempt_number`.
- `max_attempts` accepts a value other than `1`, or `attempt_number` accepts a value outside `0..1`.
- Blank required strings, negative/non-finite durations, or malformed timestamps are accepted.
- Timestamp defaults are naive, non-UTC, evaluated at import time, or shared incorrectly between instances.
- Collection defaults are shared between model instances.
- Valid models fail a JSON serialization/deserialization round trip or change enum/timestamp meaning during it.
- Validation performs I/O or executes content contained in schema fields.
- A dependency other than Pydantic is added, existing tool constraints are loosened, or CI/security checks are bypassed.
- Adjacent or future task behavior is implemented.

## 12. Acceptance Criteria

1. `app.agent.schemas` defines the six required Pydantic v2 models and the four supporting string enums specified here.
2. `LocalRepairCaseState` contains exactly the execution-plan fields with the types, defaults, and constraints in Section 6.
3. All fields are typed and strict mypy passes without `Any`, new ignores, or suppressions.
4. Valid minimal and fully populated instances can be constructed.
5. Missing required fields, unknown fields, invalid types, blank constrained strings, invalid enum values, invalid attempt values, and invalid durations raise `ValidationError`.
6. A fully populated state survives `model_dump_json` followed by `model_validate_json` with semantic equality, including nested models, enums, lists, and timestamps.
7. Default timestamps are timezone-aware UTC values created per instance and fall within test-captured clock bounds.
8. Default list fields are independent between instances.
9. Pydantic is the only new dependency and is declared as `pydantic>=2,<3`.
10. No application workflow, external adapter, sandbox, fixture, CLI, persistence, API, or v0.2 behavior is introduced.
11. The unchanged shared validation command passes formatting, linting, strict type checking, unit tests, and applicable integration tests.

## 13. Tests and Validation Commands

Add `tests/unit/test_schemas.py` with focused tests covering:

- construction of each schema and minimal/full state construction;
- malformed and unknown input rejection;
- strict integer validation, including rejection of booleans;
- enum acceptance and invalid enum rejection;
- `max_attempts=1` and `attempt_number` constraints;
- non-negative finite duration validation;
- JSON serialization round trip of a fully populated state;
- timezone-aware UTC timestamp defaults and timestamp round trips;
- independent timestamp evaluation and mutable list defaults;
- assignment validation for invalid post-construction updates.

Run from the repository root using the existing Python 3.12 virtual environment:

```text
.venv\Scripts\python.exe --version
.venv\Scripts\python.exe -m pip check
.venv\Scripts\python.exe scripts/check.py
git diff --check
git status --short
```

`scripts/check.py` covers Ruff formatting, Ruff linting, strict mypy, unit tests, and applicable integration tests. No Docker or external-service integration test applies to this task. Dependency installation is not a validation command for implementation: use the existing environment and stop if it does not contain the declared dependency or is not Python 3.12.
